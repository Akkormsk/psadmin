# Бэклог: адаптер FSPrint (calc.fsprint.ru)

Дата: 2026-09-28. Первый шаг по плану пользователя (§6 его ТЗ) — минимальный
HTTP-клиент, воспроизведение известного запроса, изучение структуры ответа.
Ничего из FSPrint-специфичных ID/enum сюда не додумано — только то, что
реально увидено в ответе.

## Готово

- `tenders/integrations/fsprint.py` — минимальный клиент: form-urlencoded
  POST, без cookies и browser-only заголовков (`Content-Type`, `Accept`,
  `X-Requested-With` — ровно то, что просил пользователь начать с; `Origin`/
  `Referer` не понадобились, реальный смоук-тест прошёл без них).
- `tenders/integrations/fsprint_mapping.py` — единственное однозначное
  соответствие: `quantity → tiraj`. Остальное не мэппится, пока не изучено.
- `tenders/management/commands/fsprint_probe.py` — смоук-тест на реальном
  payload пользователя (packet, тираж 1000), без изменения значений.
- `tenders/test_fsprint.py` — 5 тестов, сеть везде замокана.
- `tenders/integrations/fsprint_sample_payload.json` — реальный запрос
  пользователя, разобранный из его cURL (127 полей).
- `tenders/integrations/fsprint_sample_show_variant_response.html` —
  реальный ответ второго запроса (см. ниже), для справки при разборе.

## Главная находка: расчёт — это ДВА запроса, не один

`POST /ext/calc/calculate` с телом из payload пользователя **не возвращает
цену**. Он возвращает HTML-заглушку с номером расчёта:

```html
Номер расчёта: <span id="jir_nom">1547916</span> от 28.09.2026 ...
<script>
  $.post('/ext/calc/show_variant', {record: 1547916, var: 0, curr: 'RUR', usetemp: 0}, ...);
</script>
```

Сама раскладка стоимости приходит вторым запросом —
`POST /ext/calc/show_variant` с `{record, var, curr, usetemp}`, где `record`
— номер, полученный из ответа первого запроса. Оба запроса — обычный HTML
(не JSON), с `<table>` внутри, рассчитанным на прямую вставку в страницу
калькулятора.

## Что реально нашлось во втором ответе (реальные цифры на 1000 пакетов)

Верхняя таблица — «Срочность / Наценка % / Общая стоимость / Цена за 1 шт.»,
несколько строк (разные сроки изготовления, от базового до 6 часов):

| Срочность | Наценка | Общая стоимость | Цена за 1 шт. |
|---|---|---|---|
| базовый (25-30 дней) | 0% | 74 515.99 ₽ | 74.52 ₽ |
| 3-4 дня | 70% | 126 677.19 ₽ | 126.68 ₽ |
| 1-2 дня | 100% | 149 031.99 ₽ | 149.03 ₽ |
| 24 часа | 150% | 186 289.98 ₽ | 186.29 ₽ |
| 12 часов | 300% | 298 063.97 ₽ | 298.06 ₽ |
| 6 часов | 350% | 335 321.97 ₽ | 335.32 ₽ |

Дальше в том же ответе — подробная раскладка по статьям себестоимости,
каждая в собственной HTML-таблице вида `<tr><td>Название: </td><td><b>значение</b></td></tr>`
(похоже на стабильный, парсибельный формат): стоимость сборки пакета,
скотч (с артикулом и длиной), ручки (тип/диаметр/цвет/стоимость установки),
стоимость бумаги (с плотностью/фактурой/цветом/ценой за лист и за кг),
стоимость печатных форм и печати (приладка + цена за прогоны отдельно),
резка. Всего в этом ответе десятки таких пар — не переписаны здесь
целиком, смотри `fsprint_sample_show_variant_response.html`.

## Полный список продукции калькулятора (снято 28.09.2026)

`tenders/integrations/fsprint_product_list.json` — 23 `product_id` со
страницы calc.fsprint.ru (выпадающий список `#product`): алкоголь,
блокноты, бумажные стаканчики, визитки, воблеры, журналы, календари
(квартальные/перекидные/домики), коробки конфет, коробочки, кубарики
для записей, листовая печать, наклейки, **пакеты**, папки,
послепечатные операции, самокопирующиеся бланки, скретч-карты,
флажки, цифровая персонализация, шоколадки, конверты.

`tenders/integrations/fsprint_default_form_fields.json` — допустимые
значения основных полей (типы/плотности/фактуры бумаги, ламинация,
шелкография, тиснение, конгрев) для продукта, который открыт на
странице по умолчанию — но какие именно поля есть у КАЖДОГО из 23
product_id и какие из этих значений для них актуальны, ещё не снято
(набор полей формы меняется при выборе продукта в интерфейсе).

## Структура полей всех 23 продуктов (снято 28.09.2026)

По просьбе пользователя прошли по всем 23 `product_id`, переключая
`#product` на живой странице и читая имена полей формы. Результат —
`tenders/integrations/fsprint_product_fields.json`. Кратко:

- набор полей **действительно разный** по продуктам (от нуля отделок у
  «Конвертов»/«Шоколадок» до полного списка ламинация+лак+шёлкография+
  тиснение+конгрев+высечка у «Пакетов»/«Блокнотов»/календарей) — гипотеза
  подтвердилась, общий парсер «одна схема на все продукты» не подойдёт;
- поля повторяются блоками `main1`/`main2`/`main3` (несколько частей
  изделия — напр. обложка+блок у блокнотов/журналов) с одинаковым набором
  полей на блок; `block_count` в верхнем уровне управляет, сколько блоков
  показывать;
- `use_handmade_<hex-id>` — общий каталог ручных допотделок (69 одних и
  тех же id почти везде, где он вообще есть); не продукт-специфичен,
  нужно снимать один раз отдельно (только id встречены, подписи чекбоксов
  — нет, не сняты);
- **«Воблеры» (`vobler`) фактически не имеют полей расчёта** — в форме
  только блок контактов/реквизитов (заявка), самого калькулятора для
  этого product_id на сайте, похоже, нет, хотя пункт есть в `#product`;
- «Послепечатные операции» (`postprint`) — единственный продукт без
  блоков main1/2/3, все поля на верхнем уровне (видимо, конструктивно
  одноблочный).

## Решено пользователем 28.09.2026

- **Единый вызов**: `calculate()` и `show_variant()` объединяются в один
  метод адаптера (пользователь: «да как хочешь, давай в один») — следующий
  шаг реализации, не сделано ещё.
- **Срок для стоимости**: базовый срок остаётся дефолтом на сейчас;
  пользователь допускает в будущем подбирать срочность по желаемому сроку
  поставки из ТЗ («это отдельная информация, её в просчёте вообще нет») —
  отложено, не блокирует текущий шаг.

## Чего всё ещё не знаем

- допустимые значения (не только имена) полей для каждого конкретного
  product_id — сняты пока только для дефолтного продукта главной страницы
  (`fsprint_default_form_fields.json`);
- `lam_film_id` (длинный hex-ID из примера «Пакеты») — не нашёлся как
  статичный список, видимо вычисляется по комбинации type+subtype+thick
  отдельным запросом;
- зависимости между полями (что обязательно, что взаимоисключающее);
- стабильна ли структура HTML-ответа `show_variant` между продуктами,
  или каждый product_id даёт свою вёрстку — пока проверено только на
  «Пакетах»;
- что значат `var`/`curr`/`usetemp` в `show_variant` за пределами
  увиденных значений (0, 'RUR', 0);
- подписи (не id) для 69 `use_handmade_*` — не сняты.

## Сделано 28.09.2026: единый вызов + парсер

- `tenders/integrations/fsprint.py`: `calculate()` теперь один вызов —
  сам делает `/calculate` → достаёт `record` (regex по `id="jir_nom"`) →
  сам делает `/show_variant` → парсит ответ в `FSPrintPriceResult`
  (`timeline_options`: срок/наценка%/сумма/цена за шт. — все 6 строк;
  `fields`: все пары `<tr><td>label</td><td><b>value</b></td></tr>` одним
  плоским списком, без попытки разложить на «шапку» и «статьи себестоимости»
  отдельно — это была бы догадка о структуре, а не факт из ответа).
- Формат ошибок не изменился: если `record` не нашёлся или таблица сроков
  пустая — `FSPrintPriceResult.error` с текстом, что не так, `raw_text`
  сохранён целиком для ручного разбора; никогда не выдумывает цифры.
- Живая проверка на «Пакетах» (тот же продукт/полный набор полей, что и
  раньше) — цифры совпали с сохранённым примером день в день
  (74515.99 ₽ / 74.52 ₽ за базовый срок, все 6 строк), новый двух-шаговый
  клиент работает end-to-end на реальном сервере.
- Тесты (`tenders/test_fsprint.py`, 6 шт., сеть замокана) проверяют:
  структуру обоих запросов, извлечение `record`, разбор `timeline_options`
  и `fields` на реальном сохранённом ответе, и «не найден record» на
  постороннем формате.

## Проверка на ВТОРОМ продукте — сделана 28.09.2026, формат подтверждён

Пользователь дал реальный cURL для «Блокнотов» (179 полей, 3 блока —
обложка/блок/подложка, DevTools). Живой прогон через `calculate()`:

- `record` получен, `error` пустая;
- 6 строк сроков изготовления, но **со своими подписями и порогами**
  («Обычная, 5-7 дней» / «Оперативная: 3-4 дня» / ... вместо «базовый
  срок : 25-30 дней» у «Пакетов», наценки 0/20/30/50/100/150% вместо
  0/70/100/150/300/350%) — подтверждает, что подписи и пороги
  продукт-специфичны, а КОЛОНКИ и HTML-структура таблицы — нет;
- 133 статьи себестоимости тем же плоским форматом `<tr><td>label</td>
  <td><b>value</b></td></tr>`.

Сохранено как второй эталонный фикстур:
`fsprint_sample_payload_blocknote.json`,
`fsprint_sample_show_variant_response_blocknote.html`. Добавлен
регресс-тест `test_real_blocknote_sample_confirms_the_format_is_not_specific_to_one_product`
в `tenders/test_fsprint.py` (7 тестов всего, все проходят) — фиксирует,
что парсер не подогнан под частности «Пакетов».

**Вывод**: формат `show_variant` (таблица сроков + плоский список пар
label/value) стабилен минимум на 2 из 23 продуктов с очень разной
структурой (1 блок vs 3 блока). Хватит ли этого, чтобы считать парсер
общим для всех 23, или проверить ещё — решение пользователя; пользователь
предложил прислать реальные payload по всем продуктам («могу хоть по
всем»), не запрошено дополнительно, так как для текущего шага (адаптер +
парсер) двух показательных примеров достаточно.
