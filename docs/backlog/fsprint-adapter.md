# Бэклог: адаптер FSPrint (calc.fsprint.ru)

Дата: 2026-09-28. Первый шаг по плану пользователя (§6 его ТЗ) — минимальный
HTTP-клиент, воспроизведение известного запроса, изучение структуры ответа.
Ничего из FSPrint-специфичных ID/enum сюда не додумано — только то, что
реально увидено в ответе.

## Готово

- `tenders/integrations/fsprint.py` — минимальный клиент: form-urlencoded
  POST, без cookies и browser-only заголовков (`Content-Type`, `Accept`,
  `X-Requested-With` — ровно то, что просил пользователь начать с; `Origin`/
  `Referer` не понадобились, реальный смоук-тест прошёл без них).
- `tenders/integrations/fsprint_mapping.py` — единственное однозначное
  соответствие: `quantity → tiraj`. Остальное не мэппится, пока не изучено.
- `tenders/management/commands/fsprint_probe.py` — смоук-тест на реальном
  payload пользователя (packet, тираж 1000), без изменения значений.
- `tenders/test_fsprint.py` — 5 тестов, сеть везде замокана.
- `tenders/integrations/fsprint_sample_payload.json` — реальный запрос
  пользователя, разобранный из его cURL (127 полей).
- `tenders/integrations/fsprint_sample_show_variant_response.html` —
  реальный ответ второго запроса (см. ниже), для справки при разборе.

## Главная находка: расчёт — это ДВА запроса, не один

`POST /ext/calc/calculate` с телом из payload пользователя **не возвращает
цену**. Он возвращает HTML-заглушку с номером расчёта:

```html
Номер расчёта: <span id="jir_nom">1547916</span> от 28.09.2026 ...
<script>
  $.post('/ext/calc/show_variant', {record: 1547916, var: 0, curr: 'RUR', usetemp: 0}, ...);
</script>
```

Сама раскладка стоимости приходит вторым запросом —
`POST /ext/calc/show_variant` с `{record, var, curr, usetemp}`, где `record`
— номер, полученный из ответа первого запроса. Оба запроса — обычный HTML
(не JSON), с `<table>` внутри, рассчитанным на прямую вставку в страницу
калькулятора.

## Что реально нашлось во втором ответе (реальные цифры на 1000 пакетов)

Верхняя таблица — «Срочность / Наценка % / Общая стоимость / Цена за 1 шт.»,
несколько строк (разные сроки изготовления, от базового до 6 часов):

| Срочность | Наценка | Общая стоимость | Цена за 1 шт. |
|---|---|---|---|
| базовый (25-30 дней) | 0% | 74 515.99 ₽ | 74.52 ₽ |
| 3-4 дня | 70% | 126 677.19 ₽ | 126.68 ₽ |
| 1-2 дня | 100% | 149 031.99 ₽ | 149.03 ₽ |
| 24 часа | 150% | 186 289.98 ₽ | 186.29 ₽ |
| 12 часов | 300% | 298 063.97 ₽ | 298.06 ₽ |
| 6 часов | 350% | 335 321.97 ₽ | 335.32 ₽ |

Дальше в том же ответе — подробная раскладка по статьям себестоимости,
каждая в собственной HTML-таблице вида `<tr><td>Название: </td><td><b>значение</b></td></tr>`
(похоже на стабильный, парсибельный формат): стоимость сборки пакета,
скотч (с артикулом и длиной), ручки (тип/диаметр/цвет/стоимость установки),
стоимость бумаги (с плотностью/фактурой/цветом/ценой за лист и за кг),
стоимость печатных форм и печати (приладка + цена за прогоны отдельно),
резка. Всего в этом ответе десятки таких пар — не переписаны здесь
целиком, смотри `fsprint_sample_show_variant_response.html`.

## Полный список продукции калькулятора (снято 28.09.2026)

`tenders/integrations/fsprint_product_list.json` — 23 `product_id` со
страницы calc.fsprint.ru (выпадающий список `#product`): алкоголь,
блокноты, бумажные стаканчики, визитки, воблеры, журналы, календари
(квартальные/перекидные/домики), коробки конфет, коробочки, кубарики
для записей, листовая печать, наклейки, **пакеты**, папки,
послепечатные операции, самокопирующиеся бланки, скретч-карты,
флажки, цифровая персонализация, шоколадки, конверты.

`tenders/integrations/fsprint_default_form_fields.json` — допустимые
значения основных полей (типы/плотности/фактуры бумаги, ламинация,
шелкография, тиснение, конгрев) для продукта, который открыт на
странице по умолчанию — но какие именно поля есть у КАЖДОГО из 23
product_id и какие из этих значений для них актуальны, ещё не снято
(набор полей формы меняется при выборе продукта в интерфейсе).

## Чего всё ещё не знаем

- какие поля/допустимые значения актуальны для КАЖДОГО конкретного
  product_id — снято только для дефолтного продукта на главной странице;
- `lam_film_id` (длинный hex-ID из примера «Пакеты») — не нашёлся как
  статичный список, видимо вычисляется по комбинации type+subtype+thick
  отдельным запросом;
- зависимости между полями (что обязательно, что взаимоисключающее);
- стабильна ли структура HTML-ответа `show_variant` между продуктами,
  или каждый product_id даёт свою вёрстку;
- что значат `var`/`curr`/`usetemp` в `show_variant` за пределами
  увиденных значений (0, 'RUR', 0).

## Следующий шаг — решить с пользователем

1. Писать ли парсер под ЭТУ конкретную HTML-структуру (`<tr><td>label:
   </td><td><b>value</b></td></tr>`) как первый общий разборщик «ключ →
   значение», или дождаться второго product_id, чтобы не подогнать парсер
   под частности одного продукта.
2. Какое из шести значений «Цена за 1 шт.» (по срочности) considerать
   основным для расчёта себестоимости — видимо базовый срок, но это
   решение пользователя, не наше.
3. Добавлять ли `record`/`show_variant` как второй шаг adapter.calculate()
   сразу (единый вызов «дай мне цену»), или оставить как два явных метода.
