# Бэклог: единый жизненный цикл тендера + локальный AI-агент

Дата: 2026-09-20, обновлено 2026-09-21. Собрано по итогам обсуждения: подготовительный
аудит проекта под внедрение локального AI-агента, разбор экономики каскада (реальные
модели/тарифы из `tenders/gateway_budget.py` и активной `CascadeConfigVersion`), и план
Кодекса по единой сущности тендера (см. `docs/tender_lifecycle_experiment.md` — этот
бэклог его расширяет и продолжает, не заменяет).

Файл теперь ведётся в рабочей ветке `tender-lifecycle` (worktree `psadmin2-lifecycle`),
не в `main` — вся дальнейшая работа по этому бэклогу коммитится сюда.

## Параллельный контекст

Локальная БД переведена на Postgres, чистая — миграции применены, среда рабочая
(`psadmin2-lifecycle`, свой venv, свой `.env`). Конфигурация активного каскада
(`CascadeConfigVersion`) на этой базе не перепроверялась — не полагаться на старое
чтение из `db.sqlite3` (шаги 1/2/4 — `gemini-3.1-flash-lite`, шаг 6 — `gpt-5.4-mini`)
без свежей проверки, когда дойдём до тюнинга каскада.

### 2. `price_stats_for` — своя история first, без балльной системы — готово
**Статус**: закрыто. Убрана вся старая балльная модель (код ОКПД2 + слова +
заказчик + цена + свежесть, `_STRONG_SCORE`/`_SCOPE_CAP`/`_PRICE_BAND`) —
вместо неё простое правило без весов: похожесть = совпадение значимых слов в
названии и товарных позициях (`_keywords`, уже было в коде). Сначала берём
свои прошлые тендеры (`TenderEstimate` с известным `actual_reduction_percent`
— неважно, выиграли или проиграли, статус на статистику не влияет; товарные
позиции `TenderLine` дают точность на уровне товара, а не общей формулировки
закупки вроде «поставка полиграфии»), не хватает до 10 (`_TARGET_COUNT`) —
добираем из `ContractStat` (открытая история), тем же правилом по словам
`subject`. Совпадений меньше 3 (`_MIN_SAMPLES`) — раздел не показываем.
Тай-брейк при равном совпадении слов — тот же регион, затем свежее. Убраны
`match_level`/`customer_stats` (не просили, лишняя сложность). Карточка
тендера теперь показывает разбивку «своя история / открытая» по каждой
строке. Тесты — `PriceStatsCardTests`, `PriceStatsRelevanceTests`.

`tenders/0033` с переносом старых данных, без потери. Документы, оценка
риска, сам расчёт (`TenderEstimate`+`TenderLine`) и результат торгов

### 7. Вердикт-механика — переформулирован: только после себестоимости
**Пересмотрено 2026-09-21.** Первая формулировка (свести риск + прогноз
снижения в вердикт сразу на стадии «Проверка», до расчёта) — ошибка: без
знания реальной себестоимости прогноз снижения на 20% или 30% сам по себе
ничего не говорит о том, выгодно ли участвовать. Смысл появляется только
когда есть реальная себестоимость (уже посчитанная `TenderEstimate`/
`TenderLine`, с реальным `net_profit`/`roi` в `summary_snapshot`, а не
черновик) — тогда можно проверить, держится ли приемлемый ROI при
прогнозируемом снижении цены, и не блокируют ли участие юридические факторы
из оценки рисков.

**Новая форма**: вердикт живёт на странице расчёта (`tenders/home.html`), не
на странице найденного тендера, и появляется автоматически, как только
себестоимость посчитана по-настоящему (не черновик) — без отдельной кнопки,
по тому же принципу, по которому уже сами появляются разделы риска и
прогноза. Технически уже возможно без новых сущностей — через якорь
`Tender` из пункта 3 расчёт видит свой `FoundTender` (оценку риска) и свой
же прогноз снижения, а свою реальную себестоимость/ROI уже знает сам.
Комбинация: реальный ROI при прогнозируемом снижении + правовые красные
флаги из оценки риска → «стоит участвовать» / «не стоит» / «маржа
маленькая, но юридически чисто» и т.п. Живой, пересчитывается при каждом
открытии страницы расчёта (входы могут меняться — обновили себестоимость,
перепроверили риск, обновился прогноз). Один снимок вердикта имеет смысл
зафиксировать в момент перехода на «Торги» — для честного сравнения
прогноз/факт вместе с уже записываемым итогом торгов (пункт 8).

**Зависимости**: пункт 2 (прогноз, готово), пункт 3 (якорь `Tender`, готово)
— реализация не блокирована ничем из оставшегося бэклога.
