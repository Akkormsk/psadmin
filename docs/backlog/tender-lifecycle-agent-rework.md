# Бэклог: единый жизненный цикл тендера + локальный AI-агент

Дата: 2026-09-20, обновлено 2026-09-21. Собрано по итогам обсуждения: подготовительный
аудит проекта под внедрение локального AI-агента, разбор экономики каскада (реальные
модели/тарифы из `tenders/gateway_budget.py` и активной `CascadeConfigVersion`), и план
Кодекса по единой сущности тендера (см. `docs/tender_lifecycle_experiment.md` — этот
бэклог его расширяет и продолжает, не заменяет).

Файл теперь ведётся в рабочей ветке `tender-lifecycle` (worktree `psadmin2-lifecycle`),
не в `main` — вся дальнейшая работа по этому бэклогу коммитится сюда.

## Параллельный контекст

Локальная БД переведена на Postgres, чистая — миграции применены, среда рабочая
(`psadmin2-lifecycle`, свой venv, свой `.env`). Конфигурация активного каскада
(`CascadeConfigVersion`) на этой базе не перепроверялась — не полагаться на старое
чтение из `db.sqlite3` (шаги 1/2/4 — `gemini-3.1-flash-lite`, шаг 6 — `gpt-5.4-mini`)
без свежей проверки, когда дойдём до тюнинга каскада.

## Порядок работ

### 1. Канбан жизненного цикла тендера — реализован, не закоммичен
**Статус**: первая версия готова и проверена в браузере на реальных данных
(создание/перенос карточки, «В расчёт» переносит FoundTender → TenderEstimate
по-настоящему). Изменения: `tender_selection/views.py` (новая `kanban()`,
`_found_tender_card`/`_estimate_card`, `tender_list` дispatch по `?view=`),
`templates/tender_selection/kanban.html` (новый), `templates/tender_selection/
list.html` (добавлен тумблер Канбан/Список). Лежит в рабочей копии
`psadmin2-lifecycle`, ждёт решения — коммитить или дорабатывать дальше.

**Уточнение объёма по итогам обсуждения 2026-09-21** (расширяет исходный пункт 1,
делается тем же заходом, до отдельного коммита):
- Плоский список (`?view=list`) переиспользует те же карточки, что и канбан
  (сейчас список видит только `FoundTender`) — показывает тендеры **всех стадий**
  сразу, с быстрым фильтром по стадии тем же паттерном кнопок, что уже есть у
  44-ФЗ/223-ФЗ (`.ts-lawtabs`).
- Ручной дропдаун «интересно/не интересно» (`FoundTender.review`) убирается из
  UI — вместо него показывается **вычисляемый статус**, привязанный к действию
  «Оценить» (уже существует как `analyze_documents`/`risk_status`, ручной повтор
  риск-анализа), а не к ручному выбору. Поле `review` в БД не трогаем — просто
  перестаёт быть тем, чем управляют руками.
- **У каждой стадии — свой набор бейджей-результатов, не один общий статус**:
  светофор риска (уже есть на карточке канбана), прогноз снижения %/источник
  прогноза (новое, см. пункт 2 ниже), ROI (уже есть на карточках «Расчёт»), позже
  — факт вs прогноз на «Результат» (пункт 8). Показывать рядом, мелкими
  отдельными бейджами, не схлопывать в одну оценку — так же, как сейчас риск и
  ROI уже показаны раздельно на карточке.

**Зависимости**: нет новых — БД уже готова.

### 2. Чистка `ContractStat` / `price_stats_for` + прогноз в «Оценить»
**Зачем**: сейчас портит картину — в пул статистики попадают контракты с
несостоявшимся аукционом/единственным поставщиком (снижение 0-1% не потому что
рынок так решил, а потому что не было реальной конкуренции), и совпадение по
ОКПД2 слишком грубое. `price_stats_for` уже фильтрует `shared_purchase=False`,
но не фильтрует по числу участников — это и есть пробел.

**Объём**: фильтр `participants_count >= 2`; приоритет КТРУ над ОКПД2; поднять
вес текстового/ключевого совпадения. Вручную сверить 20-30 реальных сравнений
перед тем как полагаться на цифру. Затем — завести прогноз снижения как второй
результат кнопки «Оценить» (пункт 1), рядом с риск-анализом, одним действием.

**Зависимости**: нет (чистый код).

### 3. Единая сущность тендера (аддитивно, поэтапно)
Без изменений по существу — см. предыдущую версию бэклога. `Tender`,
`TenderDocumentImport`, `TenderItem` (происхождение каждого факта), `TenderRiskAssessment`,
`TenderCalculation` (снимок позиций на момент расчёта), `TenderOutcome` (участие,
итог торгов — даёт дом `ContractStat.is_ours`). Вводить рядом со старыми таблицами,
не одним коммитом. Первая фаза (`Tender`+`TenderDocumentImport`) может идти
параллельно с пунктом 1 — канбан потом просто переключит источник данных.

### 8. Автоматическое получение результата торгов + приоритет своей истории
**Статус**: механизм (`gosplan.fetch_contracts` по номеру закупки) проверен
вживую, не реализован. **По явному решению пользователя — отложено**, не
сбивать текущую последовательность (1→2→далее). Когда дойдём: `price_stats_for`
сначала ищет среди `ContractStat.objects.filter(is_ours=True)`, и только при
отсутствии своей истории — общий рыночный пул; ручное «вписать номер закупки и
забрать факт» пишет туда же, тем же кодом, что и автоматика.
