# Протокол: тест и прод

- **Прод** — https://admin.psodin.ru. Рабочий сайт и рабочая база.
- **Тест** — https://test.admin.psodin.ru. Близнец прода на том же VDS (46.149.70.38, российский IP —
  ЕИС и банк доступны), со своей копией базы. Прод он не видит и не трогает.

## Поток работы

1. Код пишется локально; всё, что можно проверить локально, проверяется локально (тесты обязательны).
2. **Тест обновляется автоматически**: как только агент закончил правку и локальные тесты прошли,
   он сам выкладывает её на тест и присылает ссылку, что смотреть. Команда не нужна, время суток не важно.
3. Пользователь проверяет на тесте. Замечания → агент правит → тест снова обновляется сам.
4. Команда **«в прод»** — агент переносит на прод ровно ту версию, что сейчас на тесте.

## Команды пользователя

| Команда | Что делает агент | Когда можно |
|---|---|---|
| **«в прод»** | Коммит в `main` ровно той версии, что на тесте → push → `deploy.sh` на проде (бэкап базы → миграции → перезапуск → проверка) → отчёт. | Только после 20:00 МСК. Днём — только если пользователь явно сказал, что понимает, что сейчас день. |
| **«обнови тестовую базу»** | Затирает базу теста свежей копией рабочей базы и применяет миграции текущего кода теста. | В любое время |
| **«запусти на тесте …»** (сбор тендеров, синк банка, риски и т. п.) | Разово запускает задачу на тесте. Автозадачи на тесте выключены всегда. | В любое время |
| **«откати прод»** | Возвращает прод к предыдущей версии. Если в выкатке были миграции — предлагает восстановить базу из бэкапа, сделанного перед деплоем, и сначала говорит, какие данные при этом потеряются. | Сразу |

## Правила агента

1. На прод попадает только то, что было на тесте. Если после выкладки на тест код менялся — сначала снова на тест.
2. Упавшие локальные тесты — на тест не выкладывать, отчитаться.
3. Тест ходит в те же внешние сервисы (ЕИС, ГосПлан, Модульбанк — только чтение).
   Вызовы ИИ на тесте тратят тот же бюджет, что и прод, — запускать точечно.
4. Прод не править руками на сервере: только через `main` + `deploy.sh`.
5. База теста одноразовая: её можно ломать, «обнови тестовую базу» вернёт её в рабочее состояние.

## Техника (для агента)

- Выкладка на тест: из рабочей копии агента
  `git ls-files -co --exclude-standard -z | tar --null -cf - -T - | ssh deploy@46.149.70.38 '…'` —
  распаковать в `~/psadmin-test.new`, заменить `~/psadmin-test`, записать `~/psadmin-test/.twin-version`
  (время + коммит), затем `~/psadmin-test/deploy/vds/twin.sh up`.
- Настройки теста: `~/psadmin-test.env` (все `*_ENABLED=0`, своя база `test-db`, свой `DJANGO_SECRET_KEY`).
- «обнови тестовую базу»: `~/psadmin-test/deploy/vds/twin.sh refresh-db`.
- Разовая задача: `docker compose -f ~/psadmin-test/deploy/vds/compose.test.yml run --rm -T test-web python manage.py <команда>`.
- «в прод»: `~/psadmin/deploy/vds/deploy.sh`.
