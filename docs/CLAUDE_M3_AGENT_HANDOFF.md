## Непереговорная архитектура

PSADMIN имеет **одного** ассистента. Web-чат сейчас и Telegram/другие каналы
потом — разные входы в один и тот же backend, разговор и действия.

У ассистента ровно два вида возможностей.

1. **READ** — единый безопасный механизм Django ORM. Он читает разрешённые
   модели и связи, ищет, фильтрует, сортирует, группирует и агрегирует. Никаких
   отдельных `get_cash`, `find_tenders` или других domain-specific AI tools.
   LLM строит структурированный план, backend валидирует его по Django metadata
   и исполняет ORM без SQL/Python от LLM.
2. **ACTION** — библиотека/энциклопедия уже существующих действий сайта.
   Это не библиотека новых AI-функций. Запись в ней содержит понятное описание,
   параметры, права, подтверждение, источник и ссылку на **реальный общий
   серверный исполнитель**.

Абсолютный запрет: не писать бизнес-логику, CRUD, формулы, калькуляторы или
сценарии специально для агента. Нельзя создавать `assistant_create_x`,
`agent_update_y`, отдельные модели/таблицы/маршруты ради агента или дублировать
код Django View. Agent adapter допустим только для преобразования формата
параметров/результата; он не меняет бизнес-данные сам.

Правило для любого write/action:

```
кнопка сайта / HTTP View  -> общий backend executor <- ассистент / Telegram
```

View отвечает только за HTTP, форму, сообщения и redirect. Executor отвечает
за валидацию, бизнес-эффекты и структурированный результат. Перед записью
ассистент обязан сформировать preview и дождаться серверного подтверждения;
отмена, повторная отправка и устаревшие данные не должны повторно менять БД.

Если действие существует только внутри View, не обходить View прямой записью.
Минимально вынести его фактическое ядро в сервис и перевести кнопку сайта на
тот же сервис. Если это нельзя сделать без риска — остановиться, зафиксировать
долг и спросить владельца.

## Библиотека возможностей и будущее

Существующая app-owned регистрация через `assistant_capabilities.py` уже есть.
Не переписывать её и не создавать второй registry/статический манифест.

- Модели и READ-каталог обнаруживаются из Django metadata.
- Для нового пользовательского действия разработчик обязан: (1) создать или
  переиспользовать общий backend executor, (2) перевести UI на него, (3)
  опубликовать его в `assistant_capabilities.py` приложения с корректным
  `source` реального исполнителя, схемой, правами и отметкой подтверждения.
- Нельзя честно автоматически угадать смысл любой произвольной Python-функции.
  Поэтому не имитировать магическую авто-регистрацию: регистрация action —
  короткая декларация рядом с приложением, а не новая реализация.
- Добавить/сохранить проверяемый стандарт: тест должен обнаруживать
  неразрешаемый `source`; для каждого опубликованного action UI и assistant
  вызывают одного исполнителя. Правило уже внесено в `AGENTS.md` — не ослаблять.
- При добавлении нового приложения Agent Core не меняется: только модель
  автоматически попадает в READ, а action — через app-owned декларацию.

## Решения владельца по действиям

### Делать сейчас, но только после аудита UI -> executor

1. Тендеры: скрыть неподходящий тендер; изменить плюс/минус-слова входящего
   фильтра; запустить аудит слов и применить выбранные рекомендации; включить
   или исключить завершённый тендер из прогноза; передать тендер в расчёт;
   сохранить нашу ставку.
2. Расчёты: копировать и удалить сохранённый расчёт. Сохранение расчёта уже
   сделано. Сохранение — обычное создание/изменение записи, но оно требует
   ассистентского preview/подтверждения и при создании имени — уточнения имени.
3. Касса: добавить, изменить, удалить операцию; сохранить/сверить кассу.
4. Банк: запустить существующую синхронизацию платежей; скрыть/показать
   банковский платёж для менеджеров.
5. Контрагенты и расчёт: создать контрагента; передать прайс/исходные данные в
   существующий поток обработки; проверить и активировать калькулятор;
   выполнить расчёт у контрагента. В будущем Telegram должен использовать тот
   же поток; не делать отдельное распознавание скриншота только для AI.
6. Производство: посмотреть/подтвердить предложенный маршрут; изменить
   способ/технологию производства; добавить контрагента в производственную
   цепочку.
7. Знания: подтвердить/отклонить предложенное производственное знание;
   сохранить полезный результат/правило как подтверждённое знание; удалить
   ошибочное или устаревшее подтверждённое знание.

### Не публиковать ассистенту

- Восстановление скрытого тендера.
- Ручное изменение статуса проверки тендера. Это существующая UI-кнопка
  «интересен»: она запускает оценку рисков. Владелец ожидает автоматизацию,
  поэтому агенту она не нужна.
- Ручная фиксация итога тендера. Результат должен получаться автоматически из
  протокола/контракта и архивироваться с историей.
- Ручной запуск profile-triage: на сайте есть запасная кнопка, но основной
  процесс уже автоматически запускает проверку входящих; агенту кнопка не нужна.

### Отложить и обязательно спросить владельца перед реализацией

- Настройки поиска тендеров и настройки оценки: это реальные админ-страницы,
  но владелец пока не решил, какие из них должны изменяться вручную через
  ассистента, а какие быть автоматическими. Не публиковать молча.
- `Order` (закрытый заказ: создать/изменить/удалить): сущность пока не
  используется. Не делать; сохранить явный долг до начала работы с заказами.
- Если в ходе аудита обнаружится действие, которое затрагивает внешнюю
  интеграцию, деньги, производственную цепочку или сложный импорт и общий
  executor неочевиден — не угадывать. Описать фактическую кнопку, executor,
  последствия, зависимость и задать владельцу короткий вопрос до кода.

## Сложные точки — не маскировать заглушками

- Импорт прайса -> проверка -> активация калькулятора — сложный единый поток;
  сначала найти существующие upload/parse/review/activate действия и связать
  их общими executors.
- Маршрут, технология, цепочка контрагентов — сложные связанные сущности.
- Банковская синхронизация — зависит от реального уже существующего
  интеграционного процесса.
- Производственные знания — требуют корректного источника, явного
  подтверждения и обратимого удаления.

Не объявлять эти возможности готовыми по одной регистрации или mock-тесту.
Если базовая функция сайта отсутствует, это долг, а не повод создавать AI-only
функцию.

## Порядок работы

1. Проверить Git/PR и текущий diff.
2. Для каждого действия из списка найти кнопку/endpoint, View, сервис,

3. Если ядро во View — минимально вынести только его в сервис; перевести View;
   зарегистрировать этот же executor в owning `assistant_capabilities.py`.
4. Проверить разговор через реальный assistant conversation + fake LLM:
   недостающие параметры -> preview -> explicit confirm -> ровно одно действие;
   cancel/stale/repeat ничего не меняют.
5. Запускать целевые тесты после каждого небольшого блока и только затем
   commit/push в существующую ветку. Не переписывать READ, M2 UI, Cascade или
   Calculation V2 без отдельного фактического основания.
6. Перед отчётом проверить `git status`, SHA, `gh pr view 3`, base/head,
   результаты тестов и список оставшихся долгов.

## Definition of done

Пользователь может в одном чате (с будущим Telegram на том же backend):

- свободно читать и анализировать доступные данные через единый READ;
- выбрать существующее действие сайта естественным языком;
- получить уточнения, preview и подтверждение;
- выполнить ровно ту же бизнес-операцию, что выполняет кнопка сайта;
- увидеть результат и источник, без вымышленных данных или скрытой прямой
  записи в таблицу.

Не заявлять «полностью работающий ассистент», пока выбранные действия не имеют
проверенного общего executor, сквозного диалогового теста и не остались
обозначенные выше долги.
