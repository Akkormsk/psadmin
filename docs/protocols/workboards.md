# Доски и исполнение

## Продуктовый контракт — DECIDED_BACKLOG, 2026-11-27

Доски — общий интерфейс реальной работы внутри жизненного цикла Tender, Order и Task. Торговый канбан остаётся отдельным контуром подготовки, участия, результата и будущего юридического закрытия; доски не заменяют его и не превращают Tender в Order. Результаты, обучение на завершённых случаях и возможный отдельный контур лидов будут согласованы позже. MVP не является полной ERP.

Tender, Order и Task остаются разными сущностями. Выигранный Tender остаётся Tender: на доске появляется связанная карточка его исполнения, а карточка торгов продолжает показывать торговый и юридический контекст. Завершение исполнения не закрывает Tender. Order — отдельная прямая оформленная сделка без участия в торгах; переработка Order и лидов выполняется после MVP задач и исполнения Tender.

### Доска и карточка

- Одна карточка принадлежит ровно одной доске. Доступ и фильтрация по ролям определяются отдельно и не создают вторые карточки на других досках.
- У каждой доски есть обязательная первая колонка «В очереди» и обязательная последняя колонка «Готово». Новая карточка попадает в первую; перенос в последнюю устанавливает признак завершения. Пользователь может переименовать эти колонки и создать, переименовать, упорядочить или удалить любые промежуточные колонки. Перемещение карточек остаётся ручным.
- Карточка ссылается на Tender, Order или Task и не копирует их основные данные. На первом этапе карточками становятся Task и связанное исполнение Tender; Order подключается позже.
- Простая Task может состоять только из названия и описания. Для сложной Task пользователь по желанию добавляет подзадачи. Tender/Order содержит товары; Task содержит подзадачи. Общий интерфейс не должен заставлять пользователя заполнять необязательные уровни.

### Внутренняя работа

- У товара или подзадачи есть маршрут исполнения. Для товара маршрут приходит из подготовки Tender/Order; для Task пользователь вводит маршрут вручную.
- Этап маршрута содержит минимум одну проверку выполнения; дополнительные проверки необязательны. Выполнение проверок продвигает работу по маршруту, завершение всех этапов отмечает товар или подзадачу выполненными. Перенос всей карточки между колонками остаётся ручным.
- Маршрут описывает план, а отметки выполнения относятся к конкретной карточке исполнения. Проверка «Печать произведена» в одном Tender не меняет маршрут и состояние других карточек. Изменение плана после начала работы не должно молча уничтожать уже сохранённый факт выполнения.
- Лицевая сторона карточки в будущем может кратко показывать прогресс внутренних товаров/подзадач, но без обязательных сроков и тяжёлой производственной аналитики в MVP.

### Отложенный бэклог

- Ненавязчивая инфографика: часы — есть ожидание; синий круг — требуется действие пользователя. Автоматическое определение этих признаков и правила их появления пока не реализуются.
- Сроки, загрузка сотрудников, частичное выполнение тиража, уведомления и расширенная автоматизация.
- Отдельный канбан лидов до оформления прямого Order.
- Размещение результатов, юридического закрытия и обучения на завершённых случаях.
- Автоматическая передача выигранного Tender в исполнение. MVP использует явное действие пользователя с выбором доски и не создаёт повторную карточку исполнения.

Tender остаётся в торговом контуре; товары и подготовленные маршруты переиспользуются, а факты выполнения изолированы в его исполнении. Возврат внимания к юридическому закрытию — отдельный последующий этап.
- M3: устранить дублирование финансовых данных параллельно с безопасными срезами досок; не удалять TenderEstimate/Line и OrderEstimate/Line до аудита потребителей и согласованного перехода. FinancialSnapshot — предложение для фиксации версий, не утверждённая схема. Compute и сохранённые quotes не удалять без доказанной замены.
- Order подключается после проверки Task и Tender: новый Order использует тот же UI товаров и исполнения, но остаётся отдельной сущностью. Лиды и предварительные сделки не попадают на доску исполнения без отдельного согласованного контура.
- Финальная приёмка: целостность, права, сохранение истории и отказ от старого раздела расчётов заказов только после доказанной замены. PROD отдельно по разрешению.
