Ты работаешь над существующим Django-проектом PSADMIN, приложение расчёта тендеров / заказов.

Нужно спроектировать и реализовать в существующем приложении «Расчёты» полноценную систему:

- технологических этапов;
- контрагентов;
- связи этапов с контрагентами;
- корректировки маршрута через ассистента;
- контекстных вопросов ассистента;
- обучения на feedback пользователя;
- предложений глобальных изменений базы;
- удобного UI управления этой базой.

ВАЖНО:
не создавай отдельное приложение PSADMIN «Производство».

Эта база нужна прежде всего AI-ассистенту внутри приложения расчётов.
Если пользователь считает заказ вручную без ассистента, эта механика почти не должна мешать ему.

Перед изменениями сначала изучи существующий repository, модели, templates, JS, CSS и текущую реализацию ассистента.

Не строй параллельную архитектуру, если в проекте уже есть подходящие сущности.


==================================================
ТЕКУЩАЯ ТОЧКА СТАРТА
==================================================

Работай в текущем checkout и продолжай существующую реализацию. Не переключай, не ребейзь и не меняй ветку main.

В стартовом состоянии уже есть локальная реализация маршрутов: `tenders/routes.py`, доработки `tenders/services.py`, `tenders/views.py`, `templates/tenders/home.html` и тесты `tenders/test_routes.py`. Маршрут строится отдельно от каскада; подбор готового товара запускается только явным действием внутри соответствующего этапа. Не возвращай старую принудительную схему «Закупка готового изделия» и не отменяй это разделение.

В каскаде уже добавлен Jev как выбираемый исполнитель шага 6 (`tenders/jev.py`, настройки лаборатории и `tenders/cascade.py`). Оставь его переключаемым вариантом; не делай Jev обязательным и не меняй активную конфигурацию каскада без отдельной причины.

Сначала изучи текущий код, историю Git, `docs/assistant_protocol.md` и фактические модели. Расширяй существующую реализацию, не заменяй её второй параллельной системой.


==================================================
1. ОСНОВНАЯ КОНЦЕПЦИЯ
==================================================

Нужно разделить три типа знаний.

A. ЭТАП

Отвечает на вопрос:

«Что технологически можно сделать?»

Примеры:

- Закупка готового изделия
- Универсальная типография
- Цифровая типография
- Офсетная типография
- УФ-печать
- Лазерная гравировка
- Тампопечать
- Шелкография
- Вышивка
- DTF
- Сублимация
- Швейное производство
- ПВД-пакеты
- Силиконовые браслеты
- Значки
- нестандартное производство / ручной просчёт

Этап — фундаментальная сущность.
Количество этапов относительно небольшое.

Не нужно создавать отдельный этап для каждого товара.


B. КОНТРАГЕНТ

Отвечает на вопрос:

«Кто способен выполнить этот этап и как получить у него цену?»

Один контрагент может быть связан с несколькими этапами.

Один этап может иметь много контрагентов.


C. УРОК / ПРАВИЛО

Отвечает на вопрос:

«Когда и почему выбирать такой маршрут?»

Пример:

Если бумажный пакет производится полностью с нуля,
не использовать:

Закупка готового изделия → Нанесение

а использовать:

Универсальная типография.

Уроки — не описание технологии.
Это опыт выбора маршрута.


==================================================
2. МАРШРУТ НЕ ЯВЛЯЕТСЯ СПРАВОЧНИКОМ
==================================================

Не создавай заранее постоянные сущности вроде:

Маршрут 1 = Закупка → УФ
Маршрут 2 = Закупка → Лазер
Маршрут 3 = Закупка → Вышивка

Это приведёт к комбинаторному взрыву.

Постоянными являются ЭТАПЫ.

Для конкретной позиции ассистент собирает маршрут на лету:

Этап A
↓
Этап B
↓
Этап C

После подтверждения маршрут конкретного заказа может использоваться как обучающий кейс / урок,
но не должен автоматически становиться новым фундаментальным route template.


==================================================
3. РОЛЬ ЭТАПА
==================================================

Не использовать один enum:

supplier / production / combo

Лучше хранить независимые возможности этапа:

supplies_input = да/нет
performs_production = да/нет

Пример:

Закупка готового изделия:
supplies_input = true
performs_production = false

УФ-печать:
supplies_input = false
performs_production = true

Универсальная типография:
supplies_input = true
performs_production = true

Также нужен признак:

terminal / завершает маршрут

Лучше:

always / never / sometimes

или эквивалентная простая модель.

Не усложнять без необходимости.

Существующий технический способ обработки шага маршрута сохраняется на переходный период. Он нужен только бэкенду, чтобы понимать, запускать ли подбор по каталогу, расчёт цены или завершающее действие. Не показывать этот технический слой пользователю как «роль этапа» и не заменять им свойства самого этапа.


==================================================
4. ЭТАП ДОЛЖЕН ОПИСЫВАТЬ ОБЩУЮ ТЕХНОЛОГИЮ
==================================================

На уровне этапа хранить общие свойства.

Концептуально:

name
key / slug
description
active

supplies_input
performs_production
terminal_mode

what_we_make / product scope
when_to_use
when_not_to_use

required_parameters
optional_parameters

input_object / тип объекта обработки

compatibility / возможные предыдущие и следующие этапы
или более простые правила совместимости, если они действительно нужны.

Не создавать 30 обязательных полей.

Допускается JSON/structured configuration,
если это хорошо вписывается в существующую архитектуру.

Не хранить технические IDs конкретного поставщика внутри Stage.


==================================================
5. КОНТРАГЕНТЫ
==================================================

Название в UI использовать:

«Контрагент»

а не «Поставщик».

Контрагент может:

- продавать готовые изделия;
- продавать материал;
- выполнять производственную операцию;
- выполнять полный цикл;
- совмещать несколько функций.

Не нужно жёстко классифицировать его одной ролью.

Главное — его связи с этапами.


==================================================
6. СВЯЗЬ ЭТАП ↔ КОНТРАГЕНТ
==================================================

Это очень важная отдельная сущность.

Не размножать Stage для каждого контрагента.

Пример:

УФ-печать
    ├── Контрагент A
    ├── Контрагент B
    └── Контрагент C

У каждого может быть своя настройка.

На связи этап ↔ контрагент может храниться:

- active;
- preferred / priority;
- price_source_type;
- calculator/API/catalog/manual;
- ограничения;
- дополнительные обязательные параметры;
- mapping параметров;
- комментарии;
- сроки;
- минимальный заказ;
- ссылка на внешний калькулятор;
- API config reference;
- формула / structured price rules;
- источник знания;
- дата актуальности.

Но не надо сразу делать все поля жёсткими колонками.

Используй минимально необходимую структуру + расширяемые structured settings,
если это рационально.

Способ получения цены выбирается из конечного набора уже реализованных или специально добавленных функций бэкенда: внутренний калькулятор, каталог/API, прайс-лист, внешний калькулятор, внешний API, ручной запрос или история цен. LLM не придумывает новые способы расчёта и не знает внутренние параметры адаптеров.


==================================================
7. ОБЩИЕ ПАРАМЕТРЫ VS ПАРАМЕТРЫ КОНТРАГЕНТА
==================================================

Ассистент должен работать с нашим внутренним семантическим языком.

Например:

quantity
material
width
height
colors
white_ink
lamination

а не:

main1paper_type=22
main1lam_film_id=...

Внутренние параметры внешнего калькулятора принадлежат адаптеру контрагента.

Пример:

PSADMIN:
material = coated_200

FSPrint adapter:
material → main1paper_type=22
density → 200

LLM не должен знать внутренние IDs API/калькуляторов.

Исправить маршрут

УФ-печать

«Здесь нужно считать печать

текущего item.

Feedback может:

- изменить параметры;
- сменить контрагента;
- уточнить ограничения;
- заменить этап;
- удалить этап;
- добавить соседний этап.

Если из текста следует постоянное знание,
предложить сохранить его отдельно.


==================================================
23. FUNCTION CALLING
==================================================

Не давай LLM прямой unrestricted доступ к БД.

Разделить функции на два уровня.


A. SAFE CURRENT-CALCULATION ACTIONS

Эти функции меняют только текущий draft / tender item.

Концептуально:

ask_question

add_stage
remove_stage
move_stage
replace_stage

update_stage_parameters

select_counterparty

recalculate

Названия адаптируй к архитектуре repository.

Модель может использовать их
при разборе feedback текущего расчёта.

Backend ОБЯЗАН валидировать параметры.


B. GLOBAL PROPOSALS

LLM не должен напрямую выполнять:

create_stage
disable_stage
update_global_stage
create_counterparty
modify_counterparty
set_global_route_rule

Вместо этого использовать:

propose_create_stage
propose_update_stage

propose_add_counterparty
propose_update_counterparty

propose_link_counterparty_to_stage

propose_route_rule

Proposal ничего не изменяет автоматически.

Он создаёт preview/action card.

Пользователь нажимает:

[Запомнить]

или:

[Подтвердить]

После этого backend выполняет обычные детерминированные изменения.


==================================================
24. ОДИН FEEDBACK МОЖЕТ ПОРОДИТЬ НЕСКОЛЬКО ИЗМЕНЕНИЙ
==================================================

Пример пользовательского feedback:

«Такие бумажные пакеты считай через универсальную типографию,
цену бери у FSPrint.»

Для текущего расчёта AI может понять:

replace_stage:
Универсальная типография

select_counterparty:
FSPrint

recalculate


Глобально из этого потенциально следуют:

A.

дополнить:

Универсальная типография

product scope:
+ бумажные пакеты


B.

создать Lesson:

бумажный пакет собственного изготовления
→ Универсальная типография


C.

создать / подтвердить связь:

FSPrint
↔
Универсальная типография


Пользователь НЕ должен видеть три DB-команды.

Показать человеческий summary:

«Запомнить это как постоянный способ расчёта бумажных пакетов через FSPrint?»

[Запомнить]

[Только этот расчёт]

Backend самостоятельно раскладывает подтверждённое знание по сущностям.

Если из одного feedback следуют несколько независимых глобальных изменений, показать одну компактную карточку с отдельными пунктами выбора. Например: сохранить урок, дополнить область применения этапа, подтвердить связь этапа с контрагентом. Пользователь может подтвердить все пункты или только часть. Каждое подтверждённое изменение бэкенд сохраняет отдельной записью; неподтверждённое не сохраняет.


==================================================
25. УРОКИ
==================================================

Lesson хранит логику принятия решения.

Пример:

Context / признаки:
полностью индивидуальный блокнот

Bad / discouraged:
Закупка готового изделия → Нанесение

Preferred:
Универсальная типография

Reason:
производится с нуля


Не путать Lesson со Stage description.


Lesson желательно связывать с:

source tender/item
original assistant decision
user feedback
corrected decision
confirmed_by
confirmed_at

Это позволит постепенно обучать систему на реальных решениях.

26. НЕ ОБУЧАТЬСЯ БЕЗ ПОДТВЕРЖДЕНИЯ

это НЕ обязательно Lesson.

Пользователь явно подтвердил / исправил / нажал «Запомнить»:

Нужен source:

system preset
