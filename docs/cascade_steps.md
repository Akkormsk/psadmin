# Границы каскада подбора

Актуальная точка входа — `Cascade.run()` в `tenders/cascade.py`. Старые описания
поискового маршрута в `assistant_protocol.md` не описывают эту реализацию.
В каскаде ровно восемь методов `step_N_*`, порядок закреплён в
`tenders.test_cascade_contract`. Вспомогательные методы не являются новыми шагами.

| Шаг | Вход | Выход | Основные проверки |
|---|---|---|---|
| 1 `step_1_parse_tz` | Позиция, строки ТЗ, правила галочек | `self.tz: list[Criterion]`, название и синонимы | `CascadeStep1Tests` |
| 2 `step_2_search_plan` | Название и синонимы шага 1 | Уникальные поисковые фразы | Контракт последовательности |
| 3 `step_3_search_by_name` | Фразы | Пул товаров с релевантностью и вариантами | `CascadeSearchTests` |
| 4 `step_4_name_filter` | Пул и искомый тип | Пул после фильтра названий | `CascadeSearchTests`, `CascadeNameFilterCacheTests` |
| 5 `step_5_hard_gates_and_collapse` | Пул, критерии, количество | Карточки групп с вариантами | `CascadeHardGateTests`, `CascadeCollapseTests` |
| 6 `step_6_agent_matrix` | Карточки, выбранные критерии, кэш и инструкции | Матрицы и `matrix_status` каждой карточки | `tenders.test_cascade_step6`, `CascadeAgentTests`, `CascadeAxisPrefillTests`, `CascadeFeedbackTests` |
| 7 `step_7_collapse_and_sort` | Карточки и ручные приоритеты | Полный отсортированный список без исключённых | `CascadeSortTests`, `tenders.test_cascade_step7` |
| 8 `step_8_price_and_top` | Отсортированный список | Топ-10 после обновления Oasis | Интеграционные тесты с заглушкой API |

Каждая правка шага проверяется на фиксированных входах независимо от остальных.
Результат передаётся следующему шагу через существующий контракт; переносить
правило одного шага в другой нельзя. Изменения разных шагов фиксируются отдельными
коммитами. Это позволяет сравнивать поведение и откатывать их независимо.

## Шаг 6: ограниченная проверка

- Предварительный порядок: релевантность, меньше `n` по числовым осям, больше
  `y` по осям, цена. Новых сигналов или парсеров характеристик не добавлено.
- `CASCADE_STEP6_FIRST=25`: размер очередной порции карточек. Внутри модель
  по-прежнему читает полную доступную карточку пачками по три.
- `CASCADE_STEP6_CEILING=75`: максимум новых проверок за запуск; ноль отключает
  новые проверки. Кэшированные карточки не расходуют этот лимит.
- Остановка: минимум десять полностью оценённых карточек с хотя бы одним `y`
  и не более одного `n`, либо лимит, либо конец списка. Кэш участвует в условии.
- Полный ответ с явными `m` кэшируется, но без `y` не считается достаточным
  для остановки. Частичные и пустые ответы не кэшируются как завершённые.
- Полностью пустая порция ответов прекращает новые вызовы в этом запуске.
- Числовые оси перекрывают клетки модели, но не маскируют неполноту её ответа.
- Классификация фидбека остаётся отдельным существующим проходом внутри шага 6.
  Ограничение матрицы не ограничивает затраты на фидбек.

Контракт карточки: `matrix_status=complete` — полный ответ или полный кэш;
`incomplete` — модель вызвана, но ответ неполон; `pending` — проверка не запускалась.
Без выбранных критериев карточки имеют `complete`. Признак не равен соответствию:
полностью проверенная карточка может иметь расхождения или неизвестные свойства.

`diagnostics.step6`: `pool` — незакэшированные карточки; `graded` — отправленные
модели, включая неудачные ответы; `batches` — порции; `cached` — полные оценки
из кэша; `complete` — полные оценки всего; `suitable` — удовлетворяющие условию
остановки; `pending` — не отправленные; `stop_reason` — причина остановки.

Раннее завершение экономит вызовы, но не доказывает сохранение глобального топ-10.
Повтор с достаточным кэшем не тратит токены на матрицу. Если подходящих оценок
недостаточно, следующий запуск может проверить оставшиеся карточки.

## Проверки и расходы

Шаг 7 читает `matrix_status`: при одинаковом ручном приоритете полностью
проверенные карточки идут перед непроверенными и неполными. Остальной ключ
матрицы, релевантность и цена не изменены. Резерв не удаляется.
Отсутствующий статус трактуется по прежнему правилу, чтобы шаг 7 оставался
совместим с предыдущей версией шага 6 при отдельном откате.

Разработка — только с моками, отдельной тестовой БД и блокировкой сети.
Рабочий кэш, production и баланс не изменять. После каждого запуска сообщать
реальный расход Timeweb; токены фиктивного ответа мока не являются расходом.
Живой замер требует отдельного разрешения пользователя и успешного `preflight`.
Фактическое время и рублёвая стоимость новой схемы без такого замера неизвестны.

## Лаборатория каскада

`/tenders/cascade-lab/` — закрытый экран суперпользователя для запуска тех же
восьми функций вне обычного ассистента. Лаборатория не записывает уроки и не
меняет код каскада из браузера. Она хранит собственные `CascadeLabRun` и
`CascadeLabCase`.

После каждого шага сохраняются его вход, выход, состояние каскада, время,
токены и оценка стоимости. Прогон можно остановить, продолжить следующим
шагом или создать ответвление с входа ранее выполненного шага. Выходы каталога
хранят упорядоченные ID и превью карточек; шаги 5–8 хранят JSON карточек.

Пользовательские карточки передаются JSON-массивом. Шаги 3–4 в таком прогоне
помечаются `skipped`, шаг 5 принимает этот массив, а шаги 6–8 работают обычно.
Ожидания теста поддерживают наличие/отсутствие ID, диапазон места, поля матрицы
и пределы времени/стоимости.

По умолчанию новый прогон останавливается после шага 5. Платный шаг 6 запускают
отдельным продолжением. Лимиты времени и рублей проверяются между блоками:
уже начатый вызов внутри блока они не прерывают. Перед работой применяется
общий `gateway_budget.preflight`.

Настройки `2.max_phrases`, `6.first_batch`, `6.ceiling` и размер топа применяются
только экземпляром каскада лаборатории. При отсутствии настроек обычный
ассистент использует прежние значения.
