# Эксперимент: единый жизненный путь тендера

Дата начала: 2026-09-17.

Этот документ фиксирует локальный эксперимент перед слиянием идеи в основной
`docs/assistant_protocol.md`. Он не заменяет протокол ассистента и нужен, чтобы
следующий разработчик быстро понял, зачем появились поля и сервисы вокруг
жизненного пути тендера.

## Задача

Тендер должен быть одной сущностью от первого появления в автоподборе до
расчёта, торгов и результата. Сейчас такой сущностью остаётся `FoundTender`:
она уже знает номер ЕИС, исходное извещение, риск-анализ, найденные документы и
связь с просчётом. Эксперимент не вводит новую большую модель `Tender`, чтобы не
ломать существующие экраны и перенос в расчёт.

Новая цель: подготовить `FoundTender` к будущему канбану, где тендеры идут по
колонкам:

- Входящие.
- Проверка.
- Расчёт.
- Торги.
- Результат.
- Архив.

## Решение в этом эксперименте

Добавлено поле `FoundTender.lifecycle_stage` и дата
`FoundTender.lifecycle_updated_at`. Это явный этап жизненного пути, который
будущий канбан сможет читать напрямую, не восстанавливая состояние из
комбинации `status`, `review`, `risk_checked_at`, `document_checked_at` и
`pushed_estimate_id`.

Переходы пока минимальные:

- новый тендер начинается во `Входящие`;
- автоматический или ручной разбор документов переводит новый тендер в
  `Проверка`;
- ручная отметка интересности тоже переводит новый тендер в `Проверка`;
- перенос в расчёт переводит в `Расчёт`;
- скрытие переводит в `Архив`.

Этапы `Торги` и `Результат` пока только подготовлены. Их логично связать со
статусами `TenderEstimate`: `pending` → `Торги`, `won/lost/not_participated` →
`Результат`.

## Документы ЕИС

Архив ЕИС не хранится. Сервер скачивает архив, раскрывает его в памяти,
извлекает нужную информацию и сохраняет только выжимки:

- `risk_assessment`, `risk_assessment_docs`, `risk_error`;
- `document_analysis`, `document_analysis_docs`, `document_error`.

Это сохраняет диск и не превращает приложение в хранилище клиентских документов.
Если разбор не удался, кнопка ручного повтора остаётся в карточке тендера.

## Товары и расчёт

Позиции из формализованного извещения остаются базой для создания
`TenderEstimate` и `TenderLine`. Разбор ТЗ из документов добавляет требования к
этим позициям и может предложить дополнительные найденные позиции. Сейчас такие
дополнительные позиции переносятся в расчёт с нулевой ценой и явным комментарием
для проверки.

Следующий шаг перед продом: сделать экран сравнения "извещение vs документы",
чтобы дополнительные позиции и требования подтверждались человеком до участия в
экономике расчёта.

## Ограничения

Это локальная ветка и эксперимент. Прод-деплой не предполагается без отдельного
решения.

Разбор документов может тратить токены только на извлечённый текст, не на сам
факт скачивания архива. На Timeweb важно держать лимиты размера архива,
количества файлов и общей распаковки.

## Куда двигаться дальше

1. Сделать канбан по `FoundTender.lifecycle_stage`.
2. Добавить ручной перевод между этапами для администратора.
3. Связать этапы торгов и результата со статусами `TenderEstimate`.
4. Сделать экран сверки товаров из извещения и документов.
5. После стабилизации перенести это описание в основной протокол ассистента.
