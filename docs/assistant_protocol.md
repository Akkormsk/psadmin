# Протокол работы тендерного ассистента

Этот документ — обязательная точка входа перед изменением логики ассистента, поиска товаров или расчёта себестоимости. Он описывает не интерфейс, а границы ответственности и фактический технический маршрут данных.

**Текущая стадия (2026-09-05): маршрут и себестоимость временно не считаются.** Идёт настройка поиска товара. Ассистент по каждой позиции всегда предполагает маршрут «Закупка готового изделия + Нанесение» без вызова LLM и не строит калькуляцию. Как только поиск устроит администратора, построение маршрута вернётся отдельным шагом (см. §16).

## 1. Назначение системы

Ассистент получает позицию тендера (НМЦК, наименование и ТЗ) и ищет варианты готового товара в каталогах Oasis и Gifts. Распознавание документов (НМЦК и ТЗ) не изменилось и описано в этом протоколе не будет отдельно — оно и раньше, и сейчас использует LLM для чтения документа и отдаёт структурированный список позиций и требований.

Главный принцип поиска:

> LLM не ищет товар и не знает структуру каталогов. Она только приводит грязное название позиции («Ветровка с логотипом», «сувенир рубашка-поло с символикой Думы...») к чистому виду и подсказывает несколько поисковых фраз — ровно так, как человек убрал бы канцелярские обороты перед тем, как вбить слово в поиск на сайте поставщика. Весь поиск, фильтрация и ранжирование — детерминированный код без LLM.

## 2. Источники истины

| Данные | Источник истины |
|---|---|
| Текущие цены и остатки Oasis | зеркало `CatalogProduct` (`sync_oasis_catalog`), при показе кандидатов — живой API по `ids=` для точных карточек |
| Товары, цены, остатки и категории Gifts | импорт XML в production-базу |
| Карта категорий Oasis/Gifts | зафиксированный снимок `CatalogCategory` |
| Постоянные правила поиска | `CatalogSearchRule` (применяются ко всем позициям) |
| Формулы, фильтрация и ранжирование | код бэкенда в Git |
| Неподтверждённая гипотеза и диалог | `ProductionTrainingSession` и `ProductionTrainingTurn` |

Git не хранит production-базу, выгрузки поставщиков, документы заказчиков и секреты.

## 3. Ответственность участников

### Администратор

- читает выдачу и решает, какой товар на самом деле подходит — детальная сверка с ТЗ (кроме склада, семейства цвета и типа) сейчас на администраторе, не на ассистенте;
- пишет правила обычным языком: что игнорировать, какие слова добавить/убрать, что исключить;
- удаляет правило крестиком на плашке — оно перестаёт действовать для текущей сессии;
- кнопкой «Подтвердить правила поиска» делает текущие правила постоянными для всех будущих позиций.

### LLM (один вызов на поиск)

- превращает грязное название позиции в короткий `item` (1–3 слова) и несколько поисковых `queries` — синонимов того же товара;
- убирает канцелярские обороты («с логотипом», «с символикой X», «услуги по изготовлению и поставке»), не подменяет вид товара более общим словом;
- применяет буквально правила администратора (глобальные + правила этой сессии), в том числе если они меняют item или queries;
- отдельным маленьким вызовом переводит одну фразу обратной связи в одно или несколько именованных правил.

LLM не выбирает категорию, не фильтрует и не ранжирует товары, не знает структуру каталогов поставщиков.

### Бэкенд

- ключевым скорингом выбирает категории по словам сущности (без LLM, §6);
- ищет товары локально (зеркало Oasis + Gifts, §6–7) — секунды, а не минуты;
- жёстко исключает только по объективным причинам (склад, явно не тот тип, семейство цвета, §8) и ранжирует по числу расхождений, затем по цене (§9);
- перед показом обновляет цену/остаток показанных карточек Oasis живым запросом (§7);
- хранит и применяет правила поиска — сессионные и постоянные (§10).

## 4. Полный маршрут одной позиции

1. Документ уже распознан: есть название позиции и (если было ТЗ) список характеристик.
2. Маршрут временно хардкожен: `["Закупка готового изделия", "Нанесение"]`, без LLM (см. заголовок документа).
3. `_build_search_plan()` — единственный вызов LLM в этом маршруте: название + характеристики + действующие правила → `{"item", "queries"}`. Занимает 0.5–3 секунды при типичном промпте без изображений.
4. `catalog_candidates_for_line()` ищет по `item`/`queries` в локальном зеркале Oasis и Gifts (§6–7), жёстко исключает и ранжирует (§8–9). Без LLM.
5. Перед возвратом бэкенд обновляет цену и остаток показанных карточек Oasis одним запросом `ids=` (§7).
6. Если есть точное совпадение с ценой — оно применяется в расчёт автоматически (`apply_catalog_candidate`).
7. Обратная связь администратора переводится в правило поиска (`_translate_search_feedback`) и сохраняется в сессии; кнопка «Подтвердить правила поиска» переносит их в `CatalogSearchRule` — постоянно и для всех позиций.
8. Каждый пересчёт сохраняется как `ProductionTrainingTurn`.

Основные точки кода: `tenders/services.py::build_training_hypothesis`, `tenders/services.py::_build_search_plan`, `tenders/catalog.py::_category_candidates`, `tenders/catalog.py::catalog_candidates_for_line`, `tenders/services.py::apply_catalog_candidate`.

## 5. Поисковый план

`catalog_intent`, который доходит до бэкенда, — просто «что искать», без DSL и без структурных ограничений:

```json
{
  "item": "ветровка",
  "categories": ["ветровка"],
  "synonyms": ["ветровка", "куртка ветровка", "ветровка мужская", "ветровка женская"],
  "required": [{"label": "Цвет", "value": "лаймово-зелёный"}],
  "search_rules": [{"id": "…", "text": "Исключать товары синего цвета", "label": "Без синего"}]
}
```

`required` — характеристики как они пришли из распознанного ТЗ (label/value), без операторов и уровней важности. `search_rules` — активные для этой сессии правила (глобальные правила из `CatalogSearchRule` передаются `_build_search_plan()` отдельно и не хранятся в `catalog_intent`).

## 6. Карта категорий и выбор категорий

### Правило

Категорию выбирает детерминированный ключевой скоринг `_category_candidates`, без
обращения к LLM. Это повторяет поведение навигации по дереву на сайте поставщика:
слова из `item`, названия позиции и `synonyms` сопоставляются с названиями и путями
категорий, и берётся до двух наиболее совпадающих узлов на каждый источник
(`oasis`, `gifts`). Скоринг игнорирует канцелярские слова, которые есть почти в
каждой категории промо-товаров и почти в каждой позиции тендера («логотип»,
«символика», «нанесение», «вручение», «изготовление», «поставка», «услуга») —
иначе они перевешивают единственное слово, которое действительно называет товар.

Если по источнику ни одна категория не набрала совпадений, по нему выполняется
только полнотекстовый поиск (§7).

### Oasis

- Полное зеркало каталога — `CatalogProduct` (`python manage.py sync_oasis_catalog`), как у Gifts. Пока не синхронизирован ни разу, поиск падает на медленный живой обход категорий API (`_OASIS_PAGE_CEILING` страниц, лимит API — 1 запрос/сек).
- Карта категорий — снимок `CatalogCategory`, обновляется `sync_oasis_categories` или при первом поиске.
- Цена и остаток в зеркале могут быть устаревшими на часы — поэтому перед показом бэкенд обновляет их живым запросом (§7). Постоянного расписания пересинхронизации зеркала пока нет — это открытый вопрос эксплуатации, не решённый на уровне кода.

### Gifts

- Полный импорт `sync_gifts_catalog()` читает `product.xml`, `tree.xml`, `stock.xml` и `filters.xml`.
- `tree.xml` сохраняется в `CatalogCategory` и связывает каждый товар с `category_ids` и `category_names`.
- Выбранная категория фильтрует товары по реальному ID; полнотекстовый поиск использует `search_text`.
- Собственного живого API для Gifts нет, поэтому цена и остаток не обновляются живым запросом перед показом — используется значение из последнего импорта.

Оба источника ищутся одним и тем же кодом (`_local_catalog_pool`) — категория ищется через JSON-фильтр СУБД, если она поддерживается (Postgres на проде), либо облегчённым проходом только по ID и списку категорий, без загрузки полного текста карточки (SQLite локально).

## 7. Полнотекстовый поиск, живая цена и завершение маршрута

Поиск обязан завершить маршрут, а не останавливаться после одной неудачной попытки:

1. товары ключевых категорий каждого источника (§6);
2. параллельно — полнотекстовый поиск по `item`/`synonyms` (Oasis — через `search`, Gifts — через `search_text`); по Gifts он выполняется, когда категории дали мало результатов, по Oasis — когда категория не найдена;
3. ранжирование точных или ближайших товаров (§8–9);
4. одним батч-запросом `ids=` бэкенд обновляет цену и остаток показанных карточек Oasis, взятых из зеркала — это единственный живой запрос к Oasis в обычном поиске;
5. только после этого — результат «не найдено» с диагностикой источников и причин отсева.

Товар, найденный только полнотекстом (не входящий в выбранную категорию), проходит строгую проверку типа: обычная футболка не может пройти как поло.

Нельзя ослаблять явные запреты и тип товара. Положительные требования можно использовать для выбора ближайшей альтернативы, но расхождение обязательно показывается пользователю.

**Важно про Oasis API:** `category` и `search` нельзя передавать вместе — `search` при этом молча игнорируется. `id=`/`article=` в единственном числе тоже игнорируются и возвращают весь каталог (десятки тысяч строк, минуты) — никогда их не использовать. Пакетный `ids=` (через запятую) — единственный проверенный способ быстро получить несколько карточек по ID, ~1 секунда на любое количество.

## 8. Факты, фильтры и частичные совпадения

Свойства читаются из структурированных полей товара, атрибутов, названия и описания. Поэтому слово `женская` в названии считается значением пола даже при пустом отдельном поле.

Каждое требование получает одно из трёх состояний: `match` (известно и совпадает), `mismatch` (известно и не совпадает), `unknown` (карточка не даёт данных).

Жёстко (до ранжирования) товар исключается только по объективным причинам:

- другой товарный тип (по семантике; для товара из явно выбранной категории несовпадение по названию — это `unknown`, а не отсев);
- другое семейство цвета, когда и требуемый, и предложенный цвет однозначно определены (белый против красного), а в названии нет подходящего оттенка;
- недостаточный общий остаток нужного варианта;
- запрещённое значение (`not_in`, `not_contains`), если оно явно подтверждено;
- нулевой остаток.

Всё остальное (400 мл вместо 450, 95% хлопка вместо 100%, детский крой при отсутствии в ТЗ явного требования взрослого) — **оставляет товар как ранжируемую альтернативу** с явно показанным расхождением. Отсутствие данных в карточке никогда не удаляет товар: это `unknown`. Более глубокая сверка с ТЗ (кроме этих объективных причин) сейчас на администраторе — ассистент не пытается судить о ней автоматически (нет отдельного ревизора, см. §10).

## 9. Ранжирование

Никаких числовых баллов и весов. Среди не отсеянных товаров порядок такой:

1. точные варианты (нет `mismatch` и `unknown`) выше частичных;
2. меньше `mismatch`;
3. меньше `unknown`;
4. ниже цена;
5. стабильная сортировка по названию и артикулу.

Цена — не вес, а последний критерий. Она не компенсирует лишнее несовпадение.

Поставщик на ранжирование не влияет.

Результат объясняется напрямую списком требований (`✓ Материал: металл`, `✗ Объём: требуется 450–500 мл, товар 400 мл`, `? Покрытие: данных в каталоге нет`), без отдельного AI-вызова.

## 10. Правила поиска (обратная связь)

Ревизора на LLM сейчас нет — администратор сам решает, какой товар в выдаче подходит, и управляет поиском правилами:

1. Администратор пишет фразу («убери синие», «добавь слово опт», «игнорируй категорию носки»).
2. `_translate_search_feedback()` — маленький вызов LLM — превращает фразу в одно или несколько именованных правил: `{"text": "...", "label": "..."}`. Если фраза не про поиск (например, про маршрут или цену), правил не будет.
3. Новые правила добавляются к правилам сессии и показываются плашками у списка товаров. Крестик на плашке убирает правило из сессии и пересчитывает поиск без него.
4. Правила сессии передаются в `_build_search_plan()` при каждом пересчёте этой позиции — тем же способом, что и глобальные (§ниже), но действуют только для текущей сессии, пока её не подтвердили.
5. Кнопка «Подтвердить правила поиска» переносит все правила сессии в `CatalogSearchRule` (постоянно, `is_active=True`). С этого момента правило участвует в поиске **любой** позиции, не только той, где было создано — глобальной привязки к типу товара пока нет.

Правило — обычный текст, не DSL и не структурная команда. Его буквально понимает и применяет `_build_search_plan()` при следующем поиске — так же, как он понимает саму позицию.

## 11. Расчёт и себестоимость

Пока маршрут хардкожен (см. заголовок), полноценного расчёта себестоимости нет: `costs` в гипотезе всегда пустой список, кроме одного случая — точное совпадение с ценой из каталога автоматически становится статьёй расходов через `apply_catalog_candidate()` (то же самое поведение, что было раньше). Ручное добавление источника цены (`add_calculation_source` / `apply_verified_source_quote`) технически не тронуто и продолжает работать, но без активной калькуляции маршрута практической ценности до возвращения §16 не имеет.

## 12. Диагностика

Каждая попытка поиска должна сохранять:

- режим (`selected_categories` или `full_text`);
- реальные `category_tasks`;
- поисковые термины;
- число полученных и рассмотренных товаров;
- число исключений по причинам `out_of_stock`, `product_type`, `colour`, `forbidden`;
- количество точных и частичных совпадений;
- итоговое число кандидатов;
- статус каждого источника (включая ошибку живого обновления цены, если она не удалась — в этом случае остаётся значение из зеркала, поиск не падает).

Сообщение «не найдено» без этих данных считается недостаточной диагностикой.

## 13. Найденные инженерные ошибки (архив)

1. **Три вызова LLM на выбор категории** (retrieval → селектор → верификатор). Селектор судил по *названию* узла и отбрасывал верную категорию, хотя идеальное совпадение было в кандидатах. Убрано целиком: категорию выбирает детерминированный ключевой скоринг `_category_candidates`, ноль вызовов LLM.
2. **Канцелярские слова перевешивали название товара.** «Ветровка с логотипом» находила «Блокноты с логотипом» и «Ароматические диффузоры с логотипом» — слово «логотип» встречается почти в каждой категории промо-товаров. Исправлено стоп-словами в скоринге (§6) и обрезкой хвоста фразы перед поиском (§3, LLM).
3. **Ревизор проверял только явно перечисленные пункты ТЗ.** Поло-рубашка, полностью подходящая по материалу/цвету/плотности, проходила как точное совпадение для запроса «майка», потому что тип товара нигде не был отдельным пунктом ТЗ. Промежуточное решение (пока действовал ревизор): всегда добавлять «Тип товара» первым пунктом проверки. Сейчас ревизора нет вовсе — эту проверку временно делает администратор.
4. **SQLite без индекса на JSON-принадлежность категории** — фильтр по категории превращался в построчный проход по всей таблице (30–37 тыс. строк) с полной десериализацией каждой карточки (включая многокилобайтные текстовые поля) просто чтобы проверить список категорий. Отняло до 4 секунд на источник при заведомо небольшом результате. Исправлено: сначала лёгкий проход только по ID и списку категорий, полная карточка подгружается только для найденных совпадений.
5. **Oasis-поиск был живым API-обходом категории** (до 6 страниц по 500 позиций, лимит 1 запрос/сек) — 15–45 секунд на одну немаленькую категорию. Замена на локальное зеркало (§6) свела то же самое к секундам; живым запросом теперь обновляется только цена/остаток показанных 10 карточек (§7).
6. **`category`+`search` в Oasis API молча игнорируют `search`**, `id=`/`article=` в единственном числе возвращают весь каталог вместо ошибки — проверено эмпирически перед тем, как полагаться на эти параметры (см. §7).
7. Старый подтверждённый пример мог принести в новый расчёт каталожную цену, хотя текущий поиск не нашёл товар — цена принимается только из текущей найденной карточки (не изменилось).

## 14. Обязательная проверка при изменениях

Перед развёртыванием изменения поиска должны доказать тестами:

1. Ключевой скоринг выбирает специфичную категорию (поло, а не «Одежда») без вызова LLM.
2. Канцелярские слова («логотип», «символика» и т.п.) не перевешивают название товара в скоринге категорий.
3. При отсутствии точного свойства возвращается ближайший товар с расхождением, а не пустой список.
4. Gifts сохраняет категории и связи товаров при полном импорте.
5. Когда категория источника не найдена, по нему выполняется полнотекстовый поиск.
6. Цена без текущего кандидата не попадает в расчёт.
7. Несовпадение по обычной характеристике оставляет товар альтернативой; жёстко отсеивают только тип, семейство цвета, остаток и явные запреты.
8. Постоянное правило поиска (`CatalogSearchRule`) применяется к позиции, для которой оно не создавалось.
9. Локальные тесты не подключаются к production-базе и не бьют по живому API Oasis (мокать клиента).

## 15. Условный запуск каталога

Пока запускается на каждую позицию безусловно (маршрут хардкожен, см. заголовок). Раньше, когда маршрут строила LLM, каталог опрашивался только при шаге «Закупка готового изделия» в маршруте (`route.steps`) — эта развилка (`route_buys_finished_good`) вернётся вместе с §16.

## 16. Возврат маршрута и себестоимости (следующий этап, не начат)

Когда поиск устроит администратора, маршрут строится отдельным, отдельно тестируемым шагом — не общим вызовом вперемешку с поисковым планом, как было раньше. Ориентировочно: небольшой вызов LLM на маршрут (независимый от `_build_search_plan`), с тем же принципом — LLM понимает намерение, бэкенд считает. Условный запуск каталога (§15) и полноценный расчёт себестоимости (§11) возвращаются вместе с этим шагом. Детали не зафиксированы — будут описаны здесь, когда работа начнётся.
