# Протокол работы тендерного ассистента

Этот документ — обязательная точка входа перед изменением логики ассистента, поиска товаров или расчёта себестоимости. Он описывает не интерфейс, а границы ответственности и фактический технический маршрут данных.

**Текущая стадия (2026-09-06): маршрут и себестоимость временно не считаются.** Идёт настройка поиска товара. Ассистент по каждой позиции всегда предполагает маршрут «Закупка готового изделия + Нанесение» без вызова LLM и не строит калькуляцию. Поиск + обратная связь + обучение переделаны на «детерминированный поиск → один проход ИИ по короткому списку → та же формула сортировки → уроки» (§9–§10). Как только поиск устроит администратора, построение маршрута вернётся отдельным шагом (см. §16).

## 1. Назначение системы

Ассистент получает позицию тендера (НМЦК, наименование и ТЗ) и ищет варианты готового товара в каталогах Oasis и Gifts. Распознавание документов (НМЦК и ТЗ) не изменилось и описано в этом протоколе не будет отдельно — оно и раньше, и сейчас использует LLM для чтения документа и отдаёт структурированный список позиций и требований.

Главный принцип поиска:

> LLM не ищет товар и не знает структуру каталогов. Она только приводит грязное название позиции («Ветровка с логотипом», «сувенир рубашка-поло с символикой Думы...») к чистому виду и подсказывает несколько поисковых фраз — ровно так, как человек убрал бы канцелярские обороты перед тем, как вбить слово в поиск на сайте поставщика. Весь поиск, фильтрация и ранжирование — детерминированный код без LLM.

## 2. Источники истины

| Данные | Источник истины |
|---|---|
| Текущие цены и остатки Oasis | зеркало `CatalogProduct` (`sync_oasis_catalog`), при показе кандидатов — живой API по `ids=` для точных карточек |
| Товары, цены, остатки и категории Gifts | импорт XML в production-базу |
| Карта категорий Oasis/Gifts | зафиксированный снимок `CatalogCategory` |
| Уроки поиска (обратная связь) | `Lesson` (json-поля, всплывают по контексту, §10) |
| Строки ТЗ вне подбора | `RequirementSkipRule` (метка → снята в новых тендерах) |
| Формулы, фильтрация и ранжирование | код бэкенда в Git |
| Неподтверждённая гипотеза и диалог | `ProductionTrainingSession` и `ProductionTrainingTurn` |

Git не хранит production-базу, выгрузки поставщиков, документы заказчиков и секреты.

## 3. Ответственность участников

### Администратор

- читает выдачу и решает, какой товар на самом деле подходит — детальная сверка с ТЗ (кроме склада, семейства цвета и типа) сейчас на администраторе, не на ассистенте;
- пишет правила обычным языком: что игнорировать, какие слова добавить/убрать, что исключить — в поле обратной связи **того блока**, который правит (у блока «Закупка готового изделия» своё поле, у маршрута своё). Кнопка «Учесть и пересчитать» пересчитывает только этот блок;
- удаляет правило крестиком на плашке — оно перестаёт действовать для текущей сессии;
- кнопкой «Принять и обучить» (нижняя стик-панель) принимает расчёт: себестоимость переносится в позицию, каждое замечание сессии становится `Lesson` с контекстом (§10), сессия закрывается. Принять расчёт без единого нового замечания тоже можно.

### LLM — ровно два места в поиске

1. **Поисковый план** (`_build_search_plan`, один вызов): грязное название позиции → короткий `item` (1–3 слова) + несколько `queries` (синонимы того же товара) + `skip_labels` (строки ТЗ, которые не являются признаком товара). Убирает канцелярские обороты, не подменяет вид товара более общим словом. Не видит ни обратной связи, ни уроков.
2. **Проход по короткому списку** (`_run_shortlist_pass`, один вызов, **только если есть что применять**): читает все ~40 отранжированных карточек целиком + свободный текст администратора (замечания этой сессии + подходящие уроки прошлых позиций) и правит у карточек три вещи — оценки по пунктам ТЗ (`✓`/`✗`/`?`), ячейку приоритета (`0`/`1`), флаг «убрать». Больше ничего. Свежая позиция без замечаний и без уроков — этот вызов не делается вовсе.

LLM не выбирает категорию, не делает тяжёлый поиск, не считает `✓/✗/?` с нуля, не трогает формулу сортировки, не знает структуру каталогов поставщиков.

### Бэкенд

- ищет товары полнотекстом по названию и описанию всех товаров сразу, как поиск на сайте поставщика — без выбора категории (без LLM, §6);
- ищет товары локально (зеркало Oasis + Gifts, §6–7) — секунды, а не минуты;
- жёстко исключает только по объективным причинам (склад, явно не тот тип, семейство цвета, §8) и ранжирует по фиксированной формуле (§9);
- перед показом обновляет цену/остаток показанных карточек Oasis живым запросом (§7);
- после поиска, если есть замечания или подходящие уроки, делает один проход ИИ по короткому списку и той же формулой пересортировывает (§10).

## 4. Полный маршрут одной позиции

1. Документ уже распознан: есть название позиции и (если было ТЗ) список характеристик.
2. Маршрут временно хардкожен: `_frozen_route()` — `["Закупка готового изделия", "Нанесение"]`, без LLM (см. заголовок документа). Несёт и `steps`, и совпадающий `processes` — иначе любой путь, пересобирающий маршрут из процессов (выбор товара поставщика), молча терял бы «Нанесение».
3. `_build_search_plan()` — единственный вызов LLM в этом маршруте: название + характеристики → `{"item", "queries", "skip_labels"}`. `skip_labels` — строки ТЗ, которые не являются признаком товара (маркировка/сертификация, требования к пошиву/швам, дизайн макета, бумажные документы). Занимает 0.5–3 секунды при типичном промпте без изображений. Сохраняется в гипотезе как `search_plan`.
3a. `_tag_requirement_selection()` — по `skip_labels` + постоянным `RequirementSkipRule` + регексу `_COMPLIANCE_MARKING_RE` (Честный Знак/ЦРПТ) каждой строке ТЗ проставляется `selected` (если строка не пришла с флагом от клиента — тогда флаг клиента). Строка с `selected=False` для всей сверки — как будто её нет в ТЗ (см. §8, чекбоксы). В гипотезе — `requirement_selection`.
4. `catalog_candidates_for_line()` ищет по `item`/`queries` в локальном зеркале Oasis и Gifts (§6–7), жёстко исключает и ранжирует (§8–9). Без LLM. При активных замечаниях/уроках возвращает широкий список (`shortlist_limit=40`), иначе — 10.
5. `_retrieve_lessons("catalog", …)` подбирает подходящие уроки (§10). Если есть замечания сессии или уроки — `_run_shortlist_pass()`: один вызов ИИ читает ~40 карточек + инструкции текстом и правит оценки/приоритет/флаг «убрать» у карточек. Та же формула (`_shortlist_rank_key`) пересортировывает, помеченные «убрать» уходят в `shortlist_removed`, показываются первые 10.
6. Перед возвратом бэкенд обновляет цену и остаток показанных карточек Oasis одним запросом `ids=` (§7).
7. **Первый по подбору товар с ценой автоматически берётся в расчёт** (`apply_catalog_candidate(..., selection_mode="automatic")`) — поиск считается обученным ранжировать лучший вариант первым, поэтому «показан товар, себестоимость 0» быть не должно. Точный он или частичный — берётся всё равно, у частичного расхождения видны, обоснование маршрута другое («Автоматически взят первый по подбору…»). Администратор кликом по любой карточке переопределяет (`selection_mode="manual"`); ручной выбор держится между пересчётами, пока карточка в подборке, авто — всегда пересобирается на текущий №1. Пока маршрут заморожен, `apply_catalog_candidate` возвращает `_frozen_route()` поверх догадок нормализатора (`product_type=""`, `confidence=1.0`).
8. Обратная связь администратора складывается в `session_instructions` (текст + `scope`), копится по сессии. `build_training_hypothesis(recompute=…)` ограничивает пересчёт одним блоком; область определяет **поле, в которое вписан комментарий** — LLM не угадывает:
   - `recompute="all"` (по умолчанию, «Начать заново», обратная связь по маршруту) — полная пересборка: и `search_plan`, и маршрут заново;
   - `recompute="catalog"` (обратная связь блока «Закупка готового изделия», крестик на плашке правки, чекбоксы ТЗ, выбор товара) — маршрут и `search_plan` берутся из прошлой гипотезы дословно (название не менялось), заново только бэкенд-поиск и проход ИИ. Во фронте «думает» только тело этого блока; узел маршрута в DOM сохраняется.
9. Кнопка «Принять и обучить» (`confirm_production_type`, ветка `session_id`) закрывает сессию: `learn_lessons_from_session()` пишет по одному `Lesson` на каждое замечание блоков подбора/ТЗ, с контекстом (§10). Замечаний может не быть — расчёт всё равно принимается.
10. Каждый пересчёт сохраняется как `ProductionTrainingTurn`.

Основные точки кода: `tenders/services.py::build_training_hypothesis`, `::_build_search_plan`, `::_run_shortlist_pass`, `::_retrieve_lessons`, `::learn_lessons_from_session`, `tenders/catalog.py::catalog_candidates_for_line`, `::_shortlist_rank_key`.

## 5. Поисковый план

`catalog_intent`, который доходит до бэкенда, — просто «что искать», без DSL и без структурных ограничений:

```json
{
  "item": "ветровка",
  "categories": ["ветровка"],
  "synonyms": ["ветровка", "куртка ветровка", "ветровка мужская", "ветровка женская"],
  "required": [{"label": "Цвет", "value": "лаймово-зелёный"}],
  "ranking_override": {}
}
```

`required` — характеристики как они пришли из распознанного ТЗ (label/value), без операторов и уровней важности. `ranking_override` — пусто либо `{"price": "desc"}`: сессионная смена хвоста сортировки («сначала дорогие»), в уроки не пишется (§10). Никаких минус/плюс-слов и правил в `catalog_intent` больше нет — свободный текст обрабатывает проход ИИ по короткому списку.

## 6. Поиск по тексту (без выбора категории)

### Правило

Поиск работает так же, как поиск на сайте поставщика: **один полнотекстовый
запрос** по `search_text` (название + описание + характеристики) **всех товаров
зеркала сразу** — OR по каждой фразе плана (`item` + `queries`) и по каждому
значимому слову в них. Категория не выбирается вообще (`_category_candidates`,
ключевой скоринг категорий — удалён из горячего пути; остался только в
холодном live-обходе Oasis, см. ниже).

Почему убрали выбор категории: ключевой скоринг регулярно попадал в
соседний узел — по запросу «Сумка шопер» он предлагал пляжные / спортивные /
поясные сумки и **вообще не выдвигал** «Для шопинга», где лежат хлопковые
шоперы; а искались только два верхних узла. Промах категории → промах всей
выдачи. У поиска по тексту категории нет — промахиваться нечему.

### Релевантность (`_relevance_tier`, `_score_pool_relevance`)

Каждому найденному товару присваивается ступень 0–2 по тому, **где встретились
слова запроса**:

- **0** — в названии стоит вся фраза `item` или её *различающее* слово
  («…шопер…» для «Сумка шопер»); либо в названии общее слово, а различающее —
  в описании;
- **1** — в названии только *общее* слово товара («Спортивная сумка» — есть
  «сумка», ничего шоперского);
- **2** — слова запроса только в описании, не в названии;
- **3** — не совпало ничего → товар отбрасывается.

«Различающее» против «общего» решается **на каждый поиск** по тому, в скольких
найденных товарах встречается слово: «сумка» почти во всех → общее, «шопер» в
единицах → различающее. **Никаких зашитых списков слов.** Ступень — первый
ключ сортировки (§9): нужный тип товара идёт выше «чистого по ТЗ, но не того».

### Oasis

- Полное зеркало каталога — `CatalogProduct` (`python manage.py sync_oasis_catalog`), как у Gifts. Поиск читает его текст. Пока зеркало не синхронизировано ни разу — холодный live-обход API (`_OASIS_PAGE_CEILING` страниц, лимит 1 запрос/сек); только он всё ещё использует ключевой скоринг категорий, потому что у API Oasis нет вменяемого релевантного поиска. Прод и дев работают на зеркале.
- Цена и остаток в зеркале могут быть устаревшими на часы — перед показом бэкенд обновляет их живым запросом `ids=` (§7). Постоянного расписания пересинхронизации зеркала пока нет.

### Gifts

- Полный импорт `sync_gifts_catalog()` читает `product.xml`, `tree.xml`, `stock.xml`, `filters.xml`; `search_text` собирается из названия и описания.
- Всегда ищется по тексту (`_text_search_pool`), живого API нет — цена/остаток из последнего импорта.

### Известное ограничение производительности

Полнотекст на SQLite (дев) — это скан таблицы: для очень общего слова
(«сумка», «пакет») ~1–2 с на выборку + ~2 с на скоринг релевантности +
~3–4 с на проверку пригодности 600 карточек = 5–8 с на позицию. На боевом
Postgres нужен GIN-индекс по `to_tsvector` — тогда выборка и ранжирование
становятся одним быстрым индексным запросом. **Это следующий шаг для кнопки
«посчитать весь тендер разом».** Специфичные запросы (жилет, поло, рюкзак)
уже 2,5–4 с.

## 7. Живая цена и завершение маршрута

Поиск обязан завершить маршрут, а не останавливаться после неудачной попытки:

1. один полнотекстовый запрос по каждому источнику (§6), объединение, ступень релевантности, срез 600 лучших;
2. проверка пригодности (§8) и ранжирование по фиксированной формуле (§9);
3. одним батч-запросом `ids=` бэкенд обновляет цену и остаток показанных карточек Oasis из зеркала — единственный живой запрос к Oasis в обычном поиске;
4. только после этого — «не найдено» с диагностикой источников и причин отсева.

Товар, у которого в названии нет ни одного слова запроса и совпало только
описание (ступень 2) или не совпало ничего (ступень 3), проверку типа
проходит строго: обычная футболка не пройдёт как поло, а «эко-ручка» — как
«эко сумка».

Нельзя ослаблять явные запреты и тип товара. Положительные требования можно использовать для выбора ближайшей альтернативы, но расхождение обязательно показывается пользователю.

**Важно про Oasis API:** `category` и `search` нельзя передавать вместе — `search` при этом молча игнорируется. `id=`/`article=` в единственном числе тоже игнорируются и возвращают весь каталог (десятки тысяч строк, минуты) — никогда их не использовать. Пакетный `ids=` (через запятую) — единственный проверенный способ быстро получить несколько карточек по ID, ~1 секунда на любое количество.

## 8. Факты, фильтры и частичные совпадения

Свойства читаются из структурированных полей товара, атрибутов, названия и описания. Поэтому слово `женская` в названии считается значением пола даже при пустом отдельном поле.

Каждое требование получает одно из трёх состояний: `match` (известно и совпадает), `mismatch` (известно и не совпадает), `unknown` (карточка не даёт данных).

Жёстко (до ранжирования) товар исключается только по объективным причинам:

- другой товарный тип (по семантике; для товара из явно выбранной категории несовпадение по названию — это `unknown`, а не отсев);
- другое семейство цвета, когда и требуемый, и предложенный цвет однозначно определены (белый против красного), а в названии нет подходящего оттенка;
- недостаточный общий остаток нужного варианта;
- запрещённое значение (`not_in`, `not_contains`), если оно явно подтверждено;
- нулевой остаток.

Всё остальное (400 мл вместо 450, 95% хлопка вместо 100%, детский крой при отсутствии в ТЗ явного требования взрослого) — **оставляет товар как ранжируемую альтернативу** с явно показанным расхождением. Отсутствие данных в карточке никогда не удаляет товар: это `unknown`. Более глубокая сверка с ТЗ (кроме этих объективных причин) сейчас на администраторе — ассистент не пытается судить о ней автоматически (нет отдельного ревизора, см. §10).

## 9. Ранжирование

Никаких числовых баллов и весов. `_shortlist_rank_key` (в `catalog.py`) — фиксированный список критериев сверху вниз, читается как слова в словаре. Среди не отсеянных товаров:

1. ячейка приоритета: `0` (поднят) выше `1` (обычный). Поднимает карточку только проход ИИ (§10); по умолчанию у всех `1`;
2. ступень релевантности `relevance` (§6): `0` (нужное слово в названии) выше `1` (только общее слово) выше `2` (слово только в описании). Это то, на что сортирует поиск сайта в первую очередь — нужный тип товара выше «чистого по ТЗ, но не того»;
3. меньше `mismatch`;
4. меньше `unknown`;
5. сначала карточки с ценой, среди них — дешевле; либо, при сессионном `ranking_override.price="desc"`, дороже; без цены — в конец;
6. название + артикул — только стабильность, не критерий.

«Точные» (0 `mismatch` и 0 `unknown`) отдельной ступенью не выделяются — это полностью следует из п. 3+4. Цена не компенсирует несовпадение. Поставщик на ранжирование не влияет.

**Проход ИИ этот список не трогает никогда** — только его входные данные у карточек. Та же формула пересортировывает.

Результат объясняется напрямую списком требований (`✓ Материал: металл`, `✗ Объём: требуется 450–500 мл, товар 400 мл`, `? Покрытие: данных в каталоге нет`), без отдельного AI-вызова.

## 10. Обратная связь и обучение

Ревизора на LLM нет. После детерминированного поиска остаётся короткий список (~40 карточек). Если у позиции есть замечания администратора или подходящие уроки — **один небольшой вызов ИИ** (`_run_shortlist_pass`, отдельная модель — по умолчанию `anthropic/claude-haiku-4-5`, см. §18) читает все карточки целиком + инструкции текстом. ИИ **не решает «убрать» или «поднять» сам и не переписывает оценки кода**: он превращает каждую инструкцию в один **именованный критерий** и говорит, каким карточкам он подходит. Действие применяет код.

Типы инструкций (ИИ классифицирует каждую фразу):
- **`priority`** — «подними / опусти / сначала / приоритет / нужны X / лучше X» и **любая нечёткая формулировка (по умолчанию сюда)**. ИИ заводит критерий («Пол: мужской») и перечисляет id карточек, у которых он **явно выполняется**. Код ставит этим карточкам приоритет `0` → п. 1 сортировки. «Опусти X» = «подними не-X».
- **`exclude`** — **только явное** «убери / исключи / спрячь / только X / без X». ИИ перечисляет id карточек, которые **явно противоречат** критерию (непонятно = не противоречит = оставляем). Код помечает их `_removed` → уходят в `shortlist_removed` (свёрнутая строка «ИИ убрал: N»). **Расхождение с ТЗ по плотности/цвету/составу само по себе — не `exclude`**, это `mismatch`, код уже посчитал.
- **`soften`** — «220 г это норм», «цвет считай совпавшим». ИИ = какой признак смягчить + id карточек; код убирает у них `mismatch`/`unknown` по этому признаку.
- **`ranking`** — «сначала дорогие / дешёвые» → `ranking_override` (только сессия, в урок не пишется, снимается крестиком → `clear_ranking`).

**Условные инструкции** — «если в ТЗ <условие> — <действие>», «если в ТЗ НЕ указано X — …». Проход **уже видит полный ТЗ текущей позиции** в промпте, поэтому проверка условия — тот же один вызов, без отдельного LLM. Условие не выполняется → `applied:false`, `cards:[]`, в `note` — почему; правка не применяется, но урок всё равно сохраняется (сработает на других позициях). В плашке — серым «условие не выполнилось».

**Широта урока — `applies_to`** (проход определяет по формулировке): `item` (по умолчанию, про этот вид товара) или `any` — общее правило, не привязанное к товару (условие про ТЗ вообще, «Честный Знак не учитывай»). `any` → `learn_lessons_from_session` пишет урок с пустыми `item_word`/`tz_labels` → `_retrieve_lessons` подаёт его в **каждый** проход (score +2).

Никаких списков слов и заплаток: если ИИ ошибся в «да/нет» по критерию — это правится промптом узкой задачи или моделью посильнее (§18), не кодом.

**Уроки** — таблица `Lesson` (json-поля). «Принять и обучить» (`learn_lessons_from_session`) пишет по одной записи на каждое замечание блоков подбора/ТЗ:

- `admin_text` — слова администратора как есть;
- `summary` — чистая формулировка от ИИ (для плашки и дедупа);
- контекст: `scope` (`catalog`/`requirements`/… — при разморозке маршрута добавятся `route`/`production_step`/`cost`), `item_word` (слово-товар), `tz_labels` (метки учитываемых полей ТЗ), `production_type`;
- `outcome` — что вышло (какие карточки убрали, у скольких поправили оценки) — чтобы следующий проход видел «и это сработало».

Учится с первого раза. `_retrieve_lessons` дёшево (одна выборка `filter(scope, is_active)` + скоринг по слову-товару, пересечению меток ТЗ, типу производства; топ ~12) подаёт подходящие записи в тот же проход как «раньше на похожих позициях администратор говорил …». Одно повторение — правило активно, без весов. Конфликтующие уроки (отключил «Честный Знак» у швейных, включил у медизделий) хранят разный контекст — ИИ в проходе видит оба и решает по текущему; разрешать конфликты кодом не нужно.

Плашки у списка товаров минимальны: «Учтён прошлый опыт» (сработавшие уроки, зелёным), «Ваши корректировки» (замечания сессии с × для удаления и пометкой, если ИИ не смог применить), «ИИ убрал: N». Крестик на корректировке пересчитывает без неё (`instructions_override`, `recompute="catalog"`).

Что остаётся детерминированным: тяжёлый поиск (найти ~40 из тысяч), жёсткие отсевы по типу/цвету/остатку, счёт `✓/✗/?` по ТЗ, сама формула сортировки. Проход ИИ — только над готовым коротким списком, только правит поля карточек.

## 11. Расчёт и себестоимость

Пока маршрут хардкожен (см. заголовок), полноценного расчёта себестоимости нет: `costs` в гипотезе пустой, кроме статьи `material` — первый по подбору товар с ценой автоматически становится статьёй расходов через `apply_catalog_candidate()` (§4 п. 7). Ручное добавление источника цены (`add_calculation_source` / `apply_verified_source_quote`) технически не тронуто, но без активной калькуляции маршрута практической ценности до §16 не имеет.

## 12. Диагностика

Каждая попытка поиска должна сохранять:

- режим (`text_search`, либо `selected_categories` для холодного live-обхода Oasis);
- фразы запроса (`query_phrases`) и раскладку по ступеням релевантности (`relevance_tiers`);
- число полученных и рассмотренных товаров;
- число исключений по причинам `out_of_stock`, `product_type`, `colour`, `forbidden`;
- количество точных и частичных совпадений;
- итоговое число кандидатов;
- статус каждого источника (включая ошибку живого обновления цены, если она не удалась — в этом случае остаётся значение из зеркала, поиск не падает).

Сообщение «не найдено» без этих данных считается недостаточной диагностикой.

## 13. Найденные инженерные ошибки (архив)

1. **Выбор категории целиком** — сначала три вызова LLM (retrieval → селектор → верификатор), потом детерминированный ключевой скоринг `_category_candidates`. Оба поколения промахивались мимо нужного узла: скоринг по запросу «Сумка шопер» предлагал спортивные/поясные сумки и не выдвигал «Для шопинга». Убрано целиком — поиск идёт полнотекстом по всем товарам сразу (§6), категории больше не при чём (`_category_candidates` остался только в холодном live-обходе Oasis).
2. **Канцелярские слова перевешивали название товара.** «Ветровка с логотипом» находила «Блокноты с логотипом» и «Ароматические диффузоры с логотипом» — слово «логотип» встречается почти в каждой категории промо-товаров. Исправлено стоп-словами в скоринге (§6) и обрезкой хвоста фразы перед поиском (§3, LLM).
3. **Ревизор проверял только явно перечисленные пункты ТЗ.** Поло-рубашка, полностью подходящая по материалу/цвету/плотности, проходила как точное совпадение для запроса «майка», потому что тип товара нигде не был отдельным пунктом ТЗ. Промежуточное решение (пока действовал ревизор): всегда добавлять «Тип товара» первым пунктом проверки. Сейчас ревизора нет вовсе — эту проверку временно делает администратор.
4. **SQLite без индекса на JSON-принадлежность категории** — фильтр по категории превращался в построчный проход по всей таблице (30–37 тыс. строк) с полной десериализацией каждой карточки (включая многокилобайтные текстовые поля) просто чтобы проверить список категорий. Отняло до 4 секунд на источник при заведомо небольшом результате. Исправлено: сначала лёгкий проход только по ID и списку категорий, полная карточка подгружается только для найденных совпадений.
5. **Oasis-поиск был живым API-обходом категории** (до 6 страниц по 500 позиций, лимит 1 запрос/сек) — 15–45 секунд на одну немаленькую категорию. Замена на локальное зеркало (§6) свела то же самое к секундам; живым запросом теперь обновляется только цена/остаток показанных 10 карточек (§7).
6. **`category`+`search` в Oasis API молча игнорируют `search`**, `id=`/`article=` в единственном числе возвращают весь каталог вместо ошибки — проверено эмпирически перед тем, как полагаться на эти параметры (см. §7).
7. Старый подтверждённый пример мог принести в новый расчёт каталожную цену, хотя текущий поиск не нашёл товар — цена принимается только из текущей найденной карточки (не изменилось).

## 14. Обязательная проверка при изменениях

Перед развёртыванием изменения поиска должны доказать тестами:

1. Полнотекстовый поиск находит товар по слову из названия/описания, даже если ни одна категория его не описывает («Сумка шопер» → хлопковые шоперы).
2. Товар, чьё название совпадает с *различающим* словом запроса, идёт выше товара с чистым паспортом, но не того типа («Рюкзак-мешок» выше «Рюкзак детский» по запросу «рюкзак мешок»).
3. При отсутствии точного свойства возвращается ближайший товар с расхождением, а не пустой список.
4. Gifts сохраняет категории и связи товаров при полном импорте.
5. Слово запроса, встречающееся у меньшинства найденных товаров, считается различающим и даёт ступень релевантности 0; общее слово («сумка») — ступень 1; совпадение только в описании — ступень 2; ничего — товар отброшен.
6. Цена без текущего кандидата не попадает в расчёт.
7. Несовпадение по обычной характеристике оставляет товар альтернативой; жёстко отсеивают только тип, семейство цвета, остаток и явные запреты.
8. Локальные тесты не подключаются к production-базе и не бьют по живому API Oasis (мокать клиента).
9. `recompute="catalog"` не пересобирает `search_plan` и оставляет маршрут прошлой гипотезы дословно; `recompute="all"` пересобирает и то и другое.
10. «Принять и обучить» без замечаний в сессии не падает, а принимает расчёт и закрывает сессию.
11. Замороженный маршрут несёт `processes` из двух шагов; выбор товара поставщика (`apply_catalog_candidate`) не роняет «Нанесение» и не выдаёт догадку по типу/уверенности.
12. Строка ТЗ с `selected=False` не даёт ни ✓, ни ✗, ни «?», не влияет на поисковые термины и на порядок; строка, пришедшая с флагом от клиента, не перетегируется.
13. «Принять и обучить» переносит снятые строки ТЗ в `RequirementSkipRule`; строка такой метки приходит снятой в новом тендере.
14. `_collapse_requirements` схлопывает повторные строки ТЗ (одна на характеристику, самая полная формулировка) — в распознавании и в ассистенте.
15. Свежая позиция без замечаний и без уроков не делает вызов `_run_shortlist_pass` (ноль лишних токенов); при замечании/уроке — ровно один вызов, и та же формула пересортировывает список.
16. Проход ИИ отдаёт `{тип, критерий, cards:[id]}` на инструкцию — не «убрать/поднять» напрямую. `priority` → приоритет `0` перечисленным; `exclude` → `_removed` перечисленным; `soften` → снятие `mismatch` по признаку; `ranking` → `ranking_override`. Код НЕ верифицирует «да/нет» ИИ словарями (заплатки `_gate_removals` больше нет).
17. Нечёткая инструкция («нужны хлопковые») классифицируется как `priority` (мягко), не `exclude`.
18. Замечание сессии → `Lesson` при «Принять и обучить», с `item_word`/`tz_labels`; урок сам всплывает в проходе на похожей позиции без нового ввода. `ranking_override` в урок не пишется.
19. Проход ИИ, вернувший битый JSON или упавший, не роняет расчёт: детерминированный порядок + `shortlist_warning`.
20. `_run_shortlist_pass` зовёт `_ai_gateway_json(model=…)` с моделью из `TIMEWEB_AI_MODEL_SHORTLIST` (дефолт `anthropic/claude-haiku-4-5`), а не общей.

## Окно ассистента (структура сверху вниз)

1. Заголовок позиции.
2. Плашка «Соответствие не подтверждено» — только если ТЗ не привязалось; при нормальном совпадении её нет.
3. `<details>` «Техническое задание» — свёрнут по умолчанию, не зависит от расчёта. У каждой строки чекбокс: снятая = «не участвует в подборе» (строка серым, зачёркнута, для сверки не существует). Начальное состояние — из `requirement_selection` (см. §3a). Сверху счётчик «Подбор по N из M пунктам». После расчёта — кнопка «Учесть и пересчитать» (шлёт `scope="requirements"` → `recompute="catalog"`) и плашки постоянных правил `RequirementSkipRule` с × (`data/requirement-skip/drop/` → вернуть строку в подбор). «Принять и обучить» переносит все снятые строки в `RequirementSkipRule` — их метки приходят снятыми во всех будущих тендерах.
4. Блок «Технологический маршрут»: обоснование текстом, затем вертикальная колонка пронумерованных шагов (`.training-route__steps`, кружок + стрелка-связка), **каждый шаг — сам `<details class="training-route__step">`, раскрывается на месте внутри блока маршрута**. Ниже — свёрнутый `<details>` «Исправить маршрут». Отдельной блок-схемы и дублирующего списка шагов больше нет.
   - Шаг «Закупка готового изделия»: сверху минимальные плашки (сработавшие уроки «Учтён прошлый опыт», свёрнутая «ИИ убрал: N», `shortlist_warning`), затем карточки (у каждой раскрывающийся `<details>` с полным списком ✓/✗/? по ТЗ — сначала ✗ и ?), затем «Ваши корректировки» (`.training-block-changes`) + поле обратной связи (`scope="catalog"`). Первый по подбору с ценой — «В расчёте · авто».
   - Остальные шаги — заглушка (`routeStepHint`).
   - **Все шаги свёрнуты по умолчанию.** `rerender` при `scope in {catalog, requirements}` перерисовывает целиком, восстанавливая открытые `<details id>` и несохранённый текст полей.
5. Блок «Конечная себестоимость» — идёт **сразу после** блока маршрута, когда есть цена: заголовок, статьи расхода, итог за ед./тираж.
6. Нижняя фиксированная панель: два числа себестоимости (за ед. — серое, за тираж — зелёное) + кнопка `↺` (только иконка, «Начать заново») + «Принять и обучить». До первого расчёта — одна кнопка «Рассчитать».

**3 типа блоков маршрута (заметка на будущее, пока существует только тип 1):**
- **закупка готового товара** — цена из каталога поставщика, своей формы источника нет;
- **типография PSODIN** — свой калькулятор;
- **типовые производственные этапы** (цифровая печать, широкоформат, пошив и т.п.) — снаружи одинаковые: список источников + форма добавления источника + поле объяснения + цена из накопленной истории (нужен обучаемый механизм, не обязательно LLM). Отдельной формы «Добавить поставщика» на уровне окна больше нет — она вернётся внутрь блоков этого типа, когда вернётся разбор маршрута (§16).

Точки кода фронта: `templates/tenders/home.html::openRequirements` (каркас окна + нижняя панель), `::trainingDialogueHtml` (маршрут + блоки шагов), `::feedbackWidgetHtml` (переиспользуемое поле обратной связи), `::bindProductionControls` (обработчики, `runRevise` со scoped-плашкой и частичной перерисовкой, `data-finalize-training`).

## 15. Условный запуск каталога

Пока запускается на каждую позицию безусловно (маршрут хардкожен, см. заголовок). Раньше, когда маршрут строила LLM, каталог опрашивался только при шаге «Закупка готового изделия» в маршруте (`route.steps`) — эта развилка (`route_buys_finished_good`) вернётся вместе с §16.

## 16. Возврат маршрута и себестоимости (следующий этап, не начат)

Когда поиск устроит администратора, маршрут строится отдельным, отдельно тестируемым шагом — не общим вызовом вперемешку с поисковым планом, как было раньше. Ориентировочно: небольшой вызов LLM на маршрут (независимый от `_build_search_plan`), с тем же принципом — LLM понимает намерение, бэкенд считает. Условный запуск каталога (§15) и полноценный расчёт себестоимости (§11) возвращаются вместе с этим шагом. Детали не зафиксированы — будут описаны здесь, когда работа начнётся.

## 18. Модели

`_ai_gateway_json(..., model=…)` — модель выбирается по назначению, не одна на всё:

| Вызов | Env | Дефолт | Почему |
|---|---|---|---|
| Чистка названия (`_build_search_plan`) | `TIMEWEB_AI_MODEL` | `openai/gpt-4.1-mini` | тривиально, дёшево |
| Проход по короткому списку (`_run_shortlist_pass`) | `TIMEWEB_AI_MODEL_SHORTLIST` | `anthropic/claude-haiku-4-5` | суждения «да/нет» по критерию — качество прямо влияет на ранжирование, вызов маленький и редкий |
| Распознавание документов | `TIMEWEB_AI_MODEL` | тот же | картинки, дорого — менять отдельно и осознанно |

Шлюз Timeweb отдаёт ~99 моделей (OpenAI, Anthropic, Google, DeepSeek, xAI, Qwen, …), список — `GET /v1/models` с ключом. Чтобы попробовать другую модель на проходе — поставить `TIMEWEB_AI_MODEL_SHORTLIST` в окружении сервера (не в `.env` — его читают и тесты).
