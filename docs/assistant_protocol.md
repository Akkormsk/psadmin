### Семейства и варианты

`CatalogProduct.family_key` — родительское семейство. Для Gifts ключ строится
из фактических связей каталога, для Oasis — из `group_id` или устойчивого
артикула. Единый технический контракт для одежды, накопителей и любых
других категорий — названия категорий в правилах не зашиты. Шаг 3 возвращает
по одному представителю семейства вместе с дочерними вариантами; шаг 5
проверяет ограничения каждого варианта и сохраняет `eligible_variant_ids`,
поэтому размерный ряд одежды может остаться одной карточкой, а подходящая
ёмкость накопителя не теряется внутри общего семейства.

Метка варианта (что показать вместо «размер») тоже не зашита в код: сперва
`_variant_size` (тег «, размер XL» в названии / поле `size`), иначе —
`_group_varying_attribute` находит, какой атрибут реально различается по
значению между SKU одной семьи (для флешек это окажется «Объём памяти», для
бумаги — «Плотность», без единой строчки кода, которая знала бы про них
заранее); различается 0 или больше одного атрибутов — метки нет, код не
гадает.

Для Oasis ключ считается прямо в потоковом проходе синхронизации, на
странице API — второй проход по всей таблице не нужен (до 14.09.2026 был
нужен, снят как источник OOM на проде: полная таблица целиком в память). Для
Gifts семья определяется сопоставлением артикулов между строками, это
требует видеть весь набор сразу — синхронизация Gifts по-прежнему
пересчитывает ключи отдельным проходом в конце.

Команда `python manage.py rebuild_catalog_families` — без сетевых запросов
и без LLM, ручной пересчёт задним числом (после старого импорта или если
формулы семей изменятся); Oasis она тоже поддерживает, хотя обычная
синхронизация в ней больше не нуждается.

### Шаг 1: разбор ТЗ без списка известных характеристик

Один вызов сильной модели на позицию (кэш по хэшу набора отмеченных строк).
Возвращает по каждой строке: `concept`, `operator` (`>=|<=|=|!=|~|in`),
`value`, `unit`, `num_min`/`num_max` — для ЛЮБОЙ числовой характеристики, не
только для памяти/объёма; `axis` — свободное слово-код, если этим отличаются
варианты ОДНОГО товара (список осей не ограничен списком заранее); `options`
— перечислимые значения; `maps_to` — `"color"`/`"material"`, если критерий
про цвет/материал товара целиком (структурная подсказка вместо поиска слова
«цвет» в тексте критерия); `importance` — вес критерия для лимита активных
требований; `keep` — признак ли это готового товара вообще.

Одна строка ТЗ → МАССИВ разборов, не один объект: `{"criteria":{"1":[{...}]}}`.
Строка с несколькими числами через «х»/«x»/«*» на разные оси одного товара
(«Размер, мм: ≥240 x 340» — длина и ширина; «7\*7\*7 см» — длина/ширина/высота)
возвращается НЕСКОЛЬКИМИ записями в массиве этой строки, у каждой свой
`label` (метка оси, например «Длина»/«Ширина») и свои `num_min`/`num_max`.
Два числа, которые описывают разброс ОДНОЙ величины (диапазон, не разные
оси — «200-220 г/м2»), остаются одной записью с `num_min`/`num_max` этой
записи. Ключ, по которому матчатся галочка клиента и `RequirementSkipRule`,
— `source_label` (исходная строка ТЗ до разделения), не `label` разделённой
оси — иначе снятая целиком составная строка не снимет свои оси.

### Шаг 5: детерминированная проверка критериев

До шага 6 код проверяет каждый отмеченный критерий сам, если может:

- `maps_to="color"`/`"material"` — сверка со списком `colors`/`materials`
  карточки (эти два поля всегда присутствуют в структуре товара, это не
  выбор конкретной характеристики, а факт схемы данных);
- `options` без числовых границ — размерный ряд карточки против требуемого
  набора: `axis_mode="fulfill_set"` требует ВЕСЬ набор, `"choose_one"` —
  пересечение;
- ЛЮБОЙ числовой критерий (включая оси capacity/volume — для кода это такое
  же понятие, как любое другое) — код ищет число в характеристиках карточки
  (`attributes`) по пересечению значимых слов понятия критерия со словами
  названия атрибута, без перевода единиц измерения (единица должна
  совпадать текстом, через словарь `UnitAlias`, или быть не указана хотя бы
  с одной стороны). Несколько атрибутов с РАЗНЫМИ числами — неоднозначно,
  код не решает. Если слова не пересеклись, но для этого же понятия агент
  уже когда-то подтверждал конкретное имя атрибута на другой карточке —
  код пробует и его (`AttributeConceptHint`, см. шаг 6).

Ничего не решается, если код не уверен — строка остаётся
`matrix[].source == "not_checked"` и уходит агенту. Код никогда не
подставляет вердикт, которого агент бы не дал; переписать уже решённую
кодом клетку не может ни агент, ни кэш.

Вся эта проверка — настройка шага 5 `numeric_prefill` («Понятные числа
считать кодом»): `"yes"` (по умолчанию) включает описанное выше,
`"no"` отключает прикидку кодом полностью и отдаёт все отмеченные критерии
агенту шага 6 как есть.

### Шаг 6: агент — только по остатку, и самообучение словаря

Агент читает карточку целиком и оценивает только строки, которые шаг 5 не
закрыл (полностью решённая шагом 5 карточка на шаг 6 не попадает вовсе).
Все такие карточки оцениваются за один проход (пачки внутри — параллельно,
`ThreadPoolExecutor`, см. `_grade_grid`); отдельного ограничения по числу
карточек за прогон нет — сколько дошло до шага 6, столько и оценивается.
При активном фидбеке (замечания администратора/уроки) классификация
замечаний — отдельный проход внутри шага 6, бюджет матрицы на неё не
расходуется.

В лаборатории для самой матрицы можно выбрать Jev. Он получает отдельный
вопрос «да/нет» для каждой открытой клетки и возвращает вероятность: высокая
становится «да», низкая — «нет», промежуточная — «нужно уточнить». Jev не
разбирает свободный фидбэк и не открывает новые имена атрибутов: это остаётся
за обычным агентом. Кэш матрицы разделён по исполнителю, поэтому ответы Jev и
обычного агента не смешиваются.

Если для критерия, у которого имя атрибута заранее не угадывается по словам
(«плотность» ТЗ vs «граммаж» на карточке), агент сам сопоставил число с
конкретной характеристикой — он называет её в необязательном поле ответа
(`"a":"Граммаж"`). Код запоминает эту пару понятие↔атрибут в
`AttributeConceptHint` (ключ понятия — набор его значимых слов, без единого
зашитого в код названия), с счётчиком подтверждений. Шаг 5 следующего
прогона — любой позиции, любого поставщика — пробует эту подсказку наравне
с обычным совпадением слов (`_learned_attribute_name`), и в некоторых
случаях закрывает такой критерий сам, без обращения к агенту вовсе. Разные
поставщики могут называть одно и то же понятие по-разному — словарь хранит
все варианты сразу и предпочитает более подтверждённый.

Контракт карточки: `matrix` содержит отдельную строку на каждое требование
с `verdict=yes|no|unknown|not_checked`, `reason` и
`source=code|agent|cache|not_checked`. `matrix_status=complete` — заполнены
все строки; `incomplete` — агент вызван, но ответ неполон; `pending` —
проверка не запускалась. Без выбранных критериев карточки сразу `complete`.
`unknown_count` считает и «проверили — данных нет», и «ещё не проверяли»
одинаково (для читателя оба значат «неизвестно»); `matrix_status` отдельно
и честно отличает эти случаи для ранжирования и кэша. Признак не равен
соответствию: полностью проверенная карточка может иметь расхождения.

Вердикт кэшируется по (карточка, хэш ТЗ) только когда `matrix_status ==
"complete"` — частичный или пустой ответ не кэшируется. Повтор с
достаточным кэшем не тратит токены на матрицу вовсе.

### Шаг 7: сортировка

Фиксированный ключ: удалённые — в конец; ручной приоритет (ставит только
инструкция фидбека «подними X»); полностью проверенные — перед
непроверенными/неполными; меньше расхождений → больше совпадений → меньше
неизвестного; релевантность; цена. Без обрезки — возвращает каждую карточку
шага 6, включая отклонённые. Только шаг 8 исключает отклонённые.

## 4. Обратная связь и уроки

Администратор пишет правила обычным языком в поле того блока, который
правит; «Учесть и пересчитать» пересчитывает только этот блок. ИИ
классифицирует каждую фразу в `priority`/`keep_only`/`exclude`/`soften`/
`ranking` и перечисляет id карточек — код применяет действие, формула
сортировки не меняется. «Принять и обучить» переносит каждое замечание в
`Lesson` с контекстом (слово-товар, метки учитываемых полей ТЗ); урок
всплывает в проходе на похожей позиции без нового ввода.

## 5. Лаборатория каскада

`/tenders/cascade-lab/` — закрытый экран суперпользователя для запуска тех
же восьми функций вне обычного ассистента. Не пишет прогоны в базу — снимки
живут только в открытой вкладке браузера.

После каждого шага доступны его вход, выход, состояние каскада, время,
токены и стоимость. Можно листать снимки, продолжать следующим шагом или
повторять с выбранного места. Пользовательские карточки передаются
JSON-массивом: шаги 3–4 в таком прогоне помечаются `skipped`, шаг 5
принимает этот массив, шаги 6–8 работают обычно.

Настройки каждого шага сохраняются под именем; кнопка «Применить настройки
к подбору товаров» создаёт версию глобальной конфигурации, обычный
ассистент использует активную версию. Все параметры лаборатории — реальные
входы соответствующего шага (модель, кэш, допуск и т.д.), не
имитация: изменение настройки меняет фактическое поведение того же кода,
которым пользуется обычный подбор.

Параметры лаборатории — модель, кэш, допуск, интенсивность фильтра и т.п.,
только то, что шаг реально принимает на вход; никакой настройки не должно
существовать, если она включает зашитый в код список понятий (см. §10 п.8) —
поведение для новых/незнакомых понятий должно быть тем же кодом, что и для
любых уже встречавшихся.

Список моделей в селекторах (шаги 1, 2, 4, 6) не захардкожен — это
`gateway_budget.available_models()`, живой список из `/models` шлюза AI
Gateway (кэш 6 часов); жёстко заданный набор остаётся только запасным
вариантом на случай, если шлюз недоступен.

Лимит времени передаётся текущему вызову модели; перед каждым вызовом
проверяется консервативная оценка стоимости — новый вызов не начинается,
если может превысить общий рублёвый предел (`gateway_budget.preflight`,
`spend_rub`). Между шагами проверяется фактически накопленный расход.

## 6. Расход и баланс

Разработка и тесты — только на моках, отдельная тестовая БД, сеть
заблокирована (`tenders.test_cascade*`). Рабочий кэш, production и баланс
изменениями не трогать. После каждого живого прогона нужно знать реальный
расход Timeweb — токены фиктивного ответа мока расходом не являются. Живой
платный замер — отдельный явный запуск, после успешного `preflight`.

`tenders/gateway_budget.py`: `account_balance()` (баланс Timeweb Cloud,
`manage.py gateway_balance`), `spend_rub(usage, model)` (оценка стоимости
вызова из точных токенов ответа), `RATES_RUB_PER_M` (тарифы моделей, ₽ за 1M
токенов — обновлять из дашборда AI Gateway при появлении новых моделей).

## 7. Расчёт и себестоимость (V1; не полный Calculation V2)

В этом этапе разработки автоматически считается только стоимость выбранных
каталожных товаров. Она показывается как «Рассчитанная часть стоимости».
Остальные этапы можно обсуждать и обучать; отсутствие их цены не означает ноль.
Выбор товара не меняет технологический маршрут. Результаты каталога привязаны
к id этапа. Изменённые/удалённые этапы теряют устаревший подбор и цену;
неизменившийся этап при том же исходном ТЗ сохраняет результаты.

## 8. Построение маршрута и обучение

`tenders/routes.py` строит и проверяет маршрут; `build_training_hypothesis`
вызывает либо его, либо существующий каскад по явному запросу каталога.
Этап содержит `id`, `name`, `kind` (`catalog`, `production`, `completion`),
`details` и при необходимости `catalog_item`. Название этапа не определяет
инструмент. `selected=false` в ТЗ исключает строку только из подбора, но
не из проектирования производства.

Замечания к маршруту и этапу сохраняются в сессии с областью и идентификатором
этапа; модель объясняет изменения и задаёт вопросы при недостатке данных.
«Принять и обучить» атомарно сохраняет маршрут в `ProductionTrainingExample`
и замечания в `Lesson`. Старые заглушки без `route.schema_version=1` не
используются как знания маршрута. Повторное подтверждение того же контекста
создаёт новую версию, помечает старую `superseded_by` и отключает её уроки.
Другие ТЗ и тиражи не вытесняются. В окне можно отключить ошибочный пример
или урок; данные сохраняются и доступны для восстановления в админке.

Для следующего диалога отбираются примеры и уроки по словам вида продукции;
LLM проверяет их применимость к полному ТЗ. Это подсказки, а не автоматическое
копирование маршрута. Список переданного опыта виден в окне ассистента.
Модель маршрута: `TIMEWEB_AI_ROUTE_MODEL` (V1 default `gemini/gemini-3.1-flash-lite`; V2/глобальный ассистент имеют независимые настройки, историческая недоступность OpenAI не определяет текущую доступность),
проверка баланса через `preflight`, лимит стоимости из активной конфигурации,
реальные токены ответа пишутся в результат и журнал. Тесты — локальная БД,
ответы LLM и каталога имитируются, сеть блокируется.

## 10. Найденные инженерные ошибки (архив, не повторять)

1. **Выбор категории целиком** (LLM или ключевой скоринг) регулярно
   промахивался мимо нужного узла («Сумка шопер» → спортивные/поясные сумки,
   без «Для шопинга», где лежат хлопковые шоперы). Убрано целиком — поиск
   идёт по названиям всех товаров сразу, категорий в пайплайне больше нет.
2. **Пофилдовые парсеры структурных требований** («плотность это тоже
   хардкод») — раньше код заранее знал набор проверяемых характеристик и
   единицы измерения. Заменено на шаг 1 (модель структурирует ЛЮБОЙ
   критерий) + детерминированную сверку по факту данных карточки (шаг 5), а
   не по заранее зашитому списку полей.
3. **Схлопывание по «текстовому распознаванию размера» вместо устойчивого
   ключа** — заменено на `family_key`/`group_id`.
4. **Пустая матрица трактовалась как точное совпадение** — карточка, которую
   агент не оценил вовсе, ранжировалась как «подтверждено», хотя не была
   проверена. Исправлено контрактом `matrix_status`.
5. **SQLite `icontains` не фолдит кириллицу** — поиск по названию идёт
   Python-сканом по стемам (`name_index.py`), не через `LIKE`.
6. **`category`+`search` в Oasis API молча игнорируют `search`**, `id=`/
   `article=` в единственном числе возвращают весь каталог вместо ошибки —
   не использовать эти параметры.
7. **Смысловой (векторный) поиск шага 3, положивший CPU прода в 100%
   (15.09.2026)** — настройка лаборатории `step_3.semantic=yes`, однажды
   сохранённая в общем `CascadeConfigVersion.is_active` (кнопка «Применить
   настройки к подбору товаров»), включила этот шаг сразу для ВСЕХ боевых
   прогонов, не только лаборатории — код держал в памяти процесса всю
   матрицу эмбеддингов каталога (`CatalogProduct.embedding`) на 1 CPU/1 ГБ
   проде. Решение — не заглушка переменной окружения, а полное удаление:
   `CatalogProduct.embedding*` (миграция 0029), `_semantic_candidates`/
   `_semantic_catalog_index`/`rebuild_catalog_embeddings` из
   `tenders/catalog.py`, команда `rebuild_catalog_embeddings`, ветка
   `step_3.semantic` из `cascade.py` и лаборатории. Смысловой поиск каталога
   как фича будет прорабатываться отдельно и только на локальной машине,
   без завязки на общий боевой конфиг, прежде чем снова появляться в
   `main`.
8. **Хардкод для capacity/volume пролез обратно, несмотря на п.2** —
   `axis == "capacity"/"volume"` доставало число регэкспом из названия
   (`_capacity_mb`/`_volume_ml`), промпт шага 1 просил переводить именно эти
   две оси в МБ/мл, а `variant_axes` при синке считал capacity/size для
   ДВУХ зашитых понятий и нигде не читался (мёртвый код). Не масштабируется:
   с новым поставщиком/доменом (бумага, текстиль — что угодно) под каждое
   новое понятие пришлось бы писать свой парсер. Убрано под корень: числовая
   сверка любой оси идёт тем же путём, что и любой другой числовой критерий
   (характеристики карточки, шаг 5); метка варианта — через
   `_group_varying_attribute` (какой атрибут реально различается внутри
   семьи, по данным, а не по названию понятия); единственная разрешённая
   форма «специальной обработки» — растущий по подтверждениям агента словарь
   `AttributeConceptHint`, никогда не код с именами понятий.

## 11. Входящие, документы и Calculation V2


### Серверное дерево рабочих товаров — CODE_ONLY

`tenders.working_items.tender_working_items(tender)` — внутреннее SELECT-only представление существующих моделей, без UI/API/capability и без вызовов расчётчиков. Возвращает `{tender_id, items, calculation_results, unattached_calculations}`. Рабочая позиция — активный TenderCommercialItem со связями на TenderSourceItem; непокрытые исходные позиции возвращаются как source/not_prepared. Требования исходников читаются через effective_item_requirements; сохранённые рабочие требования и их происхождение остаются отдельными.

Дерево: item → components (рекурсивно) → routes → steps → calculations. Общие маршруты лежат в shared_routes у позиции. Архивные компоненты сохраняются в historical_components. Каждый TenderComputeLine/TenderComputeWorkUnit представлен один раз в calculation_results; в узлах только ссылки. Совпадение числовой суммы не считается доказательством одинакового расхода; экономическая сумма не пересчитывается. Связи work unit с этапами берутся только из operation_step/operation_steps, без распределения компонентного расчёта между этапами. Результаты без текущего владельца сохраняются в unattached_calculations.

В calculations пять групп ссылок: current, historical, stale, unverified, pending. Новейшая запись задания перекрывает старую даже при пустом результате, история не теряется. Для component-маршрутов используется source_route_snapshots; его группировка по source_item не позволяет объявлять маршрут соседнего компонента историческим. Ready требует завершённости всех активных компонентов и этапов, включая общие, и отсутствия неразрешённых текущих результатов; неизвестная актуальность не считается готовностью. Исполнители показываются только по сохранённому provider_binding_id с confirmed knowledge_version.

НМЦК/цена/сумма извещения доступны только у позиции через notification_origin(same_item=True) и parse_notification: компоненты их не наследуют и цены не делятся. Компоненты показывают собственные сохранённые результаты. Существующий effective_quantity умножает количество коммерческой позиции на quantity_per_parent без обхода родителей; поэтому для вложенных компонентов quantity=None, доступны исходный множитель и stored_effective_quantity, выдаётся issue. Алгоритм расчёта не менялся. Для embedded provider_quote, generic work unit и синхронизации рабочей редакции требований нет универсальной проверки актуальности: unknown/unverified, без вымышленных подтверждений. Отдельная ProviderCalculationQuote не присоединяется по одному binding.

PR #62, feature/tender-working-tree от test-server 5a9ad7f. 19 тестов: простой товар, исходные товары, вложенный набор, НМЦК набора, запрет наследования цены компонентом, обязательные/общие этапы, единый общий расход, устаревшие/исторические/ожидающие результаты, архивные компоненты, общий исходник нескольких компонентов, явный исполнитель, непривязанные результаты. Каждый вызов проверяется SELECT-only SQL-guard. Модели, миграции, TenderEstimate/TenderLine и расчётные алгоритмы не менялись. Слияние и deploy не выполнялись.

### Единый путь и источники

`Tender` (`tender_selection.models`) — якорь ЕИС/ГосПлана, документов, отбора, стадий и расчёта по `(law, purchase_number)`. Не возвращать FoundTender как параллельный реестр. `TenderEstimate`, `OrderEstimate` и самостоятельный калькулятор различаются; обычному заказу не нужен фиктивный тендер.

Цепь V2: `TenderSourceItem` → `TenderCommercialItem` → `CalculationComponent` → `ComponentRoutePlan`/`ComponentOperationStep` → `Counterparty`/`ProviderCalculatorBinding` → `ProviderCalculationQuote` → `TenderComputeLine`. Выполнение хранится в `TenderComputeJob`/`TenderComputeWorkUnit`. Наличие классов не доказывает полный автоматический расчёт; V1 сохраняется до принятия V2.

### Чтение, доказательства и продолжение

- Учитываются все доступные источники. Имя файла не доказывает ненужность документа; непрочитанное/незагруженное не означает отсутствие условий. `DocumentPreview` и версии оригиналов сохраняются, реальные документы не входят в Git.
- Устойчивые адреса связывают параграфы, строки/ячейки таблиц и изображения с версией документа. Равный текст дедуплицируется с сохранением occurrences; различный табличный контекст не склеивается. Оригинальные ячейки, spans и первая строка не теряются.
- Один compact inventory заменяет произведение «фрагменты × страницы товаров». Reader возвращает source-bound факты/локальные ссылки; backend прикрепляет точный существующий текст. Изображения требуют реального модельного чтения, а не выдуманной транскрипции.
- Неустановленная связь с товаром нормализуется в `unassigned`, без угадывания ID и потери успешного чтения. Неизвестный fragment ID/неподтверждённая цитата отвергаются. Восстановление оплаченных unlinked text records требует совпадения целого оригинала/версии и проверки цитат; visual output этим способом не чинится.
- Состав → ПП1875 → ТЗ получают выбранные item facts и релевантные global/unassigned facts. Разрешён budget-sized manifest page/точный оригинал/изображение. Отсутствие в выбранном контексте не доказывает отсутствия факта. Exact quote доказывает наличие источника, не полноту семантического извлечения.
- Размер запроса зависит от лимитов каталога моделей, сериализованных данных, ожидаемого output/reasoning/vision и бюджета, не фиксированных 20 товаров. UTF-8 bound — оценка, не измеренный token count. Непомещающийся атомарный факт/табличная строка приводит к честной остановке, не отбрасыванию текста.
- Готовые чтения/per-item результаты сохраняются в обычных diagnostics; fingerprints связывают версии исходников, inventory, policy и явные original lookups. Изменение зависимости инвалидирует соответствующие результаты, а изменение границ пачек само по себе — нет. Подтверждённые записи повторно не отправляются.
- Валидные closed records сохраняются при malformed/truncated ответе. Не дописывать JSON, не подделывать завершение. Продолжать только при росте покрытия и доступном бюджете. No-progress/неопределённый расход останавливают цикл; потерянный ответ не считать бесплатным.
- Downstream source navigation после прерывания может повторить незавершённый lookup; не обещать для него гарантию кэширования законченных фактов. Маршруты сохраняются/переиспользуются по нормальным fingerprints, но старый маршрут не доказывает новый анализ и не является кэшем исполненного расчёта контрагентов.

### Состав, наборы, ПП1875 и принятие

Исходное извещение — базовая линия. Документальные enrich/split/component сохраняются как предложения с provenance; новые данные не обнуляют исходные требования/количество/цену/ручное решение. Неподтверждённый документ не становится активным составом молча. Canonical baseline facts учитываются через source-backed keep/merge/omit; одно новое свидетельство не обязано иметь несколько источников ради искусственного merge.

Наборы сохраняют связь с исходной позицией и количественную/финансовую сохранность. Неизвестная цена компонента не превращается в долю общей цены без расчёта. Принятие состава и `push_to_estimate` используют общие активные источники/требования. Старые расчёты не пересоздаются; отсутствие requirements в обновлении собственной строки не означает очистку, stale/чужой ID проверяет backend. Исходные факты и документальные добавления различаются, полная цитата/источник доступны в общем workspace.

ПП1875 определяется по позициям и источникам извещения/документов: запрет, ограничение, преимущество и неизвестность различаются. Конфликт сохраняет доказательства/unknown, а не выдуманный положительный ответ. Риск использует те же source-backed факты; нехватка документов не даёт зелёного.

Readiness требует всех фактических фаз, полного покрытия, source-backed профиля и текущих непустых маршрутов (`tender_selection/intake_readiness.py`, `tenders/analysis_presentation.py`). Fallback, старые маршруты или отметка профиля недостаточны. Просмотр карточки/сохранённого маршрута не инициирует новый paid analysis.

### Фон, лимиты и следующий этап

Optional compose profile `intake` использует `run_calculation_v2_job --watch`; обычный web deploy не активирует consumer. Требуются V2 flag и согласованный положительный `CALCULATION_V2_AUTO_DAILY_BUDGET_RUB` (default 0). Резерв под settings-row lock учитывает active/uncertain reservations и реальные затраты; flow/claim/daily caps не обнуляются новым запуском. Consumer выбирает только intake_refresh jobs, сохраняет прогресс при heartbeat/stale recovery; unrelated jobs не захватывает.

Цель — фоновые входящие → полноценный разбор → маршруты → автоматический расчёт позиций. Сейчас проверяется полный механизм разбора одного большого тендера. Массовый прогрев, consumer и PROD не включать до приёмки и отдельного бюджета. Расчёт поставщиков/всех операций и экономика всего тендера требуют следующего доказательства.

#### Согласованный цикл входящих — DECIDED_BACKLOG, 2026-11-14

Владелец подтвердил единую компактную историю всех реально полученных системой тендеров; отдельно существующие расчёты, пользовательские правки и подтверждённые уроки сейчас не перерабатывать. Закупки, не возвращённые первичным поиском источника, не объявлять полученными или сохранёнными. Сохранять идентичность существующей сущности Tender, не создавать параллельный реестр тендеров или второй архив; конкретная миграция объединения истории ещё не реализована.

1. **Источники и бюджет.** ЕИС — источник публикуемых закупок в соответствующем контуре, не универсальный реестр всех покупок РФ. ГосПлан агрегирует сведения и предоставляет первичный поиск. Целевой общий потолок этого сборщика — 9 HTTP attempts в минуту, включая повторы, не в секунду и не обязательное число запросов. Соблюдать фактический provider remaining/reset/Retry-After. Прямое получение подробностей из ЕИС — отдельный механизм, не secondary-запросы ГосПлана. ЕАТ подключается после основного контура, пункт 9 порядка внедрения; не включать его в ранние этапы.
2. **Два раздела настроек.** «Что получать из ГосПлана»: закон (44/223 — отдельные endpoints), цена от/до, регионы, этап, способ закупки, ОКПД2, слова в названии, границы публикации/обновления/окончания подачи, доступные идентификаторы и организации, обеспечение/специальные признаки 44-ФЗ, валюта. Частые настройки видимы сразу, остальные раскрываются как дополнительные. Пустое необязательное поле не должно скрыто включать бизнес-ограничение.
3. **Начальные значения.** Существующие закон, цену и прочие выбранные условия не менять молча; верхняя цена 2 млн и окна 7/14 дней использовались в экспериментах, не являются автоматически утверждёнными настройками. Этап по умолчанию — подача заявок; доступны также работа комиссии, завершение и отмена. Пользовательский фильтр даты публикации по умолчанию не ограничивает возраст ещё открытой закупки. API имеет `published_forpast` с default `1m`: требуется проверить явный способ получения всех подходящих открытых закупок, а не предполагать, что отсутствие published_after отменяет собственный default источника. Техническое разбиение выдачи по времени не должно превращаться в скрытый отсекающий период.
4. **Плюс-слова и ИЛИ.** Между разными условиями — И, между альтернативными плюс-словами — ИЛИ. 2026-11-14 на реальном `/fz44/purchases` проверено: `полиграф` вернул 2 записи, `бланк` — 10, `полиграф|бланк` — те же 12 по идентификаторам. Не запускать цикл по одному слову, если слова можно безопасно объединить. На полном пользовательском списке отдельно проверить допустимую длину запроса и совпадение результатов; разбивать на группы только при доказанном ограничении, с удалением дублей по источнику/закону/номеру. Пользовательские слова экранировать как текст; не трактовать знак `+` составного правила как произвольную регулярку. Поиск object_info относится к названию/предмету закупки, а не полным вложениям: полнота означает соответствие заданным словам, а не нахождение любого интересного товара, спрятанного в документации.
5. **Подготовка слов.** Использовать текущий список как исходный. Аудит может предложить расширение по существующему профилю или по явному заданию владельца, например фокус на сувенирах/бизнес-подарках/корпоративном мерче без добавления офсетной, бланковой или наградной тематики. Это содержание конкретного запроса владельца, не хардкод профиля. Показать предлагаемый список и изменения, сохранить только после подтверждения. Возможный вызов через ассистента должен использовать тот же общий backend executor, права и подтверждение, что экран аудита; опубликованной возможности пока нет. Анализ причин отсева использует существующие механизмы, без отдельной новой системы уроков.
6. **Вторичный автоматический отбор.** Единый механизм минус-слов/составных исключений, точная проверка составных плюс-условий при более широком запросе источника и контроль актуальности срока для активных входящих. `ремонт+дорог` означает наличие обеих частей в названии, не обязательно рядом; это составное словесное правило, не новый третий фильтр. Ручное скрытие — пользовательское действие, не условие автоматического фильтра. Не добавлять иных правил отсева без понятного назначения и настройки. В текущем TEST selector при включённом profile_triage_enabled сигнал profile_disposition может переопределять слова при показе списка; при внедрении разового отбора это поведение нужно явно согласовать и не оставлять скрытым повторным фильтром. Настройку сейчас не менять.
7. **Отсев и хранение.** Полученную страницу обрабатывать без скачивания дополнительных сведений для отсеянных. Сохранить компактные текстовые факты, уже предоставленные ГосПланом: источник/закон/номер, название, ОКПД2 и доступные цена/валюта, заказчик, регион, способ/этап, даты и ссылка. Сохранить совпавшие плюс-слова, точные минус/составные условия, версию правил, дату и автоматическую причину исключения. Отсеянная запись видна в едином архиве как исключённая из «Входящих»; ни ЕИС-обогащение, ни загрузка вложений, ни AI-анализ такого отсева автоматически не запускаются. Прошедшая запись остаётся во «Входящих». Повторы обновляют внешние сведения, а не создают копию или заново отменяют решение пользователя.
8. **Однократное решение и восстановление.** Отбор выполняется один раз при первоначальном поступлении. Дальше обновлять внешние сведения и отслеживать дедлайн, не прогонять постоянно показанные карточки через изменившиеся слова. Изменение фильтров влияет на новые поступления; пересмотреть уже полученные — отдельная явная команда. Компактный архив показывает имеющиеся сведения без фонового получения полной карточки; полная подкачка — по восстановлению, с сохранением номера/идентичности и прежнего этапа. Ручное восстановление не должно немедленно отменяться тем же словесным правилом. После истечения срока — архив с отдельной причиной; состояние срока не приравнивается к «не наш профиль».
9. **Полнота и измерение.** Проверка выполняется кодом в приложении/фоновом задании или разрешённом diagnostic workflow, не серией ручных запросов агента и без AI. Фиксировать версию фильтров, границы проверяемого периода, actual attempts/200/429/прочие ошибки, число успешных страниц, записей/уникальных номеров, прошедших/отсеянных и завершённых/незавершённых участков. При 429 дождаться разрешённого времени и повторить ту же страницу. Конец участка — успешный ответ короче запрошенной страницы; 100 записей требуют продолжения. Ограничение skip<=1000 требует корректного разбиения, а не прекращения обхода; избегать повторного скачивания первых 1100 записей каждого переполненного участка. Продвигать подтверждённую границу только после полного и сохранённого результата, включая архив отсева; при сбое сохранять пригодный для продолжения прогресс. Следующий сбор получает новые/изменённые данные, не повторяет без причины весь начальный объём.
10. **Приёмка.** На шаге 3 выполнить короткий программный проход с реальным объединённым списком слов и согласованными условиями; ориентир длительности проверки — 10–15 минут, не суточное наблюдение. Период публикации в выборке и длительность запуска — разные параметры. Истечение таймера не означает полного обхода: показать завершение всех участков либо конкретный остаток/ошибку. Если проверяется дневная публикация, различать «все новые за день» и «из них ещё открытые». Длительный 7-дневный эксперимент остановлен владельцем, его частичный результат не выдавать за точный общий объём. После успешного прохода показать фактические количества, конец всех участков, время, расход и размер текстовых данных. Частоту опроса выбирать по измеренным новым **и изменившимся** сведениям, включая часы нагрузки, а не теоретическим 900 карточкам/мин. Это проверка покрытия фильтров в выдаче ГосПлана, не независимое доказательство полного охвата ЕИС. Отдельно проверить получение открытой закупки старше прежнего окна, составные/минус-слова, дубли, повтор после 429, неизменность ручных решений и отсутствие запросов ЕИС/AI для отсева.

#### Согласованный архив и компактная история — DECIDED_BACKLOG, 2026-11-14

Решение владельца: один архив с одинаковыми карточками и одной кнопкой восстановления; разделы определяются этапом выбытия (Входящие, оценка, расчёт, торги/результат, в дальнейшем исполнение), причина исключения хранится отдельно. Истечение срока — причина, а не отдельный дублирующий архив. Восстановление возвращает на прежний этап и сохраняет внутреннюю работу пользователя.

- Первичный поиск использует доступные параметры ГосПлана; вторичный отбор выполняется один раз при поступлении. Решение и сработавшие слова сохраняются. Обновление внешних сведений не должно заново исключать уже отобранные или восстановленные вручную карточки. Фоновая архивация по истечению срока остаётся. Изменение правил действует на новые поступления; повторный отбор старых — только по отдельной команде с понятными последствиями.
- Для отсеянного на входе тендера достаточно компактной текстовой записи. Открытие архивной записи показывает сохранённые сведения; подкачка полной карточки запускается при восстановлении. ЕИС восстанавливается по номеру извещения, не по названию; другие источники требуют своего адаптера. Недоступность внешнего сервиса явно показывается, не объявляется успешным восстановлением.
- Приложение сохраняет текстовые данные. Вложения загружаются из источника по явному клику/запросу чтения, используются временно и не сохраняются как постоянные бинарные копии или бинарные данные внутри HTML/base64; временные файлы удаляются после обработки, включая ошибки. Исходные ссылки и полученный текст можно сохранять. Это целевое поведение: существующий DocumentPreview ещё требует сверки/изменения, хранение только текста не объявлено реализованным.
- Одна каноническая таблица компактной истории: одна запись на `(источник, закон, номер закупки)`. ## 12. Общий ассистент, знания и backlog

### M3 и операции пользователя

Актуальный TEST `assistant_agent.py` использует Chat Completions Function Calling, app-owned capabilities и `assistant_read.py`; старые JSON next_step/assistant.navigate-графы не восстанавливать по историческим инструкциям. Код plan/ask/finish/cancel, verified references и compact memory не является новой live-приёмкой чата в рамках уборки.

- READ строится из Django metadata и проверяется ORM validator; SQL от LLM запрещён. `verbose_name`, help_text, choices, права/связи и общий selector экрана определяют смысл, не phrase-specific hardcode.
- ACTION объявляется приложением и использует тот же callable, что UI. Входы/права/ссылки проверяются до preview и снова при исполнении. Подтверждение — штатная кнопка, не текстовое «да». Повтор/stale/отмена не создают повторную запись.
- References берутся из реального READ/сохранённых verified sources. «Из них» сохраняет исходный набор даже при пустом результате; нельзя заменить его global search. Нет оснований — уточнение в бизнес-терминах без просьбы назвать internal ID.
- Незавершённое подтверждение и аргументы сохраняются; законченные tool payload не повторяются бесконечно. Диалог, debug, lessons и confirmed knowledge — разные scopes. Наблюдаемая трасса не является скрытым рассуждением модели.
- Возможность сайта не становится автоматическим разрешением AI: права/preview/audit обязательны. Webhooks/фоновые/технические endpoints не публикуются как пользовательские макрофункции. Telegram — будущий адаптер общего backend без второй логики.

`ProcessDefinition` — способность/этап, `Counterparty` — организация, `StageCounterpartyLink` — связь. Положительное обучение отбора — подтверждённое движение в работу, отрицательное — нерелевантность до расчёта, не проигрыш торгов. Слова/риск-пороги автоматически без подтверждения не применять; исторические 7/14-дневные пороги не считать текущим договором.

DECIDED_BACKLOG/DEFERRED: назначение требований подходящим операциям (нанесение/заготовка/комплектация не смешиваются), принятая автоматическая калькуляция всех операций и ROI всего тендера, полное исполнение/Telegram. Не выдавать неизвестную себестоимость за 0; UI и момент назначения stage requirements не считать решёнными по старым заметкам.

FSPrint — существующий эксперимент `tenders/integrations/fsprint.py`, не принятая V2-интеграция: POST `/ext/calc/calculate` → `record` (`jir_nom`) → POST `/ext/calc/show_variant` (`record,var,curr,usetemp`). 23 формы различаются; примеры пакетов/блокнотов не доказывают остальные; ошибки не заменяются выдуманной ценой. Базовая срочность по умолчанию; срок из ТЗ требует отдельной проверки. Сохранять fsprint JSON/HTML fixtures. Project111 не принят по одному адаптеру; Oasis/Gifts используют действующие источники.

Запрещённые старые эвристики: независимые высота/ширина не группируются общей единицей, составные оси связываются `source_label`; UnitAlias нормализует обозначения одной единицы, не переводит denier в г/м². Нижнеграничный fix не доказывает full range-to-range matching. Jev-эксперимент с cache collision не доказывает экономию; сравнивать равные настройки, учитывать расход параллельной волны, не обещать более жёсткий лимит, чем код гарантирует.

## Mandatory Contributor Policy

The following policy is carried forward from the previous AGENTS.md without removing requirements. It remains mandatory; the concise contributor guide does not replace these controls.

### PSADMIN: правила разработки

#### Инварианты

- GitHub — источник истины для кода; production PostgreSQL на Timeweb — для операционных знаний. Не копировать production-данные в Git.
- Работать только в изолированной ветке и TEST-среде. Без прямого разрешения владельца не менять PROD, production-флаги, секреты и не запускать destructive migrations, deploy или массовый AI/backfill; для backfill нужен определённый бюджет.
- Сохранять V1 до принятия соответствующего V2. Использовать существующие модели и доменные сервисы, не создавать параллельные реестры, calculation engines или learning stores.
- LLM интерпретирует язык; backend выполняет расчёты, валидацию, фильтрацию каталога и ранжирование. Не хардкодить поставщиков, товары или бизнес-правила в core. Подтверждённая обратная связь и вытесненные знания должны быть версионируемы и восстанавливаемы.
- Локальные тесты не подключаются к production и не меняют его. Git содержит код, миграции и curated fixtures, но не credentials, production dumps, клиентские документы или выгрузки поставщиков. Интеграции поставщиков не скачивают изображения без явного запроса.
- Не объявлять deploy состоявшимся без проверки фактического commit SHA и health. UI проверять в реальном браузере, когда доступна аутентификация; новые экраны соблюдают navigation contract: логический parent fallback, Home и отсутствие navigation traps.
- В отчёте этапа указать изменения, проверку, commit, состояние TEST-deploy, ограничения и конкретную ручную проверку.
- Новая пользовательская Django-модель или поле, доступное через assistant READ, имеет осмысленный `verbose_name`, а при необходимости `help_text`; не создавать assistant-only каталог имён и отвечать пользователю человеческими подписями, а не техническими именами. Для составного отбора публиковать existing generic READ hook модели и общий read-only service экрана, не копировать правило в агента и не делать phrase-specific tool; проверять их одинаковое поведение.

#### Минимальный, проверяемый код

- Сначала проверить и подготовить структуру данных: существующие сущности, ключи, связи, хранение и совместимость. Если нужна новая схема — подготовить её и безопасный перенос существующих данных до поиска, фильтров и интерфейса; не создавать параллельный реестр вместо согласованной модели. Это не требование менять схему без необходимости.
- Сначала назвать допущения и неоднозначности; при существенной неясности остановиться и спросить. Делать минимальное решение без спекулятивных функций, абстракций и рефакторинга по соседству.
- Менять только необходимое, сохранять стиль; удалять лишь созданные своими изменениями orphaned imports/variables/functions. Каждый изменённый фрагмент должен относиться к задаче.
- Задать проверяемый критерий успеха. Для бага по возможности сначала воспроизвести его тестом; для новой логики сначала написать проверку. Если test-first невозможен, назвать причину.
- Код должен объяснять себя; комментарии нужны только для нетривиальных ограничений, схем или причин, не для механики языка.

#### Документация и расход контекста

`AGENTS.md` задаёт нормы разработки; `docs/assistant_protocol.md` — единственный источник подтверждённого поведения, решений и состояния системы. Не создавать новые человеческие `*.md`/`*.txt` как roadmap, handoff, prompt, архитектурные заметки, TODO, отчёты или параллельные протоколы. Новые сведения — в существующий протокол; старые документы не удалять без проверки переноса и разрешения владельца. Машинные тестовые артефакты допустимы и не являются вторым источником решений.

Эти правила едины для Claude, Codex, ChatGPT, локальных и облачных агентов; не вводить и не требовать `CLAUDE.md`.

- Перед задачей сначала посмотреть структуру протокола и прочитать только разделы, относящиеся к изменяемому поведению, данным, рискам и проверкам. Полностью читать обе версии (`main` и `test-server`) нужно только для релизной сверки или когда задача действительно требует полного контракта.
- Начинать с точечного `rg`, импортов и определений, затем читать нужные диапазоны файлов. Не загружать целиком большие документы, JSON, логи или результаты тестов без причины.
- Для бага: воспроизведение → целевые тесты после исправления → необходимая регрессия. Полный набор — перед завершением значимого изменения или при затрагивании общей логики. Не повторять неизменившиеся тесты без причины.
- Не использовать субагентов и широкое исследование репозитория по умолчанию. Экономия контекста не отменяет проверок безопасности, прав, сохранности данных, миграций и релиза.

#### Протокол, окружения и релизы

- `main/docs/assistant_protocol.md` описывает только подтверждённый PROD; `test-server/docs/assistant_protocol.md` — подтверждённый TEST, отличия и план. Ветка, PR, mock-тест или локальный тест не являются релизом.
- Для каждой возможности использовать честный статус: `PROD_VERIFIED`, `TEST_VERIFIED`, `CODE_ONLY`, `DECIDED_BACKLOG`, `DEFERRED` или `REJECTED`. Подтверждение требует server/release SHA: для TEST — `.twin-version` или равный достоверный источник, для PROD — deployed Git SHA/версия. В протоколе фиксировать дату, ветку, source SHA, deployed SHA либо «не подтверждён», проверки и известные пробелы; не включать персональные данные, секреты или реальные выгрузки.
- Не смешивать согласованный план, код/автотесты и проверенную работу сервера. Изменение архитектуры/тестового кода, принятое решение, находка, эксперимент или перенос в TEST обновляет протокол в том же наборе коммитов; после TEST-deploy сверить SHA и health. Перед PROD-deploy подготовить обновление `main` и после него сверить SHA и основные сценарии. Расхождения фиксировать, а не угадывать.
- Любое слияние, удаление документов, migration production DB, test/prod deploy или массовый AI backfill требует ранее данного явного разрешения владельца; молчание не является согласием. `test-server` деплоится при любом push, включая документацию: перед merge проверить workflow и текущий релиз, после разрешённого push дождаться deploy+health. PROD запрещён без прямой команды; в 09:00–19:00 Москвы нужно отдельное однозначное подтверждение запуска в рабочее окно, вне окна тоже нужна явная команда. Использовать реальные backup/migration/health scripts.
- Перед передачей или релизной сверкой: проверить ветку, status, HEAD, base/PR, дату и deployed SHA; при необходимости прочитать обе версии протокола и сравнить схему/алгоритмы с кодом, миграциями и тестами; запустить нужные тесты; сообщить изменения, SHA, результаты, серверную приёмку, долг и требуемый approval. Не удалять неперенесённые требования и не считать один адаптер принятым V2.

#### Ассистент и пользовательские операции

- Единица capabilities — законченная пользовательская макрофункция: назначение, обязательные входы, результат, побочные эффекты, подтверждение и общий executor. Любая новая/изменённая пользовательская возможность в том же PR изменяет декларацию capabilities и тесты; если её нельзя безопасно публиковать, указать причину в протоколе.
- Автоматизированный реестр не даёт AI разрешение на выполнение. Для записи обязательны права, preview/confirmation, идемпотентность и аудит. Логику HTTP/JavaScript сначала выносить в реальный общий backend executor для сайта и агента, не в assistant-only helper.
- Сохранять аргументы из нескольких сообщений, спрашивать только недостающие, заменять исправленное значение и выполнять запись лишь после полного контракта и server-side confirmation. Web и Telegram — адаптеры общего диалогового состояния и семантических действий; Telegram не имеет отдельной бизнес-логики.
- M3.1 — одна макрооперация с её штатными backend-шагами и одним итоговым подтверждением. Несколько независимых READ/ACTION — M3.2, не маскировать их одним гигантским AI-only executor. Для нового приложения или изменения ACTION тестировать разрешение каждого опубликованного `source` в callable и единый executor для UI/ассистента; Python-функция сама по себе не даёт `TEST_VERIFIED` или `PROD_VERIFIED`.

#### Актуальность checkout и веток

- Перед работой получить актуальные refs GitHub, проверить HEAD/status и сравнить с нужной базой. Старый checkout не является источником текущих инструкций. Не сбрасывать чужие изменения. `main` — PROD, `test-server` — TEST.
- Для задачи использовать одну рабочую ветку от актуальной базы. После завершения удалять разрешённые владельцем старые ветки только после проверки достижимости всех коммитов из сохраняемой ветки либо exact head слитого PR и отсутствия последующих уникальных изменений. Закрытый PR сам по себе недостаточен.
- Последний отчёт/решение сначала переносить в сохраняемую историю. Не удалять ветки с уникальной работой. Архив удалённых инструкций хранится в Git, не в новом handoff.
- Протокол начинается актуальным снимком, источниками подтверждения, ограничениями и следующим шагом. Обновлять тематические разделы вместо добавления копий всей истории и отменённых промежуточных инструкций. Проверенный release и HEAD документации различать.

#### Доставка и чтение серверов без личного SSH

- Каждый push в `test-server`, включая документацию, запускает `.github/workflows/deploy-test-vds.yml`. GitHub Actions через существующие `PSADMIN_TEST_SSH_*` сохраняет проверенный backup TEST, доставляет архив, вызывает `deploy/vds/twin.sh up`, проверяет offline tests, host/container `.twin-version`, флаги и public health. Не задавать pilot inputs при документационном деплое.
- Каждый push в `main`, включая документацию, запускает `.github/workflows/deploy-prod-vds.yml` и существующий `deploy.sh`: backup, миграции, health и проверка `.release-sha`. Это production release. Без прямой команды на PROD подготовить отдельную ветку/PR; не обходить ограничение. Правило дополнительного подтверждения в 09:00–19:00 МСК сохраняется.
- Личный SSH агенту не требуется: соединение выполняет Actions. Не заменять эту доставку прямыми действиями Timeweb или новым workflow. Чтение workflow/runs/jobs/logs доступно через GitHub API.
- TEST input `inspect_tender_number` запускает `scripts/inspect_tender_analysis.py`, пропускает deploy/ИИ и использует PostgreSQL `READ ONLY`. Сначала читать workflow выбранной ветки: расширенные диагностические режимы других веток могут иметь побочные эффекты.
- Timeweb Cloud GET `/api/v1/servers` и `/api/v1/servers/{id}` дают состояние инфраструктуры, не Django/PostgreSQL. Использовать настроенный `TIMEWEB_API_TOKEN` только для `api.timeweb.cloud`. Не выводить полные ответы: они могут содержать пароли/cloud-init; не сохранять их в Git.
- PROD проверяет версию через `X-PSADMIN-Revision`/`.release-sha`; TEST — host/container `.twin-version`. Успешный inspect не равен deploy, а неудачный pilot после запуска healthy-контейнера не доказывает откат кода.
