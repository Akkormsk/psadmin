# Протокол работы тендерного ассистента

Этот документ — обязательная точка входа перед изменением логики ассистента,
поиска товаров или расчёта себестоимости. Он описывает не интерфейс, а границы
ответственности и фактический технический маршрут данных.

> **Как читать протокол (ревизия 2026-10-13):** разделы 1–10 — технический контракт и накопленная история **V1** (маршруты, восемь шагов каталожного каскада и обучение), а не доказательство полного Calculation V2. Текущий снимок ветки и степень проверки содержатся в §11. Исторические решения/метрики и ещё не закрытые вопросы собраны в §12. При расхождении фактов верить реально запущенному коду и явно указывать расхождение.

**Текущая стадия: маршрут разморожен; обучение через диалог.** Маршрут
строится отдельным вызовом LLM по полному ТЗ, подтверждённым примерам и
урокам. Каталог запускается только кнопкой «Подобрать товар» внутри этапа;
раскрытие этапа и построение маршрута не запускают каскад. Полная
калькуляция остальных этапов ещё не подключена.

Маршрут собирается из активных `ProcessDefinition`. Если подходящего
процесса ещё нет, ассистент возвращает лишь предложение нового процесса;
оно создаётся в справочнике только при подтверждении маршрута. Свободный
фидбэк переводится в ограниченный план действий бэкенда, а не в произвольные
изменения данных. Ответы на вопросы ассистента относятся только к текущей
позиции и не становятся уроками. Они хранятся отдельно от исходного документа
как `requirements.clarifications`, но для маршрута и каталожного каскада входят
в единый рабочий чек-лист. Явные характеристики из названия позиции модель
возвращает как `requirement_proposals`; backend оставляет только значения,
буквально присутствующие в названии, а пользователь подтверждает их перед
переносом в `clarifications`.

## 1. Назначение системы

Ассистент получает позицию тендера (НМЦК, наименование и ТЗ), предлагает
маршрут производства и уточняет его в диалоге с администратором. На этапе
подбора готового товара по отдельной кнопке ищет варианты в Oasis и Gifts. Распознавание документов (НМЦК и
ТЗ) не изменилось — использует LLM для чтения документа и отдаёт
структурированный список позиций и требований.

Главный принцип: **ни одна характеристика товара не зашита в код заранее.**
Код не знает наперёд, что «цвет» или «объём» — это особые слова; какая
характеристика важна и чем измеряется, решает модель на шаге 1 для каждого
ТЗ заново. Код лишь применяет то, что модель уже структурировала.

## 2. Источники истины

| Данные | Источник истины |
|---|---|
| Текущие цены и остатки Oasis | зеркало `CatalogProduct` (`sync_oasis_catalog`), при показе — живой API по `ids=` |
| Товары, цены, остатки и категории Gifts | импорт XML (`sync_gifts_catalog`) |
| Семейства | `CatalogProduct.family_key` — для Oasis считает сама синхронизация построчно, для Gifts и вручную — `rebuild_catalog_families()` |
| Разбор ТЗ и кэш вердиктов | `CascadeCache` (`kind="criteria"/"searchplan"/"namefilter"/"verdict"`) |
| Самообучающийся словарь атрибутов | `AttributeConceptHint` — какое название атрибута отвечает на какое понятие критерия, растёт из подтверждений агента шага 6 |
| Уроки поиска и маршрута (обратная связь) | `Lesson` |
| Подтверждённые маршруты и их версии | `ProductionTrainingExample` |
| Строки ТЗ вне подбора | `RequirementSkipRule` |
| Формулы, фильтрация и ранжирование | код бэкенда в Git (`tenders/cascade.py`) |
| Неподтверждённая гипотеза и диалог | `ProductionTrainingSession`/`ProductionTrainingTurn` |

Git не хранит production-базу, выгрузки поставщиков, документы заказчиков и
секреты.

## 3. Каскад подбора — восемь шагов

Точка входа — `Cascade.run()` в `tenders/cascade.py`. Ровно восемь методов
`step_N_*`, порядок закреплён в `tenders.test_cascade_contract`. Каждый шаг —
самостоятельная единица со своим входом/выходом; изменение одного шага не
переносит правило в соседний. Диагностика и границы правок каждого шага — в
комментариях самого кода, здесь только контракт.

| Шаг | Вход | Выход | Кто решает |
|---|---|---|---|
| 1 `step_1_parse_tz` | Позиция, строки ТЗ | `self.tz: list[Criterion]` — критерии с оператором, числовыми границами, осью, `maps_to` | сильный агент, кэш по хэшу ТЗ |
| 2 `step_2_search_plan` | Исходное название | Чистое `item` + поисковые фразы | агент (модель настраивается отдельно) |
| 3 `step_3_search_by_name` | Фразы | Пул представителей семейств с релевантностью и дочерними вариантами | код (обратный индекс по названиям) |
| 4 `step_4_name_filter` | Пул + искомый тип | Пул после фильтра названий | Jev или выбранная чат-модель, кэш по (item, состав пула) |
| 5 `step_5_hard_gates_and_collapse` | Пул, критерии, количество | Карточки групп; `matrix` каждой карточки — с уже закрытыми кодом клетками | код |
| 6 `step_6_agent_matrix` | Карточки (с частично заполненной `matrix`), кэш, инструкции | Те же карточки, `matrix`/`matrix_status` дополнены | обычный агент или Jev — только по клеткам, которые шаг 5 не закрыл |
| 7 `step_7_collapse_and_sort` | Все карточки шага 6 и ручные приоритеты | Те же карточки в ранжированном порядке; ни одна не теряется | код |
| 8 `step_8_price_and_top` | Ранжированный список | Допущенные карточки, живая цена Oasis, топ-10 | код |

### Семейства и варианты

`CatalogProduct.family_key` — родительское семейство. Для Gifts ключ строится
из фактических связей каталога, для Oasis — из `group_id` или устойчивого
артикула. Единый технический контракт для одежды, накопителей и любых
других категорий — названия категорий в правилах не зашиты. Шаг 3 возвращает
по одному представителю семейства вместе с дочерними вариантами; шаг 5
проверяет ограничения каждого варианта и сохраняет `eligible_variant_ids`,
поэтому размерный ряд одежды может остаться одной карточкой, а подходящая
ёмкость накопителя не теряется внутри общего семейства.

Метка варианта (что показать вместо «размер») тоже не зашита в код: сперва
`_variant_size` (тег «, размер XL» в названии / поле `size`), иначе —
`_group_varying_attribute` находит, какой атрибут реально различается по
значению между SKU одной семьи (для флешек это окажется «Объём памяти», для
бумаги — «Плотность», без единой строчки кода, которая знала бы про них
заранее); различается 0 или больше одного атрибутов — метки нет, код не
гадает.

Для Oasis ключ считается прямо в потоковом проходе синхронизации, на
странице API — второй проход по всей таблице не нужен (до 14.09.2026 был
нужен, снят как источник OOM на проде: полная таблица целиком в память). Для
Gifts семья определяется сопоставлением артикулов между строками, это
требует видеть весь набор сразу — синхронизация Gifts по-прежнему
пересчитывает ключи отдельным проходом в конце.

Команда `python manage.py rebuild_catalog_families` — без сетевых запросов
и без LLM, ручной пересчёт задним числом (после старого импорта или если
формулы семей изменятся); Oasis она тоже поддерживает, хотя обычная
синхронизация в ней больше не нуждается.

### Шаг 1: разбор ТЗ без списка известных характеристик

Один вызов сильной модели на позицию (кэш по хэшу набора отмеченных строк).
Возвращает по каждой строке: `concept`, `operator` (`>=|<=|=|!=|~|in`),
`value`, `unit`, `num_min`/`num_max` — для ЛЮБОЙ числовой характеристики, не
только для памяти/объёма; `axis` — свободное слово-код, если этим отличаются
варианты ОДНОГО товара (список осей не ограничен списком заранее); `options`
— перечислимые значения; `maps_to` — `"color"`/`"material"`, если критерий
про цвет/материал товара целиком (структурная подсказка вместо поиска слова
«цвет» в тексте критерия); `importance` — вес критерия для лимита активных
требований; `keep` — признак ли это готового товара вообще.

Одна строка ТЗ → МАССИВ разборов, не один объект: `{"criteria":{"1":[{...}]}}`.
Строка с несколькими числами через «х»/«x»/«*» на разные оси одного товара
(«Размер, мм: ≥240 x 340» — длина и ширина; «7\*7\*7 см» — длина/ширина/высота)
возвращается НЕСКОЛЬКИМИ записями в массиве этой строки, у каждой свой
`label` (метка оси, например «Длина»/«Ширина») и свои `num_min`/`num_max`.
Два числа, которые описывают разброс ОДНОЙ величины (диапазон, не разные
оси — «200-220 г/м2»), остаются одной записью с `num_min`/`num_max` этой
записи. Ключ, по которому матчатся галочка клиента и `RequirementSkipRule`,
— `source_label` (исходная строка ТЗ до разделения), не `label` разделённой
оси — иначе снятая целиком составная строка не снимет свои оси.

### Шаг 3: поиск по словам

Лексика: `name_index.py`, совпадение корня слова из поисковых фраз шага 2
с названием карточки. Никакого смыслового/векторного слоя сейчас нет — см.
§10 п.7 про аварию 15.09.2026 и её удаление.

### Шаг 5: детерминированная проверка критериев

До шага 6 код проверяет каждый отмеченный критерий сам, если может:

- `maps_to="color"`/`"material"` — сверка со списком `colors`/`materials`
  карточки (эти два поля всегда присутствуют в структуре товара, это не
  выбор конкретной характеристики, а факт схемы данных);
- `options` без числовых границ — размерный ряд карточки против требуемого
  набора: `axis_mode="fulfill_set"` требует ВЕСЬ набор, `"choose_one"` —
  пересечение;
- ЛЮБОЙ числовой критерий (включая оси capacity/volume — для кода это такое
  же понятие, как любое другое) — код ищет число в характеристиках карточки
  (`attributes`) по пересечению значимых слов понятия критерия со словами
  названия атрибута, без перевода единиц измерения (единица должна
  совпадать текстом, через словарь `UnitAlias`, или быть не указана хотя бы
  с одной стороны). Несколько атрибутов с РАЗНЫМИ числами — неоднозначно,
  код не решает. Если слова не пересеклись, но для этого же понятия агент
  уже когда-то подтверждал конкретное имя атрибута на другой карточке —
  код пробует и его (`AttributeConceptHint`, см. шаг 6).

Ничего не решается, если код не уверен — строка остаётся
`matrix[].source == "not_checked"` и уходит агенту. Код никогда не
подставляет вердикт, которого агент бы не дал; переписать уже решённую
кодом клетку не может ни агент, ни кэш.

Вся эта проверка — настройка шага 5 `numeric_prefill` («Понятные числа
считать кодом»): `"yes"` (по умолчанию) включает описанное выше,
`"no"` отключает прикидку кодом полностью и отдаёт все отмеченные критерии
агенту шага 6 как есть.

### Шаг 6: агент — только по остатку, и самообучение словаря

Агент читает карточку целиком и оценивает только строки, которые шаг 5 не
закрыл (полностью решённая шагом 5 карточка на шаг 6 не попадает вовсе).
Все такие карточки оцениваются за один проход (пачки внутри — параллельно,
`ThreadPoolExecutor`, см. `_grade_grid`); отдельного ограничения по числу
карточек за прогон нет — сколько дошло до шага 6, столько и оценивается.
При активном фидбеке (замечания администратора/уроки) классификация
замечаний — отдельный проход внутри шага 6, бюджет матрицы на неё не
расходуется.

В лаборатории для самой матрицы можно выбрать Jev. Он получает отдельный
вопрос «да/нет» для каждой открытой клетки и возвращает вероятность: высокая
становится «да», низкая — «нет», промежуточная — «нужно уточнить». Jev не
разбирает свободный фидбэк и не открывает новые имена атрибутов: это остаётся
за обычным агентом. Кэш матрицы разделён по исполнителю, поэтому ответы Jev и
обычного агента не смешиваются.

Если для критерия, у которого имя атрибута заранее не угадывается по словам
(«плотность» ТЗ vs «граммаж» на карточке), агент сам сопоставил число с
конкретной характеристикой — он называет её в необязательном поле ответа
(`"a":"Граммаж"`). Код запоминает эту пару понятие↔атрибут в
`AttributeConceptHint` (ключ понятия — набор его значимых слов, без единого
зашитого в код названия), с счётчиком подтверждений. Шаг 5 следующего
прогона — любой позиции, любого поставщика — пробует эту подсказку наравне
с обычным совпадением слов (`_learned_attribute_name`), и в некоторых
случаях закрывает такой критерий сам, без обращения к агенту вовсе. Разные
поставщики могут называть одно и то же понятие по-разному — словарь хранит
все варианты сразу и предпочитает более подтверждённый.

Контракт карточки: `matrix` содержит отдельную строку на каждое требование
с `verdict=yes|no|unknown|not_checked`, `reason` и
`source=code|agent|cache|not_checked`. `matrix_status=complete` — заполнены
все строки; `incomplete` — агент вызван, но ответ неполон; `pending` —
проверка не запускалась. Без выбранных критериев карточки сразу `complete`.
`unknown_count` считает и «проверили — данных нет», и «ещё не проверяли»
одинаково (для читателя оба значат «неизвестно»); `matrix_status` отдельно
и честно отличает эти случаи для ранжирования и кэша. Признак не равен
соответствию: полностью проверенная карточка может иметь расхождения.

Вердикт кэшируется по (карточка, хэш ТЗ) только когда `matrix_status ==
"complete"` — частичный или пустой ответ не кэшируется. Повтор с
достаточным кэшем не тратит токены на матрицу вовсе.

### Шаг 7: сортировка

Фиксированный ключ: удалённые — в конец; ручной приоритет (ставит только
инструкция фидбека «подними X»); полностью проверенные — перед
непроверенными/неполными; меньше расхождений → больше совпадений → меньше
неизвестного; релевантность; цена. Без обрезки — возвращает каждую карточку
шага 6, включая отклонённые. Только шаг 8 исключает отклонённые.

## 4. Обратная связь и уроки

Администратор пишет правила обычным языком в поле того блока, который
правит; «Учесть и пересчитать» пересчитывает только этот блок. ИИ
классифицирует каждую фразу в `priority`/`keep_only`/`exclude`/`soften`/
`ranking` и перечисляет id карточек — код применяет действие, формула
сортировки не меняется. «Принять и обучить» переносит каждое замечание в
`Lesson` с контекстом (слово-товар, метки учитываемых полей ТЗ); урок
всплывает в проходе на похожей позиции без нового ввода.

## 5. Лаборатория каскада

`/tenders/cascade-lab/` — закрытый экран суперпользователя для запуска тех
же восьми функций вне обычного ассистента. Не пишет прогоны в базу — снимки
живут только в открытой вкладке браузера.

После каждого шага доступны его вход, выход, состояние каскада, время,
токены и стоимость. Можно листать снимки, продолжать следующим шагом или
повторять с выбранного места. Пользовательские карточки передаются
JSON-массивом: шаги 3–4 в таком прогоне помечаются `skipped`, шаг 5
принимает этот массив, шаги 6–8 работают обычно.

Настройки каждого шага сохраняются под именем; кнопка «Применить настройки
к подбору товаров» создаёт версию глобальной конфигурации, обычный
ассистент использует активную версию. Все параметры лаборатории — реальные
входы соответствующего шага (модель, кэш, допуск и т.д.), не
имитация: изменение настройки меняет фактическое поведение того же кода,
которым пользуется обычный подбор.

Параметры лаборатории — модель, кэш, допуск, интенсивность фильтра и т.п.,
только то, что шаг реально принимает на вход; никакой настройки не должно
существовать, если она включает зашитый в код список понятий (см. §10 п.8) —
поведение для новых/незнакомых понятий должно быть тем же кодом, что и для
любых уже встречавшихся.

Список моделей в селекторах (шаги 1, 2, 4, 6) не захардкожен — это
`gateway_budget.available_models()`, живой список из `/models` шлюза AI
Gateway (кэш 6 часов); жёстко заданный набор остаётся только запасным
вариантом на случай, если шлюз недоступен.

Лимит времени передаётся текущему вызову модели; перед каждым вызовом
проверяется консервативная оценка стоимости — новый вызов не начинается,
если может превысить общий рублёвый предел (`gateway_budget.preflight`,
`spend_rub`). Между шагами проверяется фактически накопленный расход.

## 6. Расход и баланс

Разработка и тесты — только на моках, отдельная тестовая БД, сеть
заблокирована (`tenders.test_cascade*`). Рабочий кэш, production и баланс
изменениями не трогать. После каждого живого прогона нужно знать реальный
расход Timeweb — токены фиктивного ответа мока расходом не являются. Живой
платный замер — отдельный явный запуск, после успешного `preflight`.

`tenders/gateway_budget.py`: `account_balance()` (баланс Timeweb Cloud,
`manage.py gateway_balance`), `spend_rub(usage, model)` (оценка стоимости
вызова из точных токенов ответа), `RATES_RUB_PER_M` (тарифы моделей, ₽ за 1M
токенов — обновлять из дашборда AI Gateway при появлении новых моделей).

## 7. Расчёт и себестоимость (V1; не полный Calculation V2)

В этом этапе разработки автоматически считается только стоимость выбранных
каталожных товаров. Она показывается как «Рассчитанная часть стоимости».
Остальные этапы можно обсуждать и обучать; отсутствие их цены не означает ноль.
Выбор товара не меняет технологический маршрут. Результаты каталога привязаны
к id этапа. Изменённые/удалённые этапы теряют устаревший подбор и цену;
неизменившийся этап при том же исходном ТЗ сохраняет результаты.

## 8. Построение маршрута и обучение

`tenders/routes.py` строит и проверяет маршрут; `build_training_hypothesis`
вызывает либо его, либо существующий каскад по явному запросу каталога.
Этап содержит `id`, `name`, `kind` (`catalog`, `production`, `completion`),
`details` и при необходимости `catalog_item`. Название этапа не определяет
инструмент. `selected=false` в ТЗ исключает строку только из подбора, но
не из проектирования производства.

Замечания к маршруту и этапу сохраняются в сессии с областью и идентификатором
этапа; модель объясняет изменения и задаёт вопросы при недостатке данных.
«Принять и обучить» атомарно сохраняет маршрут в `ProductionTrainingExample`
и замечания в `Lesson`. Старые заглушки без `route.schema_version=1` не
используются как знания маршрута. Повторное подтверждение того же контекста
создаёт новую версию, помечает старую `superseded_by` и отключает её уроки.
Другие ТЗ и тиражи не вытесняются. В окне можно отключить ошибочный пример
или урок; данные сохраняются и доступны для восстановления в админке.

Для следующего диалога отбираются примеры и уроки по словам вида продукции;
LLM проверяет их применимость к полному ТЗ. Это подсказки, а не автоматическое
копирование маршрута. Список переданного опыта виден в окне ассистента.
Модель маршрута: `TIMEWEB_AI_ROUTE_MODEL` (по умолчанию `gemini/gemini-3.1-flash-lite`; OpenAI-модели у Timeweb AI Gateway перестали отвечать 2026-09-30, дефолт везде в проекте переведён на Gemini),
проверка баланса через `preflight`, лимит стоимости из активной конфигурации,
реальные токены ответа пишутся в результат и журнал. Тесты — локальная БД,
ответы LLM и каталога имитируются, сеть блокируется.

## 10. Найденные инженерные ошибки (архив, не повторять)

1. **Выбор категории целиком** (LLM или ключевой скоринг) регулярно
   промахивался мимо нужного узла («Сумка шопер» → спортивные/поясные сумки,
   без «Для шопинга», где лежат хлопковые шоперы). Убрано целиком — поиск
   идёт по названиям всех товаров сразу, категорий в пайплайне больше нет.
2. **Пофилдовые парсеры структурных требований** («плотность это тоже
   хардкод») — раньше код заранее знал набор проверяемых характеристик и
   единицы измерения. Заменено на шаг 1 (модель структурирует ЛЮБОЙ
   критерий) + детерминированную сверку по факту данных карточки (шаг 5), а
   не по заранее зашитому списку полей.
3. **Схлопывание по «текстовому распознаванию размера» вместо устойчивого
   ключа** — заменено на `family_key`/`group_id`.
4. **Пустая матрица трактовалась как точное совпадение** — карточка, которую
   агент не оценил вовсе, ранжировалась как «подтверждено», хотя не была
   проверена. Исправлено контрактом `matrix_status`.
5. **SQLite `icontains` не фолдит кириллицу** — поиск по названию идёт
   Python-сканом по стемам (`name_index.py`), не через `LIKE`.
6. **`category`+`search` в Oasis API молча игнорируют `search`**, `id=`/
   `article=` в единственном числе возвращают весь каталог вместо ошибки —
   не использовать эти параметры.
7. **Смысловой (векторный) поиск шага 3, положивший CPU прода в 100%
   (15.09.2026)** — настройка лаборатории `step_3.semantic=yes`, однажды
   сохранённая в общем `CascadeConfigVersion.is_active` (кнопка «Применить
   настройки к подбору товаров»), включила этот шаг сразу для ВСЕХ боевых
   прогонов, не только лаборатории — код держал в памяти процесса всю
   матрицу эмбеддингов каталога (`CatalogProduct.embedding`) на 1 CPU/1 ГБ
   проде. Решение — не заглушка переменной окружения, а полное удаление:
   `CatalogProduct.embedding*` (миграция 0029), `_semantic_candidates`/
   `_semantic_catalog_index`/`rebuild_catalog_embeddings` из
   `tenders/catalog.py`, команда `rebuild_catalog_embeddings`, ветка
   `step_3.semantic` из `cascade.py` и лаборатории. Смысловой поиск каталога
   как фича будет прорабатываться отдельно и только на локальной машине,
   без завязки на общий боевой конфиг, прежде чем снова появляться в
   `main`.
8. **Хардкод для capacity/volume пролез обратно, несмотря на п.2** —
   `axis == "capacity"/"volume"` доставало число регэкспом из названия
   (`_capacity_mb`/`_volume_ml`), промпт шага 1 просил переводить именно эти
   две оси в МБ/мл, а `variant_axes` при синке считал capacity/size для
   ДВУХ зашитых понятий и нигде не читался (мёртвый код). Не масштабируется:
   с новым поставщиком/доменом (бумага, текстиль — что угодно) под каждое
   новое понятие пришлось бы писать свой парсер. Убрано под корень: числовая
   сверка любой оси идёт тем же путём, что и любой другой числовой критерий
   (характеристики карточки, шаг 5); метка варианта — через
   `_group_varying_attribute` (какой атрибут реально различается внутри
   семьи, по данным, а не по названию понятия); единственная разрешённая
   форма «специальной обработки» — растущий по подтверждениям агента словарь
   `AttributeConceptHint`, никогда не код с именами понятий.

### Список принятых решений и долгов (отдельно от статуса реализации)

1. **`DECIDED_BACKLOG`**: входящие — semantic `fit/not_fit/needs_review` с доказательствами; архив/ZIP — только безопасный общий документный pipeline с предварительным preview, ручным подтверждением и защитой от zip-bomb/дублирования `Tender`.

4. **`DECIDED_BACKLOG`**: подтверждение производственного знания и его версии, привязка требований ТЗ к подходящим производственным шагам, ошибочные уроки/маршруты — обратимы. Без узкотоварного хардкода и дублирующихся pricing engines.
5. **`DEFERRED`**: FSPrint — есть экспериментальные двухшаговые HTTP-запросы/парсер и тесты (`tenders/integrations/fsprint.py`, `tenders/test_fsprint.py`), но нет общей принятой V2-интеграции. Project111 также не считать принятой интеграцией без отдельной проверки.

7. **`REJECTED`**: новый параллельный registry READ/ACTION, специализированные AI-only write-сервисы, слепая миграция существующего V1, автоматическая публикация сомнительного результата, незаметные массовые AI-вызовы.

## 12. Проверенные решения из прежних технических записок (ревизия 2026-10-13)

Раздел переносит **не устаревшие задания целиком**, а сохраняемые решения, ограничения, тесты и невыполненные вопросы. Метрики из старых прогонов — исторические, не показатели работающего сейчас сервера. Удаление исходных документов допустимо только после отдельного подтверждения владельца.

### Модель данных и миграции: Tender — источник правды

- Актуальная целевая идентичность: `tender_selection.Tender` по `(law, purchase_number)` (см. `tender_selection/services.py::tender_anchor_for`). Стадия, документы, проверка риска, ставка, результат и расчёт относятся к одному тендеру. `FoundTender` из раннего эксперимента — **не новая точка входа и не отдельная параллельная карточка**; миграционная/историческая совместимость должна сохраняться, пока код и миграции действительно её поддерживают.
- `TenderEstimate.tender` относится к тендеру; `OrderEstimate` — самостоятельному заказу **без фиктивной связи с Tender**; `calculator.Estimate` живёт в отдельном калькуляторе. Финансовая запись закрытого заказа `finance.OrderRecord` — ещё один самостоятельный контур, не «Исполнение» тендера.
- Инварианты из `docs/tender-entity-migration.md`: старые записи не удалять при миграции; сверять число записей и ссылки; старые URL/история должны вести на правильный расчёт; проверить каскад/канбан, менеджерские права и изоляцию `OrderEstimate`. Извлечение документа может предложить новую позицию, но **не должно незаметно подменять** строки извещения. Старый эксперимент `docs/tender_lifecycle_experiment.md`, где `FoundTender.lifecycle_stage` считался главным объектом, исторический и отменён последующей моделью Tender.

### Каскад: детерминированная проверка, единицы и эксперимент Jev

- Шаг 5 (`tenders/cascade.py`) сопоставляет оси одного составного требования, разделённого моделью, по общему `Criterion.source_label`. **Не** группировать две исходно независимые строки ТЗ («Высота» и «Ширина») только потому, что у них одинаковая единица: эвристика отклонена как недоказанная (`docs/backlog/cascade-step5-matching.md`).
- `UnitAlias` нормализует **написания одной единицы**, например `D/den/ден/денье/denier`. Денъе (линейная плотность нити) **не переводится детерминированно** в г/м² (поверхностную плотность ткани); «класс» материала также не преобразуется универсальной формулой. Не зашивать подобные переводы. Диапазон `200-220 г/м²` внутри атрибута карточки ранее ошибочно интерпретировал `220` как единицу; минимальный фикс берёт нижнюю границу и корректно распознаёт единицу, **но полного range-to-range сравнения не реализует**. Регрессии — `tenders/test_cascade.py` (проверять фактическое имя тестов в соответствующем коде).
- Данные `docs/cascade_runs/*.json` **сохранить** как датированные результаты измерений. Файл `2026-09-28-baseline-vs-jev-ladder.json` содержит известную **кэш-коллизию**: Jev частично использовал чужой verdict cache; доказательством экономии служит только исправленный `2026-09-28-jev-ladder-clean.json`, и то **не как сравнение с боевым конфигом**. На трёх позициях в чистом эксперименте расчётные снижение стоимости вызовов ~44–72% относительно специально выбранного baseline; нельзя объявлять такой процент экономией на проде.
- Эксперимент выявил ещё одно нарушение лимита: вызовы Jev первоначально обходили `max_cost_rub`; после общей `_check_budget` лимит остаётся **мягким в пределах параллельной волны**. Проверка расхода до следующей волны не даёт абсолютной гарантии, если одновременно уже выполняются несколько вызовов. Следующий честный эксперимент — сравнивать одинаковые `step_settings` из реально активной `CascadeConfigVersion`, с заранее согласованным рублёвым потолком; не запускать большой платный замер автоматически.

### FSPrint: что известно, а чего нет

- `tenders/integrations/fsprint.py` и `tenders/test_fsprint.py` описывают отдельный HTTP-адаптер, **не принятую интеграцию Calculation V2**. Фактический протокол: `POST /ext/calc/calculate` с `application/x-www-form-urlencoded` → из HTML читается номер `record` (`jir_nom`) → `POST /ext/calc/show_variant` с `record,var,curr,usetemp` → HTML-таблица сроков/общей цены/цены за единицу и пары `label/value` по статьям; при неразборчивом ответе возвращать ошибку/исходник, **никогда не выдумывать стоимость**.
- Продуктовые формы **разные**: 23 категории, в том числе одно- и многоблочные (`main1/main2/main3`); разрешённые поля/отделки различаются, некоторые пункты — формы заявки, а не самостоятельный калькулятор. Поддерживающие фикстуры/справочники — `tenders/integrations/fsprint_*json` и `tenders/integrations/fsprint_sample*html`, их не удалять при уборке документации.
- Из старого исследования: живые проверочные расчёты выполнялись на бумажных пакетах и блокнотах; структура выходной таблицы на них совместима, но **из этого не следует** общая поддержка всех 23 товаров. У блокнотов и пакетов разные сроки и проценты срочности — нельзя задавать их как константы. По решению владельца брать **базовую срочность** по умолчанию; привязку срока выполнения из ТЗ — после отдельных тестов.
- Неизвестны/нуждаются в проверке: допустимые значения полей каждой категории, зависимости и динамические ID, варианты отделок, стабильность других продуктов, точные значения параметров `var/curr/usetemp`. Следующее действие — подключать **конкретный** продукт к `ProcessDefinition`/контрагенту по живому запросу и источнику, а не снимать все формы и не включать авторасчёт без валидации.

### Документы тендера, ручной ZIP-импорт и защищённое обучение

- Переносить требования из документов не как молчаливый overwrite: исходное извещение — базовая линия, новые компоненты/обоснования из документов — отдельные предложения с provenance и подтверждением владельца. При недостоверном документе не продолжать вычисление цены по фиктивным значениям. Правила ранжирования файлов по имени не подменяют семантический разбор **всех** доступных материалов.
- `DECIDED_BACKLOG` ручной импорт ZIP: только общая защищённая обработка архива, без второго параллельного парсера. Отклонять zip-bomb (лимиты размера/числа/степени сжатия), traversal, зашифрованные/вложенные архивы, запрещённые типы; при неоднозначности предложить выбор НМЦК и ТЗ, название редактируемо, тяжёлый разбор не блокирует UI без индикации. Сначала результат **preview**, потом создание/поиск `Tender` по `law + purchase_number`; без номера — временный черновик, не тендер в канбане. Не сохранять исходники без отдельного согласования. Тесты на анонимизированных мини-архивах и безопасности обязательны.
- `DECIDED_BACKLOG` обучение входящего потока: позитивная обратная связь — подтверждённое движение тендера в работу/расчёт/торги, негативная — **только скрытие как нерелевантного до расчёта**; проигрыш или закрытие на поздней стадии не обучают минус-словам. Предложенные моделью слова/словосочетания сохраняют источник, примеры, ручное принятие или отказ и откат. Автоприменение слов/параметров источника ЕИС без подтверждения запрещено.
- `DECIDED_BACKLOG` прозрачный риск: зелёный только при достаточности документов и отсутствии факторов, серый при нехватке данных; жёлтый/красный по фактическим срокам/ПП №1875/образцам/поставке по заявкам/обеспечению. **Исторические пороги для обсуждения**, а не обязательно текущий серверный контракт: 8–14 дней как внимание, ≤7 дней как красный. Изменяемые пороги ROI/риск-политики должны быть версионируемы.

### Производственные шаги, поставщики и знания

- `DECIDED_BACKLOG` параметры ТЗ должны назначаться **нужному этапу маршрута**, чтобы требования нанесения не применялись к товару-заготовке и наоборот. Вопрос о UI (список внутри каждого этапа или одна разметка сверху) и моменте назначения (после разбора ТЗ или после построения маршрута) **не решён**, нельзя угадывать или объявлять реализованным (`docs/backlog/route-stage-parameters.md`).
- `ProcessDefinition` — способность/этап, `Counterparty` — организация, `StageCounterpartyLink` — связь многие-ко-многим с настройками и ценой источника; нельзя создавать новый этап под каждое изделие/поставщика и нельзя создавать второй registry. Knowledge ingestion → `ProviderKnowledgeStaging` → нормализованная `CounterpartyKnowledgeVersion` → **только после подтверждения** активный `ProviderCalculatorBinding`. Подтверждённые версии, старые расчёты и уроки сохранять восстанавливаемыми.
- Старая проверенная фикстура швейного прайса: 18 нормализованных вариантов, контрольный пример 100 женских классических футболок по **414,80 ₽** за единицу и 41 480 ₽ суммарно. Это **исторический тест**, не действующая оферта контрагента и не шаблон цен.
- `M3`: читать данные только общим metadata READ, писать только через app-owned `assistant_capabilities.py` и тот же backend executor, что у кнопки сайта; действия с побочными эффектами через preview/confirmation, повтор/отмена/stale не меняют данные. Отсутствующий исполнитель — технический долг, не разрешение написать AI-only business logic.

### Деплой, версия и сохранность состояния

Новый путь не строит JSON-план, не раскрывает граф и не требует `assistant.navigate`. На каждом запросе Gateway сам либо отвечает текстом, либо возвращает стандартный `tool_call`; Django валидирует и исполняет зарегистрированный инструмент, а результат получает следующее сообщение модели как `role="tool"`. Незавершённая беседа сохраняет уже переданные реплики, поэтому обычное уточнение продолжает тот же контекст; новое намерение распознаёт сама модель по диалогу, без словарей фраз. Состояние ACTION хранит исходный `tool_call_id` только до явного подтверждения либо отмены.

READ публикует единый `plan_contract()` одновременно в Function Schema и в серверной проверке: вложенные объекты, массивы, перечисления, required и nullable-поля преобразуются рекурсивно. `filters[].value` описывает допустимое JSON-значение общего типа, а конкретный тип поля, права, сущность, фильтры и сортировка проверяются существующим ORM-валидатором перед выполнением. Для схем, которые полностью удовлетворяют требованиям OpenAI strict, передаётся `strict: true`; произвольные object/array-контракты остаются non-strict, а backend всё равно является окончательной проверкой.

**CODE_ONLY, 2026-10-18 (metadata и компактный контекст):** модель получает только IDs доступных сущностей в схеме `read`; для незнакомой сущности она вызывает зарегистрированный read-only `schema.describe`. Он строится из тех же Django metadata, что `read`, и возвращает поля, разрешённые связи, типы, ограничения и бизнес-представления одной сущности. Полный каталог полей не передаётся в системном prompt; технические `assistant.catalog` и `assistant.capabilities` остаются внутренними средствами аудита и не публикуются как model tools. Переход к настроенной пользовательской модели допускает только безопасные identity-поля configured Django user (`id`, `username`, имя и фамилия); пароли, токены и прочие auth-поля не становятся доступны.

Завершённый Function Calling turn удаляет из `agent_run` пары `assistant.tool_calls`/`role: tool` и полные массивы READ. Между turn сохраняется только компактная структурированная память последнего READ (сущность, применённый запрос, агрегаты, счётчики и ограниченный набор ID) и последней описанной схемы; незавершённый tool-call и ожидающее ACTION-подтверждение не разрываются. История пользовательских реплик ограничивается приблизительным токенным бюджетом, а не только числом сообщений. JSON null у необязательного верхнего аргумента инструмента нормализуется как отсутствие аргумента; READ применяет свои документированные defaults (`order_by=-id`, `limit=20`) до ORM-исполнения.

**CODE_ONLY, 2026-10-18 (строгий READ и подтверждённая память):** до выбора сущности `read` не публикуется как Function Definition: модель сперва вызывает `schema.describe`. В следующем стандартном Function Calling вызове `read` получает специализированную JSON Schema, автоматически собранную из тех же Django metadata: выбранная сущность, пути полей, допустимые для каждого поля операции, `choices`, сортировки, группировки и агрегаты ограничены отдельными enum/anyOf-вариантами. Значение `income` поэтому не может быть подставлено в enum другого поля, а человекочитаемая метка choice не является допустимым идентификатором. Backend всё равно повторно проверяет вызов штатным `validate_plan()`.

До выбора операции публикуются только два discovery-инструмента `schema.describe` и `action.describe`; полный контракт единственной ACTION появляется после `action.describe`, а остальные ACTION Function Definitions в этот вызов не передаются. Описание ACTION берётся из того же зарегистрированного capability, который исполняется backend. Свободный строковый аргумент изменяющей операции должен буквально присутствовать в одном из сообщений пользователя текущей беседы; иначе backend возвращает инструменту отказ, и модель просит значение обычным языком. Choices, даты и числовые значения продолжают проверяться штатным контрактом и бизнес-валидатором, а подтверждение ACTION остаётся обязательным.

Последний полный READ хранит ограниченный набор фактически возвращённых строк вместе с query, полями, счётчиками и owner беседы, а не свободное резюме модели. Повторный READ может быть обслужен из этой памяти только при текущих правах, той же сущности/базовом наборе, полном предыдущем результате и наличии всех требуемых полей; более узкий фильтр и агрегат вычисляются backend по сохранённым строкам. Неполная выборка никогда не используется для общего агрегата и вызывает обычный ORM READ. Фактический ответ текущего READ рендерится backend исключительно из подтверждённого результата, а не из текста модели. Живая проверка strict Gateway и этого поведения для данной ревизии ещё не выполнена.

**CODE_ONLY, 2026-10-18 (бизнес-разделы Function Calling):** активный набор tools больше не строится вокруг обязательных `schema.describe`/`action.describe`: эти два model tools и требование предварительно открыть технический узел удалены. Один существующий capability registry теперь собирает пользовательские разделы из Django app-владельца зарегистрированного executor; действие может явно состоять в нескольких разделах через metadata. READ-ресурс регистрируется рядом с capability один раз как человеческое имя, описание, Django entity и разделы. Его Function Definition генерируется на лету из единого `assistant_read.plan_contract(entity)`, но entity не передаётся модели и подставляется сервером в единственный универсальный `read` executor. Первая модель получает только `assistant.select_area`; после выбора — только ACTION текущего раздела и его READ-ресурсы. Раздел можно выбрать по прямому указанию пользователя или по смыслу запроса тем же стандартным tool call, без словаря фраз в backend. Новое Django-приложение становится разделом после штатной регистрации capability/resource; удалённое перестаёт публиковаться без ручной правки центрального списка.

Системная инструкция требует уточнять только бизнес-смысл — период, счёт, сумму, человека или намерение — и не спрашивать названия полей, ID, коды либо JSON. Человеческие подписи и допустимые значения ACTION задаются в его существующем contract; фактические поля и ограничения READ по-прежнему берутся из Django metadata. Локально проверены 73 теста `tenders.test_assistant_tools`/`tenders.test_assistant_conversations`, включая реальную цепочку `assistant_conversations.respond()` → выбор «Касса» → ресурс «Операции по кассе» → универсальный Django READ с тестовой записью. Живой Gateway для этой ревизии **NOT VERIFIED**: в текущем изолированном окружении отсутствуют `TIMEWEB_AI_API_KEY` и `TIMEWEB_AI_BASE_URL`; мок не считается заменой этому испытанию.

**CODE_ONLY, 2026-10-18 (проверка выбора раздела):** каталог первого шага теперь включает все шесть собственных пользовательских Django-приложений с явным `AppConfig.verbose_name` — «Калькулятор», «Касса», «Зарплата», «Финансы», «Расчёты заказов» и «Тендеры» — даже если в конкретном разделе ещё нет READ-ресурса или ACTION. Это исключает ложную проверку, в которой у модели был единственный доступный раздел и ей не из чего было выбирать. Список не зашит в Agent Core: новое пользовательское приложение попадает в него после обычного объявления `verbose_name`, а внутренний `core` и Django framework apps не попадают. На текущем вертикальном срезе полная READ-цепочка зарегистрирована только для «Кассы»; остальные пять разделов намеренно пусты и нужны лишь для честной проверки первого Function Calling выбора. Это подтверждает механизм выбора раздела, но не готовность READ для всего сайта.
