# Протокол работы тендерного ассистента

Этот документ — обязательная точка входа перед изменением логики ассистента, поиска товаров или расчёта себестоимости. Он описывает не интерфейс, а границы ответственности и фактический технический маршрут данных.

## 1. Назначение системы

Ассистент получает позицию тендера (НМЦК, наименование и ТЗ), предлагает производственный маршрут и рассчитывает себестоимость. Если для позиции нужен готовый бланковый товар, ассистент ищет варианты в каталогах Oasis и Gifts.

Главный принцип:

> LLM понимает естественный язык и формирует структурированный план. Бэкенд проверяет этот план, ищет и ранжирует товары, выполняет все вычисления и принимает только актуальные данные поставщиков.

LLM не является поисковой базой, калькулятором или источником актуальной цены.

## 2. Источники истины

| Данные | Источник истины |
|---|---|
| Подтверждённый опыт ассистента | production-база Timeweb |
| Текущие цены и остатки Oasis | онлайн API Oasis |
| Карта категорий Oasis | зафиксированный снимок `CatalogCategory`, обновляемый из API |
| Товары, цены, остатки и категории Gifts | импорт XML в production-базу |
| Формулы, валидация, фильтрация и ранжирование | код бэкенда в Git |
| Неподтверждённая гипотеза и диалог | `ProductionTrainingSession` и `ProductionTrainingTurn` |

Git не хранит production-базу, выгрузки поставщиков, документы заказчиков и секреты.

## 3. Ответственность участников

### Администратор

- подтверждает или исправляет гипотезу;
- выбирает частично подходящий товар осознанно;
- задаёт правила обычным языком;
- подтверждением превращает текущую версию в учебный пример.

### LLM

- читает полное наименование и ТЗ;
- определяет цельную товарную сущность: например, `рубашка поло`, а не `одежда`;
- выделяет синонимы, обязательные и желательные свойства;
- переводит обратную связь администратора в атомарные команды протокола;
- получает полную актуальную карту категорий и выбирает только существующие `source + category_id`;
- предлагает производственный маршрут и объясняет его.

LLM запрещено:

- придумывать ID категорий и коды поставщиков;
- самостоятельно фильтровать каталог или вычислять итоговый рейтинг;
- создавать каталожную цену из памяти или учебного примера;
- выполнять арифметику себестоимости вместо бэкенда.

### Бэкенд

- нормализует и валидирует JSON LLM;
- применяет команды обратной связи к существующему плану, не заменяя его целиком;
- хранит и отдаёт LLM полные карты реальных категорий;
- выполняет запросы к Oasis и локальному каталогу Gifts;
- извлекает факты и из полей товара, и из названия/описания;
- выполняет жёсткие исключения, считает баллы и формирует три варианта;
- повторяет поиск по альтернативным категориям и по тексту;
- принимает цену только из текущей найденной карточки;
- рассчитывает расходы, итоги и производственный маршрут по детерминированным правилам;
- сохраняет все версии обратной связи и подтверждённого знания.

## 4. Полный маршрут одной позиции

1. Бэкенд создаёт или продолжает `ProductionTrainingSession`.
2. В `build_training_hypothesis()` LLM получает позицию, текущую гипотезу, обратную связь, типы производства, похожие подтверждённые примеры, источники знаний, возможности каталогов и контракт команд.
3. LLM возвращает смысловой `catalog_intent` и производственную гипотезу.
4. Бэкенд нормализует план. Неизвестные операции и источники отклоняются с диагностикой.
5. При обратной связи LLM возвращает `catalog_operations`; бэкенд применяет их к текущему `catalog_intent`.
6. Бэкенд загружает полный зафиксированный список активных категорий Oasis и Gifts.
7. Отдельный вызов LLM выбирает из этой карты реальные категории. Любой выдуманный ID отбрасывается.
8. Бэкенд ищет товары в выбранных категориях, извлекает свойства, фильтрует и ранжирует результаты.
9. Если подходящих вариантов нет, выполняется повтор с ещё не проверенными категориями, затем полнотекстовый поиск по сущности и синонимам.
10. Если точных совпадений нет, бэкенд возвращает ближайшие частичные варианты с явным списком расхождений.
11. Точный вариант с актуальной ценой может быть выбран автоматически. Частичный вариант выбирает администратор.
12. `apply_catalog_candidate()` добавляет подтверждённую текущим поиском цену в расходы. Бэкенд пересчитывает себестоимость.
13. Каждый пересчёт сохраняется как `ProductionTrainingTurn`.
14. После подтверждения создаётся новый `ProductionTrainingExample`; предыдущий пример той же позиции деактивируется через `superseded_by`, но не удаляется.

Основные точки кода: `tenders/services.py::build_training_hypothesis`, `tenders/services.py::_select_catalog_category_tasks`, `tenders/catalog.py::catalog_candidates_for_line`, `tenders/services.py::apply_catalog_candidate`.

## 5. Контракт смыслового поискового плана

`catalog_intent` передаёт смысл, а не SQL/API-фильтры поставщика:

```json
{
  "item": "рубашка поло",
  "product_class": "футболка",
  "categories": ["поло"],
  "synonyms": ["футболка поло", "polo shirt"],
  "required": [{"label": "Цвет", "value": "белый", "weight": 1}],
  "preferred": [{"label": "Материал", "value": "хлопок", "weight": 0.6}],
  "secondary": [],
  "constraints": [{
    "field": "gender",
    "operator": "not_in",
    "values": ["женский"],
    "level": "required",
    "weight": 1,
    "missing_policy": "allow"
  }],
  "ranking": [{"criterion": "price", "weight": 0.8}],
  "fallback_queries": [{"terms": ["рубашка поло", "поло"], "relaxable": false}],
  "source_strategy": [{
    "source": "oasis",
    "category_terms": ["поло"],
    "query_terms": ["рубашка поло"],
    "search_fields": ["name", "category", "attributes"]
  }]
}
```

Допустимые коды источников — только `oasis` и `gifts`. `categories` и `category_terms` здесь являются смысловыми подсказками. Реальные категории появляются только на следующем шаге.

## 6. Карта категорий и выбор категорий

### Правило

LLM должна видеть полную карту доступных категорий, а не короткий список, предварительно угаданный бэкендом. Бэкенд может вычислить лексическую близость только как подсказку порядка, но не имеет права до LLM удалить остальные категории.

LLM получает компактное описание каждого узла: `source`, `category_id`, `name`,
`parent_id`, `parent_name`, непосредственные `children` и полный `path`. Родитель и
дети определяются по ID, а не по глубине или синтаксису пути конкретного поставщика.

LLM возвращает несколько существующих категорий с семантическими ролями:

```json
{
  "category_tasks": [
    {
      "source": "supplier-code",
      "category_id": "real-id",
      "role": "primary",
      "priority": 1,
      "reason": "Узел наиболее полно соответствует товарной сущности"
    }
  ]
}
```

Допустимые роли:

- `primary` — основной узел, наиболее полно соответствующий товарной сущности;
- `equivalent` — альтернативный узел с тем же или почти тем же смыслом;
- `conditional` — узел применим только при структурированном условии из ТЗ;
- `fallback` — более широкий узел для последующей резервной попытки.

Роль определяется из смысла узла, его parent/children и требований ТЗ. Нельзя
считать parent хуже child, автоматически выбирать leaf, самый глубокий узел или
узел с максимальным числом лексических совпадений. Структура конкретного
поставщика не кодируется отдельными правилами.

Бэкенд сверяет каждую пару с картой. Если точной категории нет, корректный ответ LLM — пустой список, после которого запускается полнотекстовый поиск. Похожая, но смыслово неверная категория не должна выдаваться за точную.

### Oasis

- Категории хранятся в `CatalogCategory` как снимок.
- Если снимка ещё нет, первый поиск получает дерево из API и сохраняет его.
- Для явного обновления используется `python manage.py sync_oasis_categories`.
- Сами товары Oasis локально не фиксируются для поисковой выдачи: поиск, цена и остаток получаются онлайн.
- Обновление карты не загружает изображения или товары.

### Gifts

- Полный импорт `sync_gifts_catalog()` читает `product.xml`, `tree.xml`, `stock.xml` и `filters.xml`.
- `tree.xml` сохраняется в `CatalogCategory` и связывает каждый товар с `category_ids` и `category_names`.
- Выбранная категория фильтрует товары по реальному ID; полнотекстовый поиск использует `search_text`.
- Система сохраняет URL изображения из каталога, но не скачивает файл изображения.

После изменения парсера Gifts нужен один полный повторный импорт production-каталога, иначе ранее загруженные товары останутся без связей с категориями.

## 7. Повторный поиск

Поиск обязан завершить маршрут, а не останавливаться после одной неудачной гипотезы:

1. выбранные LLM реальные категории;
2. ещё не проверенные реальные категории;
3. полнотекстовый поиск по `item`, синонимам и `fallback_queries`;
4. ранжирование точных или ближайших товаров;
5. только после этого — результат «не найдено» с диагностикой источников и причин отсева.

Нельзя ослаблять запреты (`not_in`, `not_contains`) и тип товара. Положительные требования можно использовать для выбора ближайшей альтернативы, но расхождение обязательно показывается пользователю.

## 8. Факты, фильтры и частичные совпадения

Свойства читаются из структурированных полей товара, атрибутов, названия и описания. Поэтому слово `женская` в названии считается значением пола даже при пустом отдельном поле.

До ранжирования безусловно исключаются:

- товар другого типа;
- запрещённое значение (`not_in`, `not_contains`);
- запрещённый источник;
- нулевой доступный остаток.

Товар без нарушения структурированного обязательного правила всегда выше нарушителя. Если есть хотя бы один такой товар, нарушители обязательного правила не показываются. Когда обязательное правило не выполнено ни одним товаром, возвращаются ближайшие частичные варианты с `mismatches` и `unknown`. Расхождение по обычному или желательному свойству не блокирует товар: его место определяют веса, поэтому явно заданный приоритет цены способен поставить дешёвую частичную альтернативу выше точной по желательному составу.

Положительное обязательное требование определяет точное совпадение, но не должно обнулять всю выдачу. Например, лонгслив плотностью 200 г/м² может быть показан ниже как альтернатива требуемым 141 г/м². Запрещённая женская модель не может быть возвращена как альтернатива, если действует правило `gender not_in [женский]`.

## 9. Ранжирование и веса

Бэкенд считает числовой рейтинг; LLM лишь задаёт относительную важность критериев от 0 до 1.

Базовые сигналы:

- совпадение типа товара — 100;
- материал/состав — 40;
- цвет — 40;
- плотность — 30;
- совместимость с нанесением — 25;
- остаток — 15;
- прочая характеристика — 35.

Вес из `ranking`, `required`, `preferred`, `secondary` или `constraints` заменяет базовый вес соответствующего критерия шкалой до 100. Совпадение добавляет баллы, расхождение вычитает их, неизвестное значение получает меньший штраф. Затем могут добавляться:

- точность названия: `SequenceMatcher × 100 × weight(name)`;
- цена: нормализованные 0–100 баллов, где минимальная цена получает максимум, умноженные на `weight(price)`;
- предпочтительный поставщик: +20.

Порядок важнее суммы баллов: сначала соблюдение структурированных обязательных правил; после этого рейтинг, наличие цены, цена, сходство названия и стабильная сортировка. Вес не способен вернуть товар, исключённый жёстким запретом.

Веса можно перестраивать обратной связью. Например, «цена важнее состава» переводится в `set_priority` для `price` и `material`, после чего бэкенд пересчитывает рейтинг.

## 10. Протокол обратной связи

LLM переводит фразу администратора в атомарные `catalog_operations`. Бэкенд применяет команды к текущему плану и возвращает ошибки неприменённых команд.

| Намерение | Команда |
|---|---|
| разрешить значение | `allow` |
| запретить/исключить | `forbid` |
| сделать обязательным | `require` |
| предпочесть | `prefer` |
| опустить ниже | `deprioritize` |
| не учитывать поле | `ignore` |
| изменить вес | `set_priority` |
| добавить/удалить синоним | `add_alias` / `remove_alias` |
| определить поведение при пустом поле | `set_missing_policy` |
| числовые пределы | `lte` / `gte` / `between` |
| оставить один источник | `source_only` |
| предпочесть источник | `prefer_source` |
| задать область правила | `set_scope` |
| отменить правило | `remove_rule` |

Политики отсутствующего значения:

- `reject` — исключить;
- `allow` — оставить наравне;
- `allow_with_penalty` — оставить ниже явно подходящих.

Обратная связь изменяет текущий план точечно. Если LLM не сформировала валидные команды, старый план сохраняется, а подтверждение обучения блокируется предупреждением.

## 11. Расчёт и каталожная цена

LLM может назвать процессы и смысл статей, но не является доверенным калькулятором. Бэкенд:

- валидирует рецепты расчёта;
- считает количество, цену за единицу, общую себестоимость, доставку, НДС и итог;
- выполняет специализированные расчёты, включая раскладку и производственные формулы;
- повторно нормализует итог после выбора товара.

Каталожная статья расходов создаётся только из текущего `catalog_candidate`, у которого есть ID, поставщик, актуальная цена и остаток. Цена из ответа LLM, памяти или старого учебного примера удаляется, если текущий поиск не подтвердил карточку.

Точное совпадение может автоматически попасть в расчёт. Частичное совпадение не включается автоматически: администратор должен нажать «Взять в расчёт», тем самым принимая перечисленные расхождения.

## 12. Обучение и embeddings

`ProductionTrainingTurn` хранит каждую версию диалога. Подтверждение создаёт `ProductionTrainingExample`; предыдущая версия деактивируется и связывается через `superseded_by`. Подтверждённые решения по товарам отмечаются в `CatalogMatchDecision`.

Embedding используется только для поиска похожих подтверждённых учебных примеров (`_training_examples_for_line`). Он помогает выбрать опыт, который показать LLM, но не ищет и не ранжирует товары Oasis/Gifts. Каталожное ранжирование выполняется детерминированно по текущим карточкам и весам.

Учебный пример — контекст, а не источник текущей цены и не глобальное правило для всех товаров.

## 13. Диагностика

Каждая попытка поиска должна сохранять:

- режим (`selected_categories` или `full_text`);
- реальные `category_tasks`;
- поисковые термины;
- число полученных и рассмотренных товаров;
- число исключений по причинам `out_of_stock`, `source`, `product_type`, `forbidden`;
- количество точных и частичных совпадений;
- итоговое число кандидатов;
- статус каждого источника и ошибки выбора категории.

Сообщение «не найдено» без этих данных считается недостаточной диагностикой.

## 14. Найденная инженерная ошибка

Поиск работал до усложнения, потому что широкий текстовый запрос позволял каталогу самому вернуть релевантные названия. Затем между LLM и каталогом появилось несколько несовместимых ограничений:

1. Бэкенд заранее сокращал карту до 12 лексически похожих категорий на поставщика. LLM физически не могла выбрать категорию, которую бэкенд уже скрыл.
2. Обычный импорт Gifts не сохранял связи товаров с `tree.xml`; в production было ноль строк `CatalogCategory`, а у товаров — пустые `category_ids`.
3. Любое несовпадение положительного обязательного свойства удаляло товар. При отсутствии идеальной плотности или состава выдача становилась пустой вместо списка ближайших вариантов.
4. Старый подтверждённый пример мог принести в новый расчёт каталожную цену, хотя текущий поиск не нашёл товар.
5. Диагностика показывала только «кандидатов 0», не объясняя, сколько товаров пришло и почему каждый был удалён.
6. При поиске Gifts по выбранной категории бэкенд сначала ограничивал всю таблицу первыми 1500 товарами и только затем проверял `category_ids`. Правильный товар за этой границей был невидим. Теперь категория фильтруется на уровне БД до лимита (с безопасным потоковым вариантом для СУБД без JSON-фильтра).

Исправленная граница ответственности проста: бэкенд хранит полную реальную карту → LLM выбирает реальные категории → бэкенд валидирует выбор, ищет, жёстко применяет только запреты и ранжирует точные/частичные совпадения → цена попадает в расчёт только из текущей карточки.

## 15. Обязательная проверка при изменениях

Перед развёртыванием изменения поиска должны доказать тестами:

1. LLM получает полную карту, включая категорию, которую лексический алгоритм не выбрал бы.
2. Выдуманный ID категории отклоняется.
3. Поло направляется в реальную категорию поло.
4. При отсутствии точного свойства возвращается ближайший товар с расхождением.
5. Запрещённое значение исключается, в том числе если найдено только в названии.
6. Gifts сохраняет категории и связи товаров при полном импорте.
7. Категория Gifts фильтруется до лимита кандидатов.
8. После пустой категории выполняются альтернативная попытка и полнотекстовый поиск.
9. Цена LLM без текущего кандидата не попадает в расчёт.
10. Веса обратной связи меняют порядок, но не обходят запреты.
11. Локальные тесты не подключаются к production-базе.

После развёртывания проверяются production-логи на позициях «поло» и «лонгслив»: выбранные категории, полученные товары, причины отсева, финальные кандидаты и источник цены.

## 16. Известное следующее ограничение

Сейчас каталожный поиск запускается при построении гипотезы. Целевое правило следующего этапа: Oasis и Gifts опрашиваются только если подтверждённый маршрут содержит «Закупка готового изделия/товаров». Для полиграфии и маршрутов только с закупкой материала каталоги готовой сувенирной продукции использоваться не должны. До отдельной реализации это нельзя считать уже действующим поведением.
