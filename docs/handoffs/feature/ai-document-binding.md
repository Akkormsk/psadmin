### Цель

Проверить, сохраняет ли существующий парсер PSADMIN достаточно текста и структуры из документов ЕИС, чтобы дальнейшая система могла распределить фрагменты по товарам без повторного чтения оригиналов.

Область проверки ограничена исходным чтением:

- полный текст;
- таблицы;
- разделы;
- точность текстовых значений;
- ссылки на документ и расположение фрагмента;
- лимиты и неполное извлечение.

Не проверялись и не связывались с этим этапом:

- формат `source_id/source_ids`;
- классификация `purposes`;
- сопоставление ИИ с товарами;
- нормализация ТЗ;
- маршруты;
- актуальность расчётов;
- жизненный цикл товаров.

### Подтверждённые факты

#### Реальная цепочка чтения

Основная цепочка подтверждена по коду:

1. Файл ЕИС скачивается через `tender_selection/services.py:_fetch_doc_bytes()` и `tender_selection/documents.py:fetch_document()`.
2. `tender_selection/services.py:store_document_preview()` передает байты в `tender_selection/documents.py:extract_preview()`.
3. Формат выбирается по расширению и сигнатуре файла:
   - DOCX: `_docx_html()`;
   - XLSX: `_xlsx_html()`;
   - PDF: `_pdf_html()`;
   - старый DOC/XLS: временное преобразование LibreOffice через `tender_selection/office.py:convert_office()`;
   - ZIP: `_archive_content()` или выбор единственного вложения.
4. Результат сохраняется как HTML/preview в `DocumentPreview`.
5. `tenders/calculation_v2_pipeline.py:_bounded_documents()` читает сохранённый preview и отделяет текст, таблицы, изображения и предупреждения.
6. `tenders/source_memory.py:document_blocks()` разбивает текст на адресуемые фрагменты.
7. Фрагменты сохраняют document ID, location, section/heading context, table context и image/page адреса.
8. `tenders/document_evidence.py:DocumentEvidence` сохраняет извлечённые facts и fragment addresses вместе с конкретной версией preview.

Preview для просмотра и фактические данные для ИИ формируются из одного сохранённого preview-механизма, но они не считаются полностью идентичными: часть информации намеренно убирается из модели для компактности и обрабатывается отдельно как таблицы или изображения.

#### Полнота и лимиты

Подтверждено для `tender_selection/documents.py`:

- `MAX_BYTES = 25 * 1024 * 1024`;
- `MAX_ROWS = 300`;
- `MAX_PDF_PAGES = 40`;
- `MAX_PARAGRAPHS = 1200`.

Ограничения ZIP:

- глубина вложений не больше 5;
- не больше 50 файлов;
- не больше 25 МБ суммарного бюджета вложений;
- размеры вложенных файлов проверяются отдельно;
- traversal, unsupported, encrypted и unreadable сообщения обрабатываются явно.

Что происходит при достижении лимитов:

- PDF обрабатывает только первые 40 страниц и добавляет `data-document-warning="truncated"`;
- XLSX обрабатывает только первые 300 строк и добавляет строку `ещё строки`;
- DOCX обрабатывает только первые 1200 параграфов или таблиц и добавляет truncated marker;
- старый DOC ограничивает вывод 1200 абзацами;
- изображение с количеством кадров больше 40 добавляет предупреждение об обрезке;
- ZIP сообщает о глубине, размере и количестве элементов.

Синтетическая проверка показала:

- DOCX из 1250 абзацев получил truncated warning;
- XLSX из 350 строк сохранил первые 300 строк;
- позиция 300 уже отсутствовала в результате.

Это значит, что достижение лимита не является молчаливой нормой завершения: неполный preview должен сохранять статус `partial` или `unreadable`, а downstream не должен считать отсутствие текста доказательством отсутствия требования.

#### Структура таблиц DOCX

Файлы `tender_selection/documents.py` содержат отдельную обработку:

- `_docx_vmerge()` для вертикального объединения;
- `_docx_gridspan()` для horizontal span;
- `_docx_table_html()` для сбора HTML-таблицы;
- `_docx_table_html()` используется `_docx_html()`.

Подтверждено:

- горизонтальные объединения сохраняются как `colspan`;
- вертикальные объединения сохраняются как `rowspan`;
- ячейки продолжающейся строки не дублируются;
- текст ячеек сохраняется;
- внутренние абзацы ячейки объединяются через `<br>`;
- встроенные изображения ячеек извлекаются в уменьшенном виде.

Синтетический DOCX с заголовком и объединённой ячейкой дал:

```text
Технические требования
Таблица 1, строка 1
Размер
Таблица 1, строка 2
Длина | ≥ 10 мм
```

HTML сохранил:

```html
<td colspan="2">Размер</td>
<td>Длина</td><td>≥ 10 мм</td>
```

`tenders/document_enrichment.py:document_table_payload()` сохраняет атрибуты ячейки:

- текст;
- `rowspan`;
- `colspan`.

При `expand=False` сохраняются компактные span-сведения.

При `expand=True` объединённые значения повторяются в логических позициях сетки для строкового анализа.

#### Структура таблиц XLSX

Подтверждено для `_xlsx_html()`:

- все листы становятся отдельными HTML section;
- имя листа сохраняется;
- объединённые ячейки сохраняются через `rowspan/colspan`;
- значения загружаются из формулного значения только через `data_only=True`;
- пустая ячейка сохраняет позицию сетки через пропуск merged-cell покрытия;
- число строк ограничено `MAX_ROWS`.

Сложность сложных многоуровневых шапок реальным документом не подтверждена.

#### Структура разделов и иерархии

`tenders/source_memory.py:document_blocks()` сохраняет:

- heading hierarchy;
- `data-outline-level`;
- названия разделов;
- номер абзаца;
- номер таблицы;
- номер строки;
- номер страницы для изображения.

Адреса имеют вида:

```text
Технические требования / Абзац 3
Технические требования / Таблица 2, строка 4
Страница 7 / Изображение 12
```

Для одинакового текста сохраняется один logical fragment с несколькими `occurrences`, поэтому повторяющийся текст в разных разделах не теряет исходные адреса.

Это подтверждено тестом `test_repeated_text_keeps_each_source_address_without_copying_facts` в `tenders/test_document_evidence.py`.

#### Точность текста

Подтверждённые механизмы:

- DOCX читает текстовые ноды ячеек и абзацев;
- XLSX переводит значение ячейки в строку;
- PDF читает постранично текстовый слой через `pypdf`;
- PDF без text layer рендерится в JPEG через `pypdfium2`;
- `_bounded_documents()` валидирует, что изображение является реальным JPEG/PNG/WebP и проходит проверку `PIL`;
- `text_parts()` сохраняет перекрытие 80 символов на границе разбиения;
- таблица передаётся как отдельные строковые фрагменты через ` | `;
- числовые значения и знаки сравнения не заменяются на вычисленное значение.

Тесты в `tenders/test_document_reading_input.py` подтверждают обработку диапазонов, единиц и запрет cross-row/cross-cell изменений.

Пример подтверждённого evidence:

```text
Размер | ≥ 10 и ≤ 12 | мм
```

Система отклоняет:

- другую верхнюю границу;
- другую единицу измерения;
- переставленные ячейки;
- склеивание значений соседних строк.

Ограничение:

- пробелы внутри текста таблиц и абзацев могут быть нормализованы;
- перенос строки и исходная геометрия страницы не сохраняются полностью;
- для PDF нет координатной геометрии ячеек.

#### Старые DOC/XLS

Старый `.doc` в `_doc_html()`:

- проверяет OLE/CFB через `olefile`;
- читает поток `WordDocument`;
- пробует UTF-16LE и CP1251;
- выбирает вариант с большей долей похожего на текст;
- не восстанавливает структуру таблиц;
- может подхватить служебный или стилистический мусор;
- помечает результат как приближённый.

Это подтверждённое ограничение кода.

Старый `.xls` сначала передается LibreOffice в XLSX:

- `tender_selection/office.py:convert_office()`;
- timeout преобразования: 60 секунд;
- результат ограничен 25 МБ;
- macros отключены;
- профиль LibreOffice временный.

Качество реального `.xls` не подтверждено без реального образца.

#### Сканы и изображения

Подтверждено:

- raster PDF страниц рендерится в JPEG;
- PDF-блок сохраняет номер страницы;
- изображения в DOCX преобразуются в уменьшенные JPEG;
- external image URL не добавляется в vision-контекст;
- inline `data:image` проверяется как реальное изображение;
- визуальные фрагменты передаются отдельными image block.

Сканы не преобразуются в структурированную таблицу внутри парсера: OCR выполняется как чтение изображения другим механизмом ИИ.

#### Ссылки на оригинал

Подтверждено хранилище адресов:

- `DocumentPreview` привязан к URL, filename, content hash и parser version;
- `TenderDocument` привязан к тендеру и preview;
- `TenderDocument.assignments` хранит binding адреса;
- `DocumentEvidence` хранит structure fragments и extracted facts отдельно;
- `document_blocks()` сохраняет location;
- одинаковые фрагменты сохраняют несколько occurrence;
- изображения имеют `image_digest`, `image_index` и location;
- каждая запись facts привязана к fragment ID.

Это позволяет заново отобразить evidence для сохранённого фрагмента без копирования текста в downstream-контекст.

Для PDF координаты элемента внутри страницы не сохраняются.

Для ZIP сохраняется имя и порядок вложения, но не физическая геометрия внешнего архивного контейнера.

### Неполные или подтверждённые частично свойства

#### Полнота

**Статус: частично подтверждено.**

Текст для обычного DOCX/DOCX в ZIP, XLSX и PDF с text layer извлекается постранично или по абзацам.

Непроверено:

- ZIP с несколькими разноформатными вложениями.

#### Структура таблиц

**Статус: частично подтверждено.**

Работают объединения ячеек и отдельные строки.

Не доказано:

- многоуровневая шапка сохраняет правильную семантическую связь всех колонок;
- повторяющаяся шапка на следующей странице восстанавливается без потери смысла;
- граница между товарами всегда сохраняется;
- вложенная таблица сохраняется как единый товарный объект;

#### Структура разделов

**Статус: частично подтверждено.**

DOCX может сохранять outline hierarchy.

Не доказано:

- PDF всегда различает заголовок и обычный абзац;
- нумерованные позиции сохраняют тот же смысл после разбивки;
- соседние разделы не объединяются;
- старый DOC сохраняет иерархию.

#### Точность текста

**Статус: частично подтверждено.**

Обычные числовые значения, диапазоны и единицы сохраняются.

Не доказано на реальных образцах:

- качество OCR сканов;
- точность распознавания символов сравнения;
- точность дробных чисел;
- сохранность пробелов в сложных обозначениях;
- качество LibreOffice на старых XLS/DOC;
- сохранение super/subscripts и специальных символов.

#### Ссылки на оригинал

**Статус: частично подтверждено.**

Текстовые фрагменты получают документ, location, section и table row.

Не доказано для PDF/scans:

- точные координаты ячейки;
- координаты абзаца;
- различение двух одинаковых строк с точными координатами в скане;

### Подтверждённые проблемы и последствия

1. **Жёсткие лимиты могут обрезать документ.**

   `tender_selection/documents.py:MAX_PDF_PAGES`, `MAX_ROWS`, `MAX_PARAGRAPHS`, `MAX_BYTES`.

   Последствие: усеченный preview нельзя считать доказательством отсутствия требований за пределами лимита.

2. **PDF со сложной таблицей не получает координатную таблицу ячеек.**

   `_pdf_html()` использует `pypdf` для text layer или рендерит страницу для vision.

   Последствие: адрес не всегда достаточен для точного распределения всех ячеек по товарам.

3. **Старый `.doc` является приближенным.**

   `_doc_html()` не восстанавливает таблицы и outline.

   Последствие: текстовый фрагмент нельзя считать доказательством точной товарной строки.

4. **Сканы остаются изображениями.**

   Файлы снетекстовым слоем сохраняются как page images.

   Последствие: дальнейшее чтение зависит от качества визуального распознавания ИИ.

5. **ZIP ограничен глубиной, количеством и объёмом.**

   `_archive_content()` сообщает об ограничениях.

   Последствие: непрочитанные вложения должны оставаться явным gap, а не считаться отсутствующими условиями.

6. **Предпросмотр не всегда сохраняет геометрию исходного документа.**

   `_bounded_documents()` берет текст и отдельно tables/images.

   Последствие: downstream получает достаточный context для обычных форматов, но сложный layout может потребовать точного оригинала.

### Предположения

### Итоговые ответы

#### Вопрос 1. Можно ли сейчас использовать существующий парсер?

Да, временно и только как базовый парсер для обычных DOCX и простых XLSX/PDF.

Использование допустимо только при одновременном выполнении условий:

- preview не помечен truncation;
- PDF-страницы читаемы;
- ZIP-вложения обработаны полностью;
- нет unreadable-page или parser error;
- сохранён документ, fragment ID и source address;
- неполное чтение не используется как доказательство отсутствия требования.

Сложные PDF, сканы, старый `.doc`, многоуровневые таблицы и неполные ZIP нельзя считать полностью доказательными.

#### Вопрос 2. Какие недостатки реально препятствуют архитектуре?

Подтверждённые недостатки:

- лимиты обрезают оригинал;
- сложные PDF-таблицы не получают координатную структуру ячеек;
- старый `.doc` приближённый;
- сканы не дают табличную структуру;
- ZIP ограничен;
- PDF и HTML не сохраняют все исходные layout-координаты;
- разделы для PDF не всегда являются семантическими heading уровня.

Эти недостатки мешают считать документ полностью обработанным и точно привязанным к товару без явного доказательства формата.

#### Вопрос 3. Есть ли основания сравнивать с Docling?

Да, но только для конкретных проверяемых проблем:

- сложные PDF-таблицы;
- многоуровневые шапки;
- продолжение таблиц на страницах;
- объединённые ячейки;
- OCR PDF и сканов;
- reading order;
- координаты ячеек;
- вложенные таблицы;
- сохранение границ товаров.

Замена парсера не подтверждена общей гипотезой. Сравнение нужно проводить на одинаковых реальных образцах и проверять конкретную потерю структуры существующего парсера.

### Итоговое заключение

Существующий парсер не является пустым или неработающим: он сохраняет текст, таблицы, section/location и ссылки для обычных DOCX и XLSX.

Он не обеспечивает доказанную полноту для всех форматов ЕИС:

- лимиты могут обрезать документы;
- сложные PDF теряют табличную геометрию;
- старый `.doc` не восстанавливает таблицы;
- сканы требуют OCR;
- ZIP и некоторые PDF могут оставаться частично прочитанными.

Поэтому architecture-level решение может опираться на существующий preview memory только при двух обязательных правилах:

1. Неполный или усечённый preview не считается полным чтением оригинала.
2. Факт привязки к товару должен иметь explicit address и source status, а не выводиться из имени файла или неполного текста.

Статус шага: `CODE_ONLY`. Полная серверная и реальная семантическая приёмка не выполнена.
